# r69 的生成长尾和固定输出量回放

100 Gbps 正序的负收益由两条异常长输出落在不同完工链上解释。只把这两条替换为各自历史短输出长度，融合相对原生从吞吐下降 23.9% 变为提高 29.6%。其余三个配对没有请求撞上限，固定逐请求输出量后仍是一正两负。TP2/EP2 的八轮数据没有显示稳定的 20% 吞吐收益，TTFT p99 也有正反序分化。

## 逐条核查 8,192 token

r68、历史 r69 和当前八轮匹配了全部 106 条请求的输入 token 指纹与生成预算。当前客户端启用 EOS，D 入口所见预算均为 8,192。客户端的流式 token 计数与服务端用量一致，848 条请求中 846 条 `stop`、2 条 `length`。两条长输出都发生在 100 Gbps 正序，分别位于原生和融合轮。两条均完成 KV 接收和流关闭。两轮的 D 引擎抢占计数均为零。 [输入与逐请求证据](output-replay.json)

| 撞上限的请求 | 历史 r68 自然输出 | 历史 r69 自然输出 | 本次其余七轮 | 撞上限时的出流 |
| --- | ---: | ---: | ---: | --- |
| 原生首轮 `extract-moves-from-video:66` | 246–277 | 224–268 | 219–268 | 54.70 秒出首 token，181.42 秒结束，首 token 后用时 126.73 秒 |
| 融合后继 `make-mips-interpreter:88` | 390–399 | 380–390 | 385–392 | 127.54 秒出首 token，245.07 秒结束，首 token 后用时 117.54 秒 |

- **原生首轮**。同一配对的融合轮也走 P0→D0，D 两个 rank 接收的描述符合计都为 232.16 MB，D 分配至 KV 就绪分别为 67.0 和 69.6 ms，融合轮输出 254 token 自然结束。长输出沿真实依赖把 `extract-moves-from-video:67` 的就绪推到 181.42 秒，最终 187.13 秒完工。缩短首轮后，另一条会话接替压尾。
- **融合后继**。前驱自然生成 140 token，在 67.22 秒完成。该后继在反序的两个融合轮也走 P1→D0，分别自然输出 390 和 392 token。撞上限那轮的 D 接收量更大，KV 在 178.3 ms 内就绪，随后实际连续出流约 117.54 秒。当其他请求全部结束时，它还要输出 7,886 token。

相同的 prompt、生成预算和 P/D 去向均出现过正常短输出。可见证据定位到模型在已交付 KV 后继续生成，到达预算才结束。归档留存每个 SSE 的时间和 token 数，实际 token 序列、logits 和 KV 数值校验未采集，具体分叉 token 和成因仍无法确定。

## 固定逐请求输出量

使用原 r69 四轮实测 `stop` 长度的逐请求下中位数作为所有八轮的同一向量，每轮合计 18,452 token。按实际 SSE 出流曲线取对应 token 到达时间，加实测收尾开销。需要延长短输出时，按该请求最近 64 token 的出流速度补时间。仍按 `max(计划到达, 前驱结束 + 工具间隔)` 释放后继，沿用各轮观察到的路由、TTFT 各段和服务驻留时间。各轮输入原实测长度时，复原全部请求的实际就绪和完成时间，误差低于 0.1 µs。

| 同档配对 | 实测吞吐变化 | 固定输出后的吞吐，原生 → 融合（token/s） | 固定输出后的吞吐变化 | 固定输出后整轮时长差，融合减原生 |
| --- | ---: | ---: | ---: | ---: |
| 100 Gbps 正序 | −23.9% | 105.06 → 136.00 | +29.4% | −39.96 s |
| 200 Gbps 正序 | +5.8% | 123.95 → 135.62 | +9.4% | −12.82 s |
| 200 Gbps 反序 | −9.3% | 131.29 → 121.47 | −7.5% | +11.35 s |
| 100 Gbps 反序 | −10.3% | 133.03 → 122.03 | −8.3% | +12.51 s |

100 Gbps 正序只替换两条长输出时，直接取各自的前 268 和 390 token，均在已观测的出流范围。原生完工从 187.13 缩到 175.63 秒，融合从 245.07 缩到 135.70 秒。两条长输出对完工差的净影响为 97.88 秒，解释了实测多出的 57.94 秒，并掩盖了这一配对约 40 秒的 P 路径优势。该回放吞吐为 108.22 → 140.22 token/s，两个实际工作总量经替换后是 19,008 和 19,028 token。

再用当前八轮自然输出的逐请求下中位数、各请求最短实测出流长度，以及保留每条请求原最早就绪时刻的回放做灵敏度检查，四对的方向均一致。最短长度版本八轮均无需外推，收益为 +28.8%、+9.4%、−7.3%、−8.1%。这些是沿用已观测服务轨迹的条件估计。真实更换输出量会重新组批、排队和选路。主模型固定了每条请求就绪后的首 token 路径，回放的 TTFT p99 因此与实测相同。

## P 路径和 TTFT 的正反序差异

用代理同机时钟拆出 P HTTP 和 D 段。P 首块派发到持有交接页使用 P 同机时间。P HTTP 发出到首块派发通过发送与返回的因果边界对齐两机时钟，单臂估计误差约 ±0.10 秒。首块派发到持页包括分块之间的等待与 KV 工作。

| 同档配对 | 实测 TTFT p99，原生 → 融合（秒） | P HTTP 到首块派发均值（秒） | 首块派发到 P 持页均值（秒） | 固定输出量，仅交换 P HTTP 对完工的影响，融合减原生 |
| --- | ---: | ---: | ---: | ---: |
| 100 Gbps 正序 | 134.26 → 103.27 | 58.21 → 41.99 | 6.57 → 4.83 | −40.92 s |
| 200 Gbps 正序 | 122.59 → 109.64 | 51.38 → 45.22 | 4.67 → 3.83 | −11.77 s |
| 200 Gbps 反序 | 117.26 → 126.07 | 47.16 → 52.16 | 4.29 → 4.81 | +12.14 s |
| 100 Gbps 反序 | 112.69 → 121.45 | 45.06 → 49.71 | 4.76 → 4.47 | +13.36 s |

未触顶的三组里，出首 token 前的 D HTTP 段均值差在 0.04 秒内。按实测时序作双向阶段交换，P HTTP 分别解释完工变化中的 −10.04、+12.07、+14.12 秒，生成量和实际出流节奏合计影响约 0.4–1.1 秒。仅看两臂 P、D 副本均相同的请求，三组 P HTTP 均值变化仍为 −5.16、+3.85、+5.18 秒。100 Gbps 反序甚至出现派发后的 P 驻留缩短而首块前等待增加的情况。这些证据将波动定位到 P 批次的推进与排队层级，当前 trace 的粒度不足以给单个融合算子分账。
