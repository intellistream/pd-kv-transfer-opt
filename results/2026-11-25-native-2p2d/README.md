# 原生 2P2D 的 100/200 Gbps 对照与完工归因

2026 年 11 月 24–25 日在两台各 8 卡的 Ascend 910B2 上完成 r43、r69 和 Basin 的 18 轮正式测量，覆盖 5,056 条请求及 288 条端口汇总记录。运行版本为 `29bad7a11909eef4cf16b8f3b714c0a7da97a2d8`，使用 Qwen3.5-35B-A3B BF16、2P2D、每实例 Attention TP4 / Expert EP4 / DP1。P/D 本地 APC、D 原生重算调度器、原生路由和自然 EOS 均启用。两侧 Store 各 64 GiB，每个模型 rank 8 GiB，两侧均就近分配。每台八口对称出站限额为 100 或 200 Gbps，对应逐口 12.5 或 25 Gbps。 [实验计划](../../docs/terminal-throughput-plan.md) · [冻结配置和运行入口](../../docs/native-npu-run.md) · [复现指纹](manifest.json)

## RDMA 是否挡住 D 供给

D 缺供按最终路由回看。一个副本上没有已收到 KV 且仍活动的请求，同时仍有去该副本的 P 请求在途，才计入这个窗口。r69 的 100 Gbps 两轮，D0/D1 这样的窗口分别有 32.70/43.98 秒和 30.22/36.12 秒。其中与 P 的任意 GET 重合的每副本仅 2.19–4.15 秒，均无 D 热点。r69 四轮逻辑 GET 为 88.08–100.15 GB，D 八口实际出站各约 8 MB。历史 r69 的对应 D 出站约 190–195 GB。当前双侧就近池下大量逻辑 GET 和极少 D 出站并存，原历史压力机制在受控端口上没有重现。 [历史 r69 的逐轮量级](../../docs/restore-workload-screen.md#r69-用实际根进度校准后继投放时间) · [当前供给重合](trace-analysis.json)

相同负载的 200 Gbps 轮中，部分单次传输的等待更短。r69 正反序的 P GET 中位数分别从 691/583 ms 降到 279/283 ms，D 分配后到 KV 就绪的均值从 364/342 ms 降到 188/171 ms。Basin 五倍突发的 P GET 中位数从 80 降到 44 ms，D 分配后到 KV 就绪从 161 降到 102 ms。以上是调用或交接等待的效果。逻辑读源、字节与组批也随实际执行变化，时延差与整轮吞吐差需各自验证。

将端口计数裁到第 60–150 秒的突发窗口，五倍突发 100 Gbps 的 P/D 八口平均出站分别是 14.43/2.41 Gbps，区间采样峰值为 29.12/9.95 Gbps。200 档的平均为 14.18/1.94 Gbps。短会话自然排空 100 档同窗平均为 14.54/1.15 Gbps，两组在两档均没有单口达到相应配额的 85%。五倍突发中两档实际 P、D 去向均相同的 115 条，D 分配到 KV 就绪的配对中位差为 −24.2 ms。再要求实际输出 token 数相同后剩 15 条，其中位差为 −11.1 ms。这是小样本请求级核对。 [按突发窗口重算的端口计数](fabric-by-burst-window.json)

## Basin 是否出现持续缓存压力

100 Gbps 的五倍突发在第 60–150 秒把 P 平均排队请求数从同档稳态的 0.05 提到 1.98，基础流平均 TTFT 从 1.68 到 4.54 秒。在第 150–360 秒，P 平均排队降到 0.11，基础流 TTFT 回到 1.45 秒，D 两副本活跃生成请求仍平均 20.89，稳态为 9.69。两档五倍实验中，最后完成的是仍在生成的突发会话，分别晚于全部基础会话 208.63/53.64 秒。客户端释放后的观测支持突发排队和残余会话长排空。这个窗口没有覆盖额外会话全部结束后基础流仍持续过载的时段。取消短测只完成 D 生成期的取消和 KV 释放验证，缺 P 在途和 D 等待 KV 两类覆盖，因此没有正式取消臂用于估计回收的因果效果。 [分窗统计](cohort-phase-comparisons.json) · [取消诊断](diagnostics/basin-cancellation.json)

## 关键路径上的节省

对已测得的每个请求，以计划到达和实际前驱完成加工具间隔中较晚者作为其可运行时刻。五段服务时间之和加到这个时刻得到完成时间，整轮取所有请求完成时间的最大值。消去一个阶段后沿会话递推。阶段替换的秒数反映给定已记录工作量和服务时间下的贡献。

把 P HTTP 与同实例任何同步 GET 重合的全部时间以及 D 分配到 KV 就绪的全部时间一起扣除，固定输出量和其余阶段。两轮 r43 的 100 档对应吞吐增幅 0.67%/0.45%。Basin 五个 100 档为 0.05%–0.24%，五倍突发的总时间仅提前 1.69 秒。即使把其每条请求的 P HTTP、转发到 D 和到首 token 的三个阶段一起消掉，五倍 100 档约提高 1.57%。这些推算包含对非网络等待的乐观扣除，适用于固定轨迹下的直接节省。组批、缓存和路由重排的交互需要单独的证据。

固定五倍突发 100 档的 412,965 个输出 token，要达到 200 档实测的 645.93 token/s，整轮需从 718.80 秒缩短到约 639.33 秒。所需的 79.47 秒与同一轨迹上直接消去两段 KV 等待所得的 1.69 秒量级差很大。

r69 两轮 100 档扣除同样阶段的结果是 +1.34%/+8.58%，其中 P 端 GET 可高度本地化。若仅让 P 派发前等待缩短 20%，固定轨迹下的两次整轮条件收益为 +4.47%/+6.57%。这组数据有足够的 P 队列时间供后续分析，但两档方向翻转和观测到的实际路由差异还不足以确认具体的接纳或调度改动。 [18 臂条件回放](cohort-phase-comparisons.json)

r69 两轮 100 档的 P 派发前等待均值 21.62/17.22 秒，p95 为 43.68/37.38 秒。对应有 25/22 个请求经历过本轮分块的页面申请失败，均在首 chunk 派发前且随后成功分配。各请求自身从首次失败到成功分配，与 106 条请求的首派发前等待合计只重合 18.20/8.55 请求秒，占 0.79%/0.47%。把同实例上等待的所有请求一起算，重合比例为 12.87%/7.89%。所有已记录拒绝时点，立即释放可分离且不属于新请求前缀的交接页也无法填补观测到的页缺口。这些事件可说明部分排队，长时间积压还需结合 P 正在执行的分块和组批核对。 [页面拒绝与恢复逐轮核对](r69-prefill-allocation-audit.json)

16 份 rank 记录均已用 CANN 的 Python 导出工具在 CPU 上导出 kernel、通信及 trace 文件。读取时仅去掉导出 JSON 数组末尾的多余逗号。每个 rank 有 10–14 个宿主 graph scope，但导出中缺少当前关联所用的 graph 提交和设备关联事件。四个窗口的 54、53、50、38 个候选步均未通过公共批次标识的核验。因此该轮可报告原生步频和整个 forward 的设备区间，暂不能给出按同一实际批次对齐的算术、访存与机内通信占比。 [离线导出与关联核对](diagnostics/r43-four-rank-breakdown.json)

## 结论

当前原生 2P2D 的数据支持较窄的结论。部分 KV 传输在 200 Gbps 轮中的等待更短。双侧就近布局下，常规长会话和 Basin 的受控端口在实测采样中均有余量。完成时间主要由自然生成及其造成的后继释放决定。Basin 五倍突发的 +12.43% 与短会话排空的 +11.65% 都是有效观测，其归因分别落在压尾链和输出量。当前证据不足以把二者作为 RDMA 吞吐收益。

研究建模应保留三段彼此可区分的状态。P 的接纳排队决定 r69 的供给。Store GET 的逻辑字节和两端实际传输需各自计量。D 的生成工作量与依赖决定常规和 Basin 的收尾。用上述观测作为七步法的事实基线，可以继续考察 r69 的 P 排队或 Basin 的拥塞恢复，端口限速仅在同时有链路持续积压、D 缺供和稳定完工差的负载中作为吞吐优化主张。
