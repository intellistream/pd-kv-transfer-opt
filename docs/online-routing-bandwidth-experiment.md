# 在线路由下的双端 RDMA 限速实验

本文记录 2026-11-20 在两台 910B2 上完成的实机回放，使用当时的 D 单侧共享 Store。最新实机安排见 [Basin 实验计划](terminal-throughput-plan.md)。

## 要回答的问题

1. 在现有 vLLM-Ascend 在线调度、P 本地前缀缓存开启、Mooncake 跨节点复用的条件下，原始网络配置是否已经限制了服务输出速率？
2. 改变 P/D 之间的 RDMA 可用带宽时，输出速率是否随之变化？吞吐发生变化的轮次里，时间具体花在哪一段？
3. 确认瓶颈后，定位能干预的环节，并用逐请求、逐计算步和逐流事件标定及验证模拟器。

以完整会话回放作为主实验。r14 用于校验方向和限速机制，r19 用于核对高恢复波次的阶段归因。当前研究主张和范围见 [七步法](research-seven-steps.md)。

## 对照设计与判读

1. **照常部署，跑原档。** 开启 P 本地 APC 和 Mooncake，用现有代理在线选 P/D，回放全量会话。主指标是客户端每秒收到的输出 token 数，整轮吞吐用总输出 token 除以从首个请求释放到最后一个请求完成的时间。同时记录输出速率时间线、原档网络配置和实际流量、P/D 利用率和阶段等待。
2. **做一次原档 → 限速 → 恢复原档。** 调整 P/D 业务 RDMA 链路的可用带宽，档位依据原档流量和现场能设置的范围确定。若用两端发送端口实现链路限速，在 P/D 两端设置相同档位，分别读回每口配置并核对两向实际流量。保持模型、调度规则、输入、输出、会话释放规则、缓存容量和预热一致。每轮排空后切换。观察到变化后补邻近档位和重复轮，找出吞吐开始下降的区间。
3. **统一每轮起点。** 模型和图预热使用独立于正式会话的缓存命名空间。各档从同等的实验缓存状态和无在途请求开始，使用相同的预热及会话前驱规则。冷启动和热会话各自成组。记录起止 KV 占用、APC 和 Store 容量，使用实验专用 Store。
4. **先看吞吐，再看阶段。** 如果实际网络服务下降、输出速率随之下降，恢复配置后输出速率也回升，就测到了该负载的带宽敏感区间。要判断原档本身是否已经受限，再看原档是否有持续的传输积压和计算等数据，条件允许时提高可用带宽复测。如果吞吐变化小，也核对首 token 和输出间隔是否受影响。沿慢请求查看 D→P 历史恢复、P→D 交接、P/D 计算和等待，找出哪段延迟进入了关键路径。按会话与请求 ID 对齐，保留实际路由、命中、字节和批形，解释调度随带宽变化产生的反馈。
5. **按实测瓶颈选解决办法。** 找到影响吞吐或延迟的具体阶段后，选一个机制做小对照，在同一带宽和负载下量它对该阶段及端到端的改善。

主结果给逐轮成功数、排空时间、请求和输出吞吐、TTFT p50/p95/p99、D TPOT/ITL、分方向实际字节和 GET 等待分布。另报本地命中、远端恢复、全冷计算三类以及换 P 的后继。尾部保留具体请求链和样本数。输出轮间配对差与波动，超时和失败单列并计入总请求数。r11/r12 的双向竞争只作历史参照。

### 事件怎么关联与保存

- **公共键。** 每条带 `run_id`、轮次、主机/角色/实例、PID/TID、物理设备与 TP rank、单调时间与序号。按需附 `request_id`、`session_id`、`predecessor_id`、代理 UUID、`iteration_id/batch_id`、`flow_id/call_id`、`allocation_id`、状态组与缓存对象代次。显式记录父子 span 或因果前驱。包括失败重试、同批多请求、异步完成需要的关联键。
- **时钟。** 同机用单调时钟算耗时。CPU/P/D 每轮开始、结束及定期留单调时间和 Unix 锚点及同步状态，保留对齐误差。CANN 记 rank、stream、设备时间单位和本机锚点。只有持续时长或误差大于待测间隔时，保留事件粒度并标明可判断的范围。
- **聚合。** 请求端 TTFT 用 ready 至第一个有效 token，排空用第一条释放到最后完成，D 的 step/TPOT 与客户端 SSE 到达间隔分别保存。NPU 计算、GET、worker load 是可能重叠或嵌套的区间。阶段归因按依赖链或区间并集计算，保留可重算的边界。缺事件写空值和原因，记录每类覆盖和丢失计数。
- **归档。** CPU 容器按 `run_id` 保存版本和配置清单、原始压缩事件、逐请求/逐步/逐流/缓存生命周期表、指标摘要、端口初值与恢复回执。保留原始事件到派生表的程序版本和 SHA-256。两台 NPU 用每轮独立临时目录写日志与 CANN，排空后经管理路径传回 CPU，校验后清理本轮文件。原始请求、环境配置及大抓取放私有归档，公开包按白名单导出。

沿用现有 [数据口径](data.md) 和 [事件 schema](../schema/rdma-lab-events-v1.json)。表中补齐项是采集计划，需要扩展与现场验收。

D 启动时可用 `ISSUE23_D_STEP_OBSERVABILITY=1` 开启含计算 token 的逐步事件。首轮核对 `d_step_dispatch`、`d_step_ready` 和设备 0 的 `d_step_device` 是否能按批次关联，再测开销。D 的零 token 等待轮、全 rank 设备周期和 RPC 取件细分仍需单独采集。

## 分散会话起点的复测

沿用相同 30 个会话、170 条请求和逐请求输出预算，把首轮集中到达变成 **0.20、0.35、0.50 新会话/s** 的固定间隔。会话内等前驱完整输出后再发下一条，工具等待保持为 0。每臂使用专用的空缓存池、同样的冒烟预热和独立的正式会话缓存命名空间，原有代理照常在线选 P、D。用原档下首轮 P 排队 p95 不超过 5 秒的最高档作为带宽对照，如果三档都超过 5 秒则保留最低档作为诊断点。固定间隔和泊松到达各自复用同一份时间表。两台宿主机均按 **200 → 100 → 10 → 200 Gbps/口** 测量并保存限速前后读回。

CPU 持久目录为 `/root/pd-kv-transfer/runs/online-rdma-20261120-paced/`。每轮保留实际发起、HTTP 响应头、首末 token 与 DONE，另采 vLLM 的 running/waiting、KV 占用、缓存计数和 Mooncake master 的可用指标。每份计划保留会话到达表和指纹，每臂保留端口读回、硬件和服务事件、跨层派生表及归档哈希。固定输出预算和零工具等待使对照可复算，业务代表性需要实测到达与工具时延验证。 [分散到达比较摘要](../results/2026-11-20-online-rdma/paced-comparison.json)
