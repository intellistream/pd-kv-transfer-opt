# r14–r16 的直接相关工作

核查截至 2026-11-19。比较以已实测的两机 16 卡 910B2、Qwen3.5-35B-A3B BF16、2P2D、每实例 attention TP4 / expert EP4 为准。D 侧 Mooncake Store 中的历史前缀经 D→P 恢复，P→D 是另一条请求交接路径。r14 固定字节改变 D→P 端口限速，隔离网络服务对同步 GET 和 P 排队的影响。r15 改同头 Attention 的实际跨机读次数，SSM/conv 按 rank 保留。r16 固定 r15 的远端读选取和载荷，改两个 P rank 间离散页的分发。两类前缀分别为 223,256 和 238,600 token，诊断轮关闭 APC。r19 和 r20 进一步在 APC 开启的真实长会话后继上回切。[实测](results.md) · [版本](deployment.md#运行域) · [数据集](workloads.md#硬限速诊断)

现有方法的可证伪局限、最强固定基线和新设计的适用边界，随 [七步法](research-seven-steps.md) 更新。

## 最接近的已合并实现

**SGLang Mooncake Direct Linker** 的 `--enable-linker-mla-dedup` 于 2026-09-20 合入并进入 v0.5.23。开启后，各 attention TP rank 校对逻辑读取计划，由 rank 0 将远端 Mooncake KV 拉到已注册的设备缓冲，再逐层将离散页 `index_select` 到有界缓冲，做 NCCL broadcast，最后 `index_copy_` 到各 rank 的原物理页。计划不一致时回退到各 rank 自读。合并 PR 中，GLM-5.2、8×H20、TP8、并发 1、FP8 KV、CUDA Graph 下，128K/256K/512K 的 TTFT 分别降低 39.5%/42.1%/38.5%。这是 r15 读一次与 r16 本机打包、广播、散写组合的直接先例。[合并与实测](https://github.com/sgl-project/sglang/pull/39565) · [v0.5.23 的加载代码](https://github.com/sgl-project/sglang/blob/297e54fd105e974cdf401e5b4d20253a22c16f90/python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_direct_linker.py#L231-L292) · [有界打包实现](https://github.com/sgl-project/sglang/blob/d89bc5b57477d89ab1411264599b153b6e34e78d/python/sglang/srt/mem_cache/mla_host_dedup.py#L181-L207)

该开关要求 layerwise 且整个 pool 在 TP rank 间复制。固定源码中，MLA/DSA + Mamba 混合组的 Attention 组件可复制，但由于 Mamba 按 TP 分片，整个组走各 rank 读取。DSV4 的多物理池可走全组复制路径。r15 按 **缓存状态组与 GQA 同头 rank 组** 缩小共享范围，SSM/conv 状态各自恢复。PR 测的是单请求 TTFT，r14–r16 提供受控跨机限速、端口流量和并发下的吞吐与尾延迟证据。[开关条件](https://github.com/sgl-project/sglang/blob/d89bc5b57477d89ab1411264599b153b6e34e78d/python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_direct_linker.py#L218-L237) · [混合组装逻辑](https://github.com/sgl-project/sglang/blob/d89bc5b57477d89ab1411264599b153b6e34e78d/python/sglang/srt/mem_cache/hybrid_cache/linker_pool_assembler.py#L635-L728)

## 同一 AscendStore 入口的公开方案

**vLLM-Ascend #14140 / #19786** 是目前同入口最直接的先例。2026-08-13 的社区任务提出在 `start_load_kv` 为 MLA 消除各 rank 重复读。10 月公开的 PR 对相同对象做全 TP 交错分片，每个 rank 负责一部分 GET，把分片打包后做一次 `all_gather_into_tensor`，再用步长计划写回分散页。PR 截至 2026-11-19 仍开放。守卫要求 `put_step == tp_size`，其 A2 机器上的 GQA 对照在 `put_step < tp_size` 下走全读。作者报告的主要效果来自单机 910B `host_shm` 池和全复制 MLA。我们的 TP4 / 两 KV heads 为 `put_step=2`，工作范围是 GQA 同头子组与逐 rank 私有状态共存的远端恢复。该重合将「分片读、打包和机内汇聚」限定为已知机制，候选贡献须落在混合恢复语义或可重复的系统证据。[社区任务](https://github.com/vllm-project/vllm-ascend/issues/14140) · [公开实现与真机数据](https://github.com/vllm-project/vllm-ascend/pull/19786)

**Mooncake #3929** 已合入 Store 客户端的单次批量读去重。一个调用的键向量中有重复项时，每个唯一键读一次，再把校验过的数据扇出到同次调用内的目的缓冲。vLLM-Ascend 实验固定版中的各 TP worker 分别发起完整 GET。r19 的协调层核对不同 worker 的请求与目的描述符，再选择唯一读取者并做 NPU 端补齐。[Mooncake 已合并改动](https://github.com/kvcache-ai/Mooncake/pull/3929/files) · [实验固定版调用](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py#L756-L785) · [r19](results.md#r19-apc-开启的高远端恢复-ab)

**上游异步支持的范围。** 固定 AscendStore 已能用 `load_async` 启动接收线程。r20 在 `load_async=false` 下移动同批本机分发的完成等待，保留每笔原生 GET 的同步调用。SGLang Direct Linker 也已有混合状态在请求入队时开始的预取，并按各 TP rank 的完成状态发布。较新 Ascend 的 Hybrid layerwise 支持按组逐层恢复，同平台 KVPP 的公开模式则面向非 Hybrid MLA/SFA。[固定版异步分支](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py#L710-L731) · [SGLang 预取](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/storage/mooncake_store/README.md#direct-linker-prefetch) · [Hybrid layerwise](https://docs.vllm.ai/projects/ascend/en/main/user_guide/feature_guide/mooncake_hybrid_attention.html) · [KVPP 支持范围](https://docs.vllm.ai/projects/ascend/en/main/user_guide/feature_guide/kvpp.html#supported-models)

## 必须核对的上游实现

- **vLLM OffloadingConnector 的 canonical layout** 已明确支持 GQA 在 TP rank 多于 KV head 时的共享副本。GPU→CPU 写者按 canonical page ID 轮换，CPU 层只存一份，各 GPU 按自己的页布局 scatter/gather。P2P 路径可把远端 CPU tier 拉到本地 CPU tier。文档的 canonical 支持范围是 full/SWA 与 MLA，限制不兼容的布局。它覆盖了 GQA 同头单副本和轮换 owner 的原则。r15 对应的不同机制是已注册 NPU 目的的 GET 在同头消费组内只发一次，设备侧分发保留原 AscendStore 格式和各 rank 的 recurrent 状态。[固定版 canonical layout 与 P2P](https://github.com/vllm-project/vllm/blob/2d4ebf923903b4f9881ffae8d0246a53a05fbd85/docs/features/kv_offloading_usage.md) · [轮换写者源码](https://github.com/vllm-project/vllm/blob/2d4ebf923903b4f9881ffae8d0246a53a05fbd85/vllm/v1/kv_offload/cpu/gpu_worker.py#L444-L562)
- **vLLM 核心的 Mooncake Store 与实验固定版 AscendStore** 都已有按组区分 Attention 与 recurrent state 的对象命名。Attention 用共享的 head 命名空间，Mamba 用独立的 TP rank。核心 vLLM 的 #49499 修正了混合布局的 per-group replica factor 和写入分工。其官方文档的 MQA 例子是一份 Store shard、多个 rank 各读一份。AscendStore 固定源码中，同头各 worker 也独立发同步 GET。r15 对应的是消费端跨机读去重。[vLLM PR #49499](https://github.com/vllm-project/vllm/pull/49499) · [Mooncake Store 的 MQA 示例](https://docs.vllm.ai/en/stable/features/mooncake_store_connector_usage/#kv_connector_extra_config) · [固定 AscendStore 键与 rank](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py#L174-L237) · [固定同步读取](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py#L782-L850)
- **Ascend KVPP / LayerSplit** 是同平台最近的设计。非 Hybrid MLA/SFA 按层把持久 KV 交给 TP×PCP 内的 owner，计算时将整层广播给其他 rank 的 scratch。v0.30 用户手册列有 Memcache whole-block pooling，也列有 Mooncake layerwise pooling。后者通过 owner 只从池里读取自己的层，在单节点 TP8、Model Runner V2、eager 下验证。这个设计改变持久缓存布局与消费时机。r15 保持完整目标页布局，只在一次历史恢复内部改变谁发跨机读取。普通 Mooncake layerwise pooling 的 Hybrid 支持范围另外核对。#17287 已加入对 align recurrent state 的支持，报告了两卡 TP1、W8A8、16K 的 Qwen3.5-35B 对照。之前 v0.23.0 的限制属于实验版本。普通 layerwise 与 KVPP 的支持矩阵分别适用。[KVPP v0.30 使用范围](https://docs.vllm.ai/projects/ascend/en/v0.30.0/user_guide/feature_guide/kvpp.html) · [KVPP 布局和约束](https://docs.vllm.ai/projects/ascend/en/main/developer_guide/Design_Documents/kvpp.html) · [Hybrid layerwise PR](https://github.com/vllm-project/vllm-ascend/pull/17287) · [v0.23.0 已知限制](https://github.com/vllm-project/vllm-ascend/issues/12390)
- **LMCache、SGLang HiCache 和 PegaFlow** 也覆盖部分机制。LMCache 固定 in-process 版本的首 rank 分支针对 MLA，GET 后广播，GPU connector 再写入目的页。SGLang HiCache 按 CP（或 MLA 的 attention TP）分片，每 rank 恢复自己的 shard，再按层 all-gather 至临时缓冲。PegaFlow 有 TP8 MLA 共享逻辑容量的实测和一组独立跨机 RDMA 吞吐观测，两组的固定条件不同。[LMCache 固定实现](https://github.com/LMCache/LMCache/blob/2d4f4bdf4297fc252d36c953f6abc7de411907c5/lmcache/v1/cache_engine.py#L849-L945) · [HiCache 分片恢复](https://www.lmsys.org/blog/2026-11-02-hicache-distributed-serving/) · [PegaFlow 原始测量](https://vllm.ai/blog/2026-05-18-pegaflow)
- **vLLM NIXL 双向传输** 在固定版本已支持从上一轮 D 拉取前缀。固定的 `kv_recompute_threshold` 基于超过 P 本地 APC 的、额外可取回 token 数，低于阈值时继续在 P 算。v0.33 的异构 TP 映射在高源 TP 时已可跳过冗余 GQA 源 rank，SSM 保留其所需的源集合。r15 是同样 TP 布局下合并多个目标 rank 的接收需求，并补齐本机副本。[D→P 工作流](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload) · [固定阈值源码](https://github.com/vllm-project/vllm/blob/0fc695fc6d1d82e9a5ac6835ac8e4e1c83703665/vllm/distributed/kv_transfer/kv_connector/v1/nixl/scheduler.py#L378-L402) · [v0.33 源 rank 映射](https://docs.vllm.ai/en/v0.33.0/api/vllm/distributed/kv_transfer/kv_connector/v1/nixl/tp_mapping/)

## 邻近机制与比较范围

| 方向 | 已覆盖的机制和证据 | 与当前实验的关系 |
|---|---|---|
| 同字节、不同提交粒度 | **Strata** 分离 GPU 页大小与 CPU/存储的 I/O 单位，用 GPU 辅助搬运缓解碎片。**Range** 用 byte stripes 与完成事件保护的存储 bank，把 NVMe→GPU 的 I/O、散写和发布代价从对象数解耦。**Stint** 已针对碎片 GPU 页实现聚集、大块 GPU↔CPU DMA 和散写，并消融融合 K/V 与双缓冲。[Strata §3–4](https://arxiv.org/html/2508.18572v1#S3) · [Range §3、§5.4](https://arxiv.org/html/2610.21241v1#S3) · [Stint §5.5](https://arxiv.org/html/2611.20106v1#S5.SS5) | 都是 r16 打包原语的先例。工作方向和通信端点不同，报出的 DMA 或恢复收益对应各自的内存层级。 |
| 供给、限速与流量方向 | **DualPath** 让 D 从独立存储读，再利用计算网 RDMA 送 P，经 QoS 隔离 KV 流量与集合通信。**ObjectCache** 在 100→10 Gbps 对照中实测远端 KV 恢复 TTFT 的带宽敏感性，并比较服务端按层聚合。[DualPath §4–6](https://arxiv.org/html/2602.21548v2#S4) · [ObjectCache §5.6](https://arxiv.org/html/2605.22850v1#S5.SS6) | r14 控制 D Store 的出端口，固定使用同样字节与路径。当前实机结果描述该路径的瓶颈及其对同步引擎的传播，概念上的远端恢复带宽敏感在此前已有实证。 |
| NPU 搬运与引擎等待 | **Recompute or Restore?** 在 Rebellions ATOM+ 上建模 host-tier restore 与 compute 共用 engine thread。**FlashOffloading** 在 Ascend910C GLM-5.2 上用 CopySFA 重叠 D 侧 H2D miss load 和稀疏注意力。**HAWK** 用目标 NPU 张量布局和 RDMA buffer 改善 GPU→NPU P→D 传送。[Recompute or Restore? §2–4](https://arxiv.org/html/2611.15126v1#S2) · [FlashOffloading §5.4、§6](https://arxiv.org/html/2611.07542v1) · [HAWK §4.2–4.3](https://arxiv.org/html/2610.29873v1#S4.SS2) | 参考其阻塞观测、源/目的内存与计算重叠的分解。r14–r16 用双机远端恢复的 GQA 与 GDN 状态，r16 的本机目标是同头组。 |
| 路由、准入和模拟 | **Nebula** 用同款 Qwen3.5-35B-A3B，在 H20 7P1D TP1 上做 position-independent cache 的分段放置，以排队、计算和传输预测完成时间。**NetKV** 模拟 P→D 的带宽感知 D 选择。**ServeTwin** 校准分布式服务的闭环反馈。[Nebula §7.2、§9.1](https://arxiv.org/html/2611.09474v1#S7.SS2) · [NetKV](https://arxiv.org/abs/2606.03910) · [ServeTwin](https://arxiv.org/abs/2610.02732) | 适合比较后续路由或模拟证据。r15/r16 路由固定，直接比较同头读和 NPU 本机分发。 |
| 读取与重算校准、负载放大 | **py-kvcache** 按存储 tier 离线标定读取和重算的交叉点，并让相同前缀的读取共享在途操作。**FlatCake** 从生产 trace 找到长会话高并发下的碎片和恢复缓冲竞争。**Fairway** 在 P 的等待队列中结合复用收益和相对等待时间，缓解短时过载下的尾延迟。[py-kvcache §6.5–6.6](https://arxiv.org/html/2609.11744v1#S6.SS5) · [FlatCake §2.2、§3.4](https://arxiv.org/html/2610.38355v1#S2.SS2) · [Fairway §4](https://arxiv.org/html/2611.02082v1#S4) | py-kvcache 和 FlatCake 主要看本地 NVMe 与 host tier，Fairway 主要调度 P 计算。可分别用作恢复门槛、长会话负载和排队策略的参照。 |

## 跨批提前恢复与通信调度

AMPD 已在多轮 P/D 的 D→P 历史 KV 路径重叠前一任务的计算，并实现 prefill 重排。Nuska 已在 vLLM 上根据下游层依赖、批次可行性和期限分配 KV 检索、collective 与 P→D 优先级。r21 观测的空档出现在 connector 提交 GET 之前。仅在低层网络原语仲裁时，这笔尚未提交的工作不在可选集合中。该接口边界说明提前暴露 GET 可能与传输优先级互补。论文 §6 的单 token 输出也覆盖不到本机约 17 s 的 D 排空尾段。两套完整系统在本平台的端到端效果尚待实机比较。[AMPD 实现](https://arxiv.org/html/2602.14516v2#S6) · [Nuska 设计与实现](https://arxiv.org/html/2603.17456v2#S4.SS4) · [Nuska 评测设置](https://arxiv.org/html/2603.17456v2#S6.SS1)

SGLang Direct Linker 已实现入队预取、私有 GPU slot 和全 TP 完成后发布。Cascade 按剩余 SLO 预算和路径带宽决定预取的前缀字节数，在预算不足时考虑重算。通用异步、临时空间、发布屏障和基于 slack 的恢复选择都有对应先例。当前候选的证伪重点是固定消费批与跨机字节下，四 rank 就绪门槛能否给出比同预算先发、最长可行 GET 和期限代理更好的早发准入。当前 r20 重放中，最晚就绪分数与最长可行读的选择一致。[Direct Linker](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/storage/mooncake_store/README.md#direct-linker-prefetch) · [Cascade §IV-C](https://arxiv.org/html/2608.06557v1#S4) · [实证、候选贡献与对照草案](prefetch-selection-claim.md)

## 当前贡献边界和可区分对照

- **r14 的实证**是同一 2P2D 长前缀回放中，固定源、目的和载荷，仅改变 D→P 八口的有效服务上限，追踪到同步 GET、P 取件和批队列等待的变化。已查到同类带宽敏感、远端恢复阻塞和队列放大的先例。自然会话 r11/r12 的前台读取占比小，吞吐效应也小，应保留这一对照的适用边界。[r14 与 r11/r12](results.md)
- **r15 的实证**是对已共享的对象，按 GQA 同头组把消费端的跨机读取合并，并保持各 rank 的 SSM/conv 状态与原数据路径。跨机 GET 914.164→460.173 GB，D MAC TX 的下降与之吻合。SGLang Linker 已有全组复制时的直接读取与分发，vLLM canonical layout 已有 GQA 同头 CPU 单副本，Ascend KVPP 已有按层 owner。当前原型在一个混合模型中按状态组选择恢复方式，同头组内每 16 个逻辑块轮换读者，使用现有的目的页和设备直读。r15 与原生各 rank 读取配对，固定组长与轮换读者的独立收益还有待测量。[r15](results.md#r15-同头-attention-kv-单次跨机读取)
- **r16 的实证**是按相邻描述符把双端地址断点与结构边界分开记账。在远端读取和 P→D 交接字节完全相同的配对轮内，将本机广播约 3,700–3,780 次降到 18–19 次。分发 p50 降约 67%，100/200 Gbps 吞吐分别增 15.96%/33.87%。记录了高并发地址碎片如何把小提交成本传给服务指标。通用打包、散写和按 owner 合批都有前述先例。候选的条件性收益可用低碎片直接分发、高碎片直接分发、同字节打包三种控制解释。[r16](results.md#r16-同头-kv-的打包分发)
- **读取/重算属于独立比较。** r19 已在 APC 开启的真实后继受控波次中确认高 D→P 恢复时的消重收益。要测读取与重算的交叉点，匹配基线包括固定远端读、主动跳过并正常重算、NIXL 式 token 阈值、MemServe 式最大带宽与重算成本比较。若允许 D 保留会话状态，再纳入 AMPD 式 D 本地增量和增量回传，记录 D TPOT/ITL。Evolving Infra 和 Nebula 已计队列与传输，后续模型可着重校准每口服务竞争、页连续性导致的本机分发变化以及 Hybrid checkpoint 就绪。[r19](results.md#r19-apc-开启的高远端恢复-ab) · [判断模型](problem-model.md#远端读取与重算) · [待测协议](bottleneck-and-validation.md#远端读与重算对照)
