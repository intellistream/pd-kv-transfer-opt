# r42 原生长会话带宽复测

## 部署复查

在 `ascend-112` 和 `ascend-180` 的 16 张 910B2 同时空闲时启动 2P2D，每实例 Attention TP4、Expert EP4、DP1。逐实例与 r28 比较实测启动命令和设备，核对两侧同一个 Qwen3.5-35B-A3B BF16 权重索引、模型配置、分词器及原生软件指纹。vLLM 和 vLLM-Ascend 的已跟踪源码均干净，Mooncake 使用 NPU wheel `0.3.11.post1`。两侧 `enforce_eager=False`，P 默认图策略 `FULL_AND_PIECEWISE`，D `FULL_DECODE_ONLY`，P 捕获列表与分块预算保留 4096。正式吞吐使用原生 connector 和路由，关闭调度改动及详细 profiler。[r28 启动与缓存口径](r28-natural-bandwidth-plan.md)

P 本地 APC 开启，D 本地 APC 按 r28 关闭。D 的八个 rank 各贡献 16 GiB 主机池。P 本地可重用的前缀由 APC 提供，外部 Store 命中才走原生各 rank 同步 GET，剩余输入在 P 实算。P→D 的解码状态交接仍走原生 MooncakeConnectorV1。每臂排空，Store 零键，P 用独立 `cache_salt` 隔离逻辑命中，代理重置初态。100/200 Gbps 指 D 八口各 12.5/25 Gbps 的聚合出站限额，逐臂读回八口。该配置与已约定的实验室部署一致。客户的链路方向、拓扑、缓存配置和实际工具间隔需要现场数据核对。[部署口径](experiment-audit.md#启动代理和计量)

客户端、代理和端口计数在 D 主机使用同一单调时钟。逐请求重放从会话就绪、发 P、P 回复、发 D、首 token 到最后完成。P HTTP 是含引擎排队、分块计算和可能同步 GET 的包络。D HTTP 发出至首 token 含交接和准备。方法内部计时结合先前独立的 r33/r39 profiling 校准。[逐阶段模型](problem-model.md#会话闭环生成工作量与完工) · [既有方法级证据](bottleneck-verification.md#归因对照-r39)

两台主机读回 Ascend 驱动 `26.1.1`。D 当前统计库指纹与 r28 的快速读取白名单不同。四臂均使用驱动 `hccn_tool -stat -g` 读取同一组 MAC 计数，并记录查询中点，按真实采样区间对齐。采样用于判定持续链路压力，逐个微突发与方法时延仍用专门的探针测量。

## 正反序逐请求归因

正序升档后，总输出少 58,765 token，完工早 212.36 秒。两轮仅 66 条请求实际 P/D 去向同时一致，30 条输出长度一致。用每条请求的原先后依赖重放，逐个替换观测阶段时，首 token 后驻留解释 220.69 秒的提前，其他阶段合计抵消 8.33 秒。再将首 token 后时间拆为实际输出量和每 token 的有效驻留，输出量项提前 259.99 秒，每 token 驻留项抵消 39.30 秒。阶段替换保留两轮的观测时间与输出，给出完工差的描述性拆分。

正序 100 档的末会话 `gpt2-codegolf` 从 10 秒释放根，到 633.86 秒结束。链上的 P HTTP 合计 79.02 秒，D 从发出到首 token 3.03 秒，首 token 后 541.61 秒。最后一步 `gpt2-codegolf:31` 的 P HTTP 仅 2.02 秒，D 首 token 后为 352.11 秒，实际生成 24,098 token。200 档同一请求生成 1,580 token，首 token 后 31.31 秒，由另一条会话 `crack-7z-hash` 的第 36 步压尾。100 档在全局最后 P 回复后 186.37 秒才结束，200 档这一间隔为 31.26 秒。

反序的 200 档实际多生成 28,548 token，整轮晚 45.69 秒完成。阶段重放拆成 P HTTP 提前 17.65 秒，其他首 token 前阶段抵消约 1.21 秒，首 token 后驻留多 62.14 秒。两档都由 `gpt2-codegolf:31` 压尾，两次末步都生成 24,098 token。它在 200 档第一个 token 晚 52.48 秒出现，随后生成快约 6.79 秒。升档的总吞吐差来自整轮分子相对增长更快。两轮配对时有 68 条请求实际 P/D 去向同时一致，23 条输出长度一致。

## 恢复负载和模型复核

正序 100 档在投放窗内实际发出 27 条冷根和 60 条后继，P 回复 74 条。相比 r28 正序 100 档，本轮 P 实算由 288.04 万增到 624.24 万 token，外部恢复由 232.45 万变为 233.78 万 token。增加的工作主要是冷 prefill。

按每 1,024 token、每 rank 10 MiB 的 Attention 组以及固定 Hybrid 状态字节计，两次 100 档在投放窗与 P HTTP 相交的 103/112 条请求，就算每条各完整恢复一次且把全部传输放进窗口，也只有约 279/304 GB，折合 33.1/36.0 Gbps。真实换 P 且源轨迹共有前缀至少 128 Ki token 的后继各只有 4 条。这个上界描述原生单次恢复工作量，协议附加流量与其他通道另计。按 128 Ki token 约 5.37 GB 的远端恢复量估算，100 Gbps 需要约 2.33 次此量级的实际恢复每秒。[Attention 页组与状态](ascend-hybrid-prefix-restore.md#单独核对跨机字节与整轮完工) · [工作量模型](problem-model.md#瓶颈归因与模型校验)

同源候选清单有 88 个独立任务。留出 8,192 个生成 token 后，未截断且与前驱共有前缀达 128 Ki token 的 238 个后继集中在 7 个任务。同会话的后继串行释放，源前缀长度只给出潜在读取量。目标场景需要核对真正换 P 或本地驱逐后的外部命中密度。

在冻结实测路由、释放关系、输出量及其他阶段的条件回放中，扣除 P HTTP 与采样单口热窗的全部重合，两次 100 档的终点均未改变。把整个 P HTTP 缩短 10% 时，吞吐分别从 404.20/375.51 变为 409.30/379.99 token/s。把首 token 后驻留缩短 10% 时则变为 441.97/410.84 token/s。这些数值量化两个阶段对终点的条件敏感性。逐次同步 GET 的提交以及实际设备传输时长需要方法级探针，本轮计时没有启用这类探针。

## 同档波动和此前优化

两次 200 Gbps 都使用同一部署和同一到达。输出为 197,442→238,084 token，完工时间为 421.50→603.70 秒，含排空吞吐为 **468.43→394.37 token/s（−15.81%）**。第二次 200 档的 `gpt2-codegolf:31` 也生成 24,098 token，首 token 后为 349.94 秒，重新成为整轮末请求。按阶段重放，同档 182.20 秒时差中，首 token 后驻留增加 207.20 秒，首 token 前合计抵消约 25.00 秒。

从 r40 和 r41 清洗 trace 复算，SJF 对应同档原生的整轮吞吐在 100 Gbps 提高 10.88%/3.78%，在 200 Gbps 提高 20.40%/18.80%。两档的首块时间和端口计数支持将定量结果用于冷首轮队列分析。整轮差额还包含输出量和生成尾会话变化。r39 固定逐请求输出和实际去向的归因轮中，同字节 GET 在 200 档缩短约 62–66 ms，整轮仅 **+0.91%/−1.21%**。同头去重的真实减量和 r19 选定高读后继的小波次收益仍可复算。吞吐主张需要在实际同步恢复决定 D 进度的自然负载内单独检验。[r40/r41 时间线](r40-prefill-order.md#吞吐变化的阶段归因) · [r39 方法级归因](bottleneck-verification.md#归因对照-r39) · [r19 实测](results.md#r19-apc-开启的高远端恢复-ab)
