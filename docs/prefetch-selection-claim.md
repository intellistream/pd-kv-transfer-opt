# 跨批恢复的证据与候选贡献

扩展重放已复现多笔可早发的批次，关键路径选择和最长可行读在原时长、后继 worker 进入前的所有样本上等价。选读策略暂停验证。下列内容保留为单笔流水的展示和选读假设的实验记录。[扩展重放](critical-path-attribution.md#多恢复批选读的扩展重放)

## 幻灯片 1 · 端口还有余量，后继批仍可能等 KV

在两机 16 卡 910B2 的 2P2D 上，r21 的同步臂测到约 0.47 s 的 D→P 空档。把一笔 1.407 GB 的恢复提前到前一批前向，100 Gbps 下实测设备前向窗重叠 140.1 ms，后继批派发到结果缩短 188.1 ms，TTFT p99 降低 3.44%。前批设备前向多用 5.4 ms，前批派发到结果多用 35.4 ms。排空请求仍在前批，首 token 后约 17 s 的输出决定整轮排空，吞吐基本持平。[r21 分阶段实测](results.md#r21-固定字节的跨批提前读)

## 幻灯片 2 · 存在可隐藏的等待，也需要有两个可行选择

r20 四个同步臂共 **44 个 P 批，其中 7 个有多笔恢复**。把任意一笔视为已经提前完成，同时保留原消费和发布顺序、同头汇合与 8.56 ms staging 散写，得到其对后继最晚 host forward 的理想贡献。四个 P0 四恢复批中，`winning-avg-corewars:131` 的贡献最大，`regex-chess:106` 第二。前者最大约 **1.12 GB/rank**，后者约 **1.03 GB/rank**，均超出 r21 的 **384 MiB/rank** staging。两者的读服务也比该批可用的前批窗口长。[逐批逐笔重放](../results/2026-11-19-r20-packed-overlap/cross-batch-choice-audit.json)

| 同步 r20 样本 | 多恢复批 | 在下批 worker 进入前有两个候选 | 扩至后继首笔原始 GET 前 |
|---|---:|---:|---|
| 100 Gbps | 4 | 0 | 仍无双候选 |
| 200 Gbps | 3 | 0 | 1 批。按原序选 `train-fasttext:69` 推进 63.28 ms，选 `count-dataset-tokens:45` 推进 75.86 ms，额外 12.58 ms |

表中使用现有缓冲和原观测 GET 时长。扩展的窗口来自后继输入准备阶段。按关键路径选择与「选最长的可行 GET」一致，所有重放设置下额外收益均为零。把 GET 时长乐观缩短 25% 后，200 Gbps 的同一批在下批 worker 进入前也能形成双候选，差值仍是 12.58 ms。r20 约 0.46–0.47 s 的稳定长空档对应四个**单恢复**批，能支持单笔流水动机。精确的端口剩余容量和页租约应从新实测采集。[参数敏感性](../results/2026-11-19-r20-packed-overlap/cross-batch-choice-audit.json)

## 幻灯片 3 · 候选方法按消费批的收益准入早发

> **在组批和发布次序固定时，把有限的端口额度和 staging 分给最能推进消费批的那笔 D→P 恢复。** GET 可在前批期间执行，状态按原恢复序位交付给后继。

从调度器已释放的批提取候选。先用源对象、缓冲生命周期、每口可用服务和剩余时间检查早发的可行性，再用各 rank 的实际分片、同头配对等待、原消费时点和 scatter 计算后继的完成门槛。对候选 $i$，比较同一批在同步路径和只提前 $i$ 的条件下的最晚就绪时点，预计增益为 $\widehat F_{\rm sync}-\widehat F_i$。对前批、共享端口和 D 输出各自设保护条件。提前准备、额度判断、搬运和按序发布服务于同一个可见时间目标。r21 在单恢复批验证了搬运，对多候选择读的边际收益仍需独立证据。[释放与发布模型](problem-model.md#跨批恢复的释放资源与发布)

## 直接相关工作和可证伪的差异

| 相关工作 | 已解决的问题 | 本场景需要的独立检验 |
|---|---|---|
| **AMPD** | 多轮 P/D 中将 D→P 历史 KV 读取与前一任务的计算重叠，并按时限重排 prefill。 | 跨批流水已有直接先例。固定组批时，这一读窗有时仅容纳一笔，核心是从可行候选中选择能推进消费批的恢复。实机用同一流水中的首次可发作为对照，AMPD 的完整路由和重排效果需单独移植评估。[AMPD §4.2、§6](https://arxiv.org/html/2602.14516v2#S6) |
| **Nuska** | 在 vLLM 中按下游计算依赖、批次可行性和有效期限调整 KV、collective、P→D 通信优先级。 | 它公开的低层仲裁从提交的通信工作开始。在 r21 的空档，后继 connector 尚无这笔 GET 可供传输层排序。将这笔读暴露给传输层可与 Nuska 相互配合。验证本方法需要在相同提交与缓冲预算下加入期限优先的代理对照。其原始评测将 D 输出限制为 1 token，长输出排空仍需本场景验证。[Nuska §4.4、§5–6](https://arxiv.org/html/2603.17456v2#S4.SS4) |
| **SGLang Direct Linker / Evolving Infra** | 前者已有入队预取、私有设备缓冲、全 TP 成功后发布及取消排空。后者在排队时从同伴 host tier 取回历史 KV 再流水恢复。 | staging、完成屏障和后台预取均有先例。r20 里可读的候选数受 NPU staging 和端口时间窗共同限制。固定消费批下测到的选择收益还需与同预算入队预取对齐。完整系统的端到端效果仍待本平台验证。[Direct Linker](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/storage/mooncake_store/README.md#direct-linker-prefetch) · [Evolving Infra §4.2](https://arxiv.org/html/2611.12304v1#S4.SS2) |
| **Cascade** | 按请求 SLO 剩余预算和路径有效带宽调度，决定恢复多少前缀、何时重算。 | 按 slack 恢复和基于带宽估算的准入已有先例。候选差异是对同一个已形成的 Hybrid 消费批，在固定的完整跨机载荷与发布顺序下衡量**哪一笔**提前后能移动 rank 汇合时点。[Cascade §IV-C](https://arxiv.org/html/2608.06557v1#S4) |

本机证据支持固定版同步打包路径的晚提交会暴露 D→P 等待。r20 证明了当前窗口与缓冲下选择空间有限，r18 则发现按批就绪择路仅比按通信完工多提前约 28.55 µs。以上结论来自本机路径和受控重放，表中论文系统在此部署的完整效果仍待匹配实机对照。[现有方法核对](related-work.md#跨批提前恢复与通信调度) · [r18](results.md#r18-原长会话打包分发-trace)

## 论文段落草案

> 在两机 910B2 的多轮 P/D 分离推理中，我们观测到同步历史 KV 恢复可以在 D→P 端口仍有余量时阻塞后继批。将一笔恢复的传输移到前批计算期，保持发布顺序，能够缩短消费批等待。多恢复批中，对消费批贡献最大的读还会受到临时空间和可用传输时窗的约束。由此提出一个可验证的问题：当至少两笔恢复都能提前提交时，基于消费批最晚就绪时点的准入，能否在相同字节、相同组批和相同额度下胜过先发和最长可行读，同时保护前批和 D 输出？

当前证据可支持论文中的问题发现、单笔流水在本平台的受控实证和选择空间的适用边界。选读的独立贡献需要原组批与顺序下重复胜过先发、最长和期限代理，并对前批和 D 输出的干扰计账。扩展重放未达到这个门槛。[七步法当前判断](research-seven-steps.md#4-what-is-the-key-idea)
