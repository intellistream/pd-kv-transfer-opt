# 直接缩短 D 侧串行生成的候选

本轮调度试验的正式基线采用 r28 的 100 Gbps 自然长会话。以下分析保留每条请求当轮真实输出、实际路由和会话前驱，只减少两个 D 最后请求独自生成的时长。模型重算下一轮释放和最后完工。[r28 自然基线](r28-natural-bandwidth-plan.md) · [逐请求与单步方法](critical-path-attribution.md#r37-原生尾请求的单步分解)

|---|---:|---:|---:|---:|---:|
| 正序中的 100 | 148,164 | 474.30 s | **312.38** | **328.06**（+5.02%） | **336.51**（+7.72%） |
| 反序中的 100 | 154,259 | 547.45 s | **281.78** | **306.00**（+8.60%） | **319.74**（+13.47%） |

吞吐单位为 token/s。两个自然轮最后一个 D 的独跑阶段分别有 **113.35 秒和 216.66 秒**。因此即使保持整个 P 和网络时序，缩短独跑也有可能传到整轮。用同一模型重算时，要在两轮都得到 10% 总吞吐，独跑分别要少约 38% 和 23%。这是针对原始输出量的敏感性。[模型输入和结果](../results/2026-11-20-decode-execution-screen/summary.json)

r40 的 A1 和 A2 都在一个短的最后请求上结束。只缩短末请求独跑 20% 时，两轮模型增幅为 **0.08% 和 0.58%**。以同 D 的代理入口、客户端首 token 与结束，加引擎运行数、等待数和累计输出核对可定位的所有单请求生成窗口。在这些窗口按 20% 缩短驻留，固定其余阶段，两轮模型吞吐分别是 **390.83→405.48（+3.75%）** 和 **406.98→427.64（+5.08%）**。D 上的可用机会可能出现在会话中段，只有实际最后一个请求长时，末请求独跑才近似整轮的主要优化空间。[r40 自然对照](r40-prefill-order.md#含排空实测) · [两轮条件回放](../results/2026-11-20-decode-execution-screen/summary.json)

## 优先核查 Qwen 原生 MTP

MTP 在 D 用模型自带草稿头预测后续 token，让一次主模型验证接受多个 token。对低并发的长输出，减少的是每个有效输出 token 所需的串行主模型步数，覆盖该步里的算子、机内 collective 和运行时工作。主模型仍负责验证。两机装载的 Qwen3.5-35B-A3B 配置声明一层 MTP，D 权重索引含 MTP 权重。固定版 vLLM-Ascend 已有 MTP 实现，且其说明要求 Qwen3.5 的 P 和 D 使用相同预测长度。当前组合的 Hybrid 缓存、Mooncake 交接和图执行仍需在一个短诊断上确认。[固定版 MTP 支持说明](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/docs/source/user_guide/feature_guide/speculative_decoding.md) · [本模型配置](../configs/qwen35-config.json)

取一个草稿 token，令其被接受的概率为 $p$，包含草稿、目标前向、验收、Hybrid 状态更新和回执的平均周期为 $c$。在连续单请求且输出较长时，每个有效 token 的时间约为 $c/(1+p)$。用 r34 的 **13.591 ms** 步间隔作为观测标尺。若实测周期为 16 ms，至少约 18% 接受才能持平，约 47% 才能缩短 20%。若周期为 18 ms，相应为约 32% 和 66%。周期数字是为量化门槛选定的情景。

最小诊断用同一自然长上下文尾请求，比较原生单步和 1 草稿。核对 NPU 图、合法 token 序列、实际接受数、提交状态、端口与两侧 Hybrid 缓存。分别量宽度 1 及仍有多条请求的批宽，记录每个有效 token 的墙钟、草稿和验证时间、拒绝后的状态处理。只有在长尾单请求和有代表性的并批下知道净服务成本，才用 r28 口径做两侧同启的正式整轮配对。现成 MTP 开关可作工程对照。最新实现已公开随并发调整预测长度的思路，提出新方案时需以固定及动态原生 MTP 为对照。[上游机制](https://docs.vllm.ai/projects/ascend/en/latest/user_guide/feature_guide/speculative_decoding.html)

## 其他可比的引擎路径

r37 的 13.59 ms 周期估计中，设备算子和访存约 8.72–9.01 ms，四 rank 到齐后的机内 collective 约 1.9 ms。按覆盖到的 D0 尾步缩短 20% 算子时间，r34 的条件总吞吐为 **345.14→355.65 token/s（+3.04%）**。缩短 20% 的实际 collective 完成段为 **345.14→347.37（+0.64%）**。具体融合候选应由独跑热点的可合并数据依赖和最晚 rank 的时间验证。P 侧拿后续轮的预执行节拍代回首 16 批，原先的整轮条件收益约 1%。这些数字决定了先减少串行验证次数，再比较每步局部开销的优先级。[r37 方法级拆分](results.md#r37-100-gbps-原生-decode-尾部单步归因) · [P 首批回放](cross-run-throughput.md#p1-首请求的运行时节拍)
