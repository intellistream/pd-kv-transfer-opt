# CPU 模拟器

仓库包含可独立运行的模拟组件，模型工作由真实的阶段锚点和可重放的因果关系驱动。

| 模块 | 当前能力 |
|---|---|
| [network_sim.py](../pd_kv_transfer_opt/simulator/network_sim.py) | 离散事件、动态多资源公平共享、方向独立或显式端点共享、FIFO 并发限制与字节守恒 |
| [lifecycle.py](../pd_kv_transfer_opt/simulator/lifecycle.py) | 物理池分配、在途容量占用、源 pin、完整 hybrid bundle 的可见性与 lease 释放 |
| [geometry.py](../pd_kv_transfer_opt/simulator/geometry.py) | 从 Qwen 配置推导 attention 与 recurrent 状态的逻辑尺寸和聚合存储量 |
| [trace_replay.py](../pd_kv_transfer_opt/simulator/trace_replay.py) | 继承的四 FIFO 条件回放，按前驱的完整结束时刻释放会话后继 |
| [decode_supply.py](../pd_kv_transfer_opt/simulator/decode_supply.py) | 用真实到达 D 的时间、两 D 各 16 槽和原生成量重放解码并发与后继释放，可替换每条 P HTTP 驻留 |
| [rdma_replay.py](../pd_kv_transfer_opt/simulator/rdma_replay.py) | 用单个 200 Gbps 参考臂重放八口限速、P 恢复交付与 D 生成，保留另一档作留出，并扫描高压窗口长度 |
| [terminal_pressure.py](../pd_kv_transfer_opt/simulator/terminal_pressure.py) | 从原生正式归档筛选两次参考轮均有回读压力的长会话，用原始请求和字节做双档配对，并核对独立 GET 事件 |
| [rdma_audit.py](../pd_kv_transfer_opt/simulator/rdma_audit.py) | 对齐同批 GET 与 P 调度事件，检查真实供给，按两档的实际工作分别校验 P 交付对整轮的影响 |
| [terminal_magnitude.py](../pd_kv_transfer_opt/simulator/terminal_magnitude.py) | 在真实字节留出轨迹和互不重复的原始会话组合中检查达到 r28 吞吐差距需要的条件 |
| [terminal_supply.py](../pd_kv_transfer_opt/simulator/terminal_supply.py) | 选择原始短尾会话，按原生分数、逐批回读和 D 可运行队列重放同负载两档，并测试前驱和入序扰动 |
| [terminal_prefill_calibration.py](../pd_kv_transfer_opt/simulator/terminal_prefill_calibration.py) | 按实际首批和逐口服务时序校准 P，归因交付时间与顺序，用两组拟合复筛冻结负载 |
| [terminal_residency.py](../pd_kv_transfer_opt/simulator/terminal_residency.py) | 复核目标 P 的早期前缀驻留，从原始会话换选窗口，重放与验证冻结 100/200 Gbps 对照 |

从 [传输示例](../configs/transport-demo.json) 运行 `python -m pd_kv_transfer_opt.simulator.network_sim --input configs/transport-demo.json --output runs/transport-demo.json`。示例使用人工容量和到达。旧四 FIFO 入口读取 measurements、protocol 和 cost-model，工作负载、已接纳缓存和路径固定，用于重构时序与灵敏度检查。CPU 用例给出最小调用示例。

## 当前执行目标

主实验转为 r43 原生 200 Gbps 的 Terminal-Bench 长会话，先用 CPU 和归档拆出整轮的 D 生成依赖、P 冷算和交接。旧双档回放保留同一参考臂的输入、依赖、路由、缓存观测和自然输出量，用于核对网络压力传导。主指标仍从首计划投放算到最后完成。 [主实验与最后一轮 RDMA 计划](terminal-throughput-plan.md)

此前用于回读压力研究的 68 窗，筛查了集中就绪的自然回读和较短的生成尾部。 [冻结投放与复算](#按本地-apc-覆盖复筛自然窗口)

### 单参考臂的带宽重放

D 的批内服务用 r73/r75 的 439 个区间拟合。预测只读取对应的 200 Gbps 臂，对齐 D 八口 MAC 字节、P 请求区间和 D 供给。模型按最热端口的服务成本延长 P HTTP，并依 D 生成重新判定每个后继的实际就绪时间。每个模拟区间核对逐口字节守恒和限额。100 Gbps 的实测在完成预测后用于核对。r64/r69 独立 profiling 的 21 个四 rank 匹配 GET 批全部在低档较慢。将高档 GET 时间按速率反比估计低档，两个方法轮的平均绝对误差分别为 0.253 和 0.180 秒。200 档最热口超过 12.5 Gbps 的窗口中，约 85% 和 73% 与同步 GET 重合。 [留出结果和批次证据](../results/2026-11-22-cpu-native-rdma-replay/summary.json)

### 原始长会话的回读压力对照

按固定部署与 Terminal-Bench 版本筛过 19 个完整正式归档。负载排序只用两个 200 Gbps 参考臂，要求保留原会话前驱、两个参考臂均自然 EOS，取两次最密 20 秒出站平均速率中较小的一项。r69 在合格组中最高，两次为 **77.16、76.97 Gbps**。确认选中 10 个任务的 53 个原始相邻两轮窗口，共 106 条，输入长度中位 103,837 token。原始账本已核对全部行和 53 条前驱边。r67 的参考读量更高，两个参考臂有 2/3 条达到原预算并改变生成尾部。 [已保存的筛选规则和冻结输入](../results/2026-11-22-cpu-terminal-pressure/selected-workload.json) · [19 组筛选与结果](../results/2026-11-22-cpu-terminal-pressure/summary.json)

### 核对回读到完工的传导

从压缩轨迹重算 r69 四臂。双侧 APC 和 106 条自然 EOS 均保留，D 实测本地命中约 814–858 万 token。回放分别对账八口的实际字节，两档用同一组字节和对应的实际 EOS，压力窗口倍率为 1。使用原始方法事件重核了 13 个请求集合及四 rank 载荷均相同的 GET 批，共 **123.88 GB**。全部批的同步 GET 在 200 Gbps 更早完成，其中 11 个可唯一接到对应的 P 调度批。在最大的 19.36 GB 批中，派发到结果的时间减少 **1.020 秒**，其中最后完成 rank 的同步 GET 少 **1.012 秒**。 [原始事件和冻结条件复核](../results/2026-11-22-cpu-terminal-pressure/causal-audit.json)

分别保持 100 和 200 Gbps 观测的 D 去向、自然输出以及其他阶段，只替换 P HTTP 驻留。两种参考臂给出的正序完工差分别是 **4.71、8.76 秒**，反序是 **6.90、6.47 秒**。用 D 的批服务模型对 P HTTP、其他首 token 前驻留、D 去向和 EOS 工作量做全部组合替换，平均各替换顺序。正反序节省的 **6.70、6.71 秒**归在 P HTTP，D 去向对应 **−0.48、−0.09 秒**。历史实测在第 56–66 秒中，升档后两对分别多交付 8 和 10 条后继，多送出 8 条后继的首 token。100 Gbps 还有实际端口热点与 D 无待运行工作、P 交付在途重叠的观测，整轮完工同时受尾部影响。 [双参考回放和原始供给](../results/2026-11-22-cpu-terminal-pressure/causal-audit.json)

200 档中 `winning-avg-corewars:117` 因原前驱到第 74 秒左右才结束，接近或决定两次的最终完工。该会话必须计入原始排空。相同的吞吐分子、分母替换，将 r69 正序升档后的 **+19.89 token/s** 拆成 **−1.78** 来自输出、**+21.67** 来自完工提前。反序的 **+22.75 token/s** 对应 **+7.89、+14.85**。r28 正序为 **+91.34 token/s**，其中输出贡献 **+91.43**，时间贡献 **−0.09**。r28 反序提前 83.77 秒，阶段替换给首 token 后生成驻留 **81.74 秒**，P HTTP 约 **2.30 秒**。r28 的 D APC 关闭，数值按其原配置作历史比较。 [吞吐与末请求分解](../results/2026-11-22-cpu-terminal-pressure/causal-audit.json)

### 复查 r28 的差距量级

r28 正序的 100 Gbps 吞吐相对低 22.62%，总时长 **474.30→474.42 秒**，实际输出 **148,164→191,533 token**。反序低 20.58%，整轮提前 83.77 秒，其中阶段替换给首 token 后 81.74 秒、P HTTP 约 2.30 秒。两次 100 档聚合出站达到 85 Gbps 的时间均不足 0.5 秒。r28 的 D APC 关闭。四臂的计数和限速复核通过，生成工作量出现了明显漂移。下方的 20.58% 是早期负载灵敏度分析使用的历史幅度。当前带宽复现按可比的读量、自然输出、D 缺供和正反序总吞吐共同判定。 [历史结果和原始端口归因](cross-run-throughput.md#r28-的差距在同负载复测中怎样变化)

重新回放 17 个未用于拟合 D 步进的归档，共 34 对。每对使用实测原始逐口流量，倍率为 1。r78 正序的 90 条 P 去向一致，两档均为自然 EOS，实测 D 出站各约 201 GB。它给出满足这些可比条件的最大留出差距，短突发回放 **10.17%**，均匀发送回放 **8.39%**。r76 反序实测低 **17.90%**，实际读量约 **216.8→160.8 GB**，P 去向仅 84/100 条一致，固定高档原始工作后按短突发重放为 **8.31%**。 [完整留出结果](../results/2026-11-22-cpu-r28-magnitude/summary.json)

### r69 P1 第 228 批的五条请求与逐口争用

## 使用实测锚点

r14 的 [逐轮样本](../results/2026-11-18-r14/rounds.csv) 和 [逐阶段摘要](../results/2026-11-18-r14/summary.json) 可用于固定条件标定。四档每请求约 9.52 GB 远端有效载荷。D→P 的八口限速和 MAC 计数应单独输入，P→D 方向另记。当同步 GET 完成后，同一 worker 才能继续 forward。EngineCore 批队列满或没有可发批时等 worker 结果，会连带影响收件。将新 token 计算和本地前缀复用留为各自的成本与事件。

模拟器现阶段提供条件回放和分组件模型。完整问题的输入、可行动作、容量约束和 100 Gbps 含排空目标见数学定义。闭环服务预测需从初态产生实际后继到达、队列、组批、命中与 D 生成，接入调度、缓存和传输的状态转移，并用独立整轮验证。条件回放可以冻结这些量来分析同轮敏感性。真实排队、最终命中和未来完成时刻用于核对模型输出。图执行、TP/EP、模型与后端变化使用新的兼容域。[问题定义](problem-model.md#问题定义) · [已验证和待校准部分](problem-model.md#瓶颈归因与模型校验)

闭环扩展的事件依赖、缓存可见性与校准口径见 [问题模型](problem-model.md)，与 ServeTwin 等系统的对照见 [相关工作](optimization-research.md)。

r28 的条件重放从同机客户端和代理事件取五段驻留时间，以会话前驱传播真实释放并重算整轮完工。它可筛选 P 各阶段加速可能传到的尾部。D 准入、页释放和每步输出竞争由闭环模型继续加入，并以保留整轮作为预测检验。事后已知的 D 入队与生成量作为校验标签。[重算入口](../pd_kv_transfer_opt/profiling/profile_closed_sessions.py) · [会话闭环模型](problem-model.md#会话闭环生成工作量与完工)

r33 提供同一 100 Gbps 原生回放的七段 P HTTP、Store GET 内部成本、按批形及前缀分组的 rank 0 forward、D 页分配与就绪、客户端结束。批派发至结果含 worker 排队，独立 device 成本用于计算服务。后台 Store 写和 decode 交接使用独立的对象及发布状态。用独立变更 P 接纳、GET、forward、D 接收和首 token 后驻留的重放核对吞吐传导。[校准结果](../results/2026-11-20-r33-native-prefill-path/summary.json) · [重放入口](../pd_kv_transfer_opt/profiling/analyze_native_prefill_path.py)

r34 补齐同负载 D 的 2,788 个四 rank 步进样本。校准表按批宽和历史长度分组，同时记录图填充、相邻步间隔、设备 forward 和 host 阶段。模型保留同 D 实例内各 rank 到达及完成约束。CANN 短窗用于确认任务和依赖，服务速率用窗口外步频校验。闭环预测仍需按生成进度触发 EOS、更新批形并在独立轮中验证。[D 成本与 join](problem-model.md#d-步进和服务成本) · [步进摘要](../results/2026-11-20-r34-native-decode-path/summary.json)

用 r73/r75 的设备输出计数和同机流式生命周期得到 439 个 D 采样区间。每实例有效单步约为 $14.27+1.24\,(n-1)$ ms，$n$ 为正在生成的请求数。区间拟合中位误差约 0.67 ms。用留出的 r78 四个真实轮分别保留每条实际生成量、D 去向及到首 token 的上游驻留。重放的末请求与实测逐臂一致，含排空时长误差约 0.22–0.87 秒。保持 100 档实际输出和 D 去向，换成 200 档的逐条 P HTTP 后，正序模型吞吐从 322.72 到 355.79 token/s，整轮提前 6.98 秒。反序 P 观测量包含受到入序与缓存反馈影响的读取字节差，保留此约束。当前模型校验 D 对给定 P 交付的响应，待测新上下文需要另测 D 成本，P 队列与缓存变化需要运行时轨迹。 [校准和留出误差](../results/2026-11-22-r78-terminal-source-restore-stable-tail/decode-batch-replay.json)

冷首轮调度筛选将实测 P 批预算分给候选顺序，按 r34 的步频曲线重新生成 D 排队和会话释放。每轮仍使用各自记录的逐请求输出长度。原序和动作均运行于同一模型，记录原序与实测偏差。入口在冷首轮分析内。r28 使用自然基线数据做阶段敏感性，P 实际分块用 r33 和 r39 的归因数据验证。[运行方式和对照](cold-prefill-order.md#已执行的离线尝试)
