# r49–r50 NarrativeQA 共享前缀筛查

r48 把同源 Terminal-Bench 扩到 254 条后，100→200 Gbps 的含排空吞吐为 **456.74→427.91** 和 **437.71→389.22 token/s**。新增冷根加深 P 排队，已有会话的后继反而更晚就绪。r49 用独立的长文问答负载增加自然共享前缀和更短的回答机会，检验高强度下是否出现更大的实际跨机 KV 需求。 [r48 扩容归因](restore-workload-screen.md#r48-同源扩容实测)

## 压力判断

前一轮启动日志中 P0、P1、D0、D1 的名义 KV 容量均为 3,093,699 token。r49 的文档共同前缀为 3,125,248 token，按原生四 rank Attention 载荷折合约 119.22 GiB。若两个 P 在实际路由下经常各自接触完整文档集合，设备缓存会有逐出机会。Store 的实测可用余量、GDN 状态开销和实际命中决定缺失块是否转化为 D→P 读。D 本地未命中的部分还可能产生 P→D 交接。

若八口持续用完 100 Gbps，32 秒需要约 400 GB 单方向载荷，约为 56 次平均长度的完整文档传输等价量。按实际页和逐口流量判定，单口热点用该口上限和实测载荷。第 125–157 秒的预先定义窗口记录实发与 P 到 D 的供给、双侧实际复用和恢复、Store 驱逐及分配、带宽及流控。端到端保留最后一条生成和排空。原生日志用于交接时间，方法级 profiling 在有压力的独立臂上补采。

## 实际生成长度的检查

r49 在首个 100 Gbps 臂的 883.99 秒取到最后一个完整筛查快照。135/306 条完成，累计成功输出 505,411 token，输出中位数 2,409 token，38 条达到 8,192-token 预算。300 秒后 D0 和 D1 分别在 132/133 和 133/133 个采样点用满 16 个槽。125–300 秒 P/D 平均出站为 12.19/8.44 Gbps。共享 Store 在 123.89 秒已累计逐出 40.03 GB，停止前的快照达到 638.71 GB。实际生成与缓存逐出同时限制可用 KV 交付率。随后结束此筛查并安全恢复双方八口。该轮只形成负载筛查快照。 [筛查快照和端口回执](../results/2026-11-21-r49-document-qualification/summary.json)

r50 用 Qwen3.5 官方直答模板尝试减少生成占槽。原 306 个问题、18 篇长文、到达和 8,192-token 预算经逐条校验，直答模板增加两个提示 token，保留 EOS。用户确认主实验继续使用原 Terminal-Bench 后，首个 100 Gbps 臂已中止。两侧限速均读回恢复，16 张卡已释放。r50 无完整计时臂。 [模型卡的直答设置](https://huggingface.co/Qwen/Qwen3.5-35B-A3B#instruct-or-non-thinking-mode)
