2026-11-19。核对了工作负载清单、两侧启动参数、代理入口、原生传输事件、客户端生成统计和整轮吞吐计算。现有结果覆盖硬限速、缓存复用、固定工作量的自然会话窗口和优化机制对照。r28 已完成保留自然命中、EOS 和原生路由的原长会话正反序对照，覆盖短时集中启动及后继请求。[实验结果](results.md) · [实测配置与命中明细](../results/2026-11-19-r27c-native-sustained/manifest.json)

## 工作负载与缓存

| 复查项 | 观察到的设置和影响 | 部署验收口径 |
|---|---|---|
| P 是否能复用前缀 | r13/r14 只投放已入 D Store 的两个长前缀并关 APC。r26 开 P APC，专门选了 22 条跨 P 高恢复后继，正式本地命中为零。r27c 两侧关闭 APC，将同一组重复 12 遍。后 11 遍贡献约 91.9% 的 GET 字节。 | 开 P APC，用原数据集增加不同会话。记录 P 本地命中、Store 命中、需要计算的 token 和实际传输字节。缓存暖态由之前的实际请求产生。 |
| 前驱和缓存预热 | r19/r25/r26/r27c 先准备指定前驱，等其排空和 Store 提交，再计时目标请求。换 P 命中热 Store 的机会由筛选确定。 | 正式会话内的前驱也计入整轮，自然经历冷算、写池、复用和淘汰。服务通常预热的部分可用同一历史窗口建立并注明。 |
| 输出长度与停止 | r13/r14 每请求固定 16 token。r10 有 125/170 条的预算为 1,024，39 条以 `length` 停止，实际输出长度达到 1,024 的有 31 条。r11/r12 冻结 r10 的实测长度。r25–r27c 用 DeepSeek 源轨迹的计数作为 Qwen 长度并设置 `ignore_eos`。 | 使用实际 `max_tokens` 和停止策略，核对输出分布及 `stop`、`length` 的占比。固定长度用于同工作量的因果对照。 |
| 到达、历史与工具间隔 | r10 的 30 个窗口从长上下文轮次起步，后续输入使用源轨迹中记录的历史。会话起点由实验生成，工具间隔为零。r26 的 8 请求/s 只投放 2.55 秒，各臂提交偏差 p95 约 22–217 ms。r27c 投放 32.80 秒后仍有约 777 秒排空，18–32 秒是积压仍增长时的输出平台。 | 增加独立会话来延长压力，记录实际会话起点和工具间隔的来源。后继由前驱真实完成触发。固定会话起点和外部等待，观察实际请求到达、客户端排队及进服速率。 |
| 固定路由与 D 输出失衡 | 机制对照预先冻结实例。r27c 两个 D 各接 132 条，D1 却承担 58.77% 的输出 token 并决定排空。 | 使用目标部署的路由和亲和策略，按实例记录命中、实际流量与输出 token。固定实例映射仍可用于等字节的诊断。 |

r11 的原生 APC-on 回放中，实际 D→P 恢复为 48/170 条。按 P 输入 token 统计，本地 APC 约 65.5%，外部传输约 11.3%，本地计算约 23.2%。这些占比使用原实机归档 `natural-best-rdma-20261118/comparison.json` 的 `A.P_prompt_token_sources` 重算。r10 的结束原因来自同一归档的 `r10-analysis.json`。两组的输出上限、窗口选择和人工到达仍需随结果一起注明。[原工作负载和回放条件](workloads.md#自然长会话) · [实测竞争对照](../results/2026-11-18-supporting/natural-rdma-competition.json)

## 启动、代理和计量

| 复查项 | 检查与修正 |
|---|---|
| 并行、图策略与 KV 预算 | 当前是双机 2P2D，每实例四卡，Attention TP4 并启用专家并行，DP1。r26/r27c 启动记录采用图模式。r27c 的 929 个 P 图观测事件均记录 `PIECEWISE` replay，D 配置为 `FULL_DECODE_ONLY`。两侧的 16 序列、4,096 分块预算、0.8 显存利用率、128 token 块、262,144 最大上下文与 P 4096 图捕获尺寸是实机参数。序列数、批预算、显存预留与图配置已移到可按角色覆盖的设置。D1 满 16 槽及排空归因随该配置解释。 |
| Store 与传输路径 | 原生堆栈同时配置 P→D 的 `MooncakeConnectorV1` 和共享前缀池 `AscendStoreConnector`。当前 P 挂载 0、D 每 rank 挂载 16 GiB，D 写回 Store，恢复为同步，取回失败策略为 `fail`。r27c 的有限热集在两档均无驱逐。池位置、容量、租户和淘汰策略均影响读取比例。按目标部署匹配这些设置，记录 D 侧 APC 状态、池占用和实际交接。 |
| 同机 lookup IPC | 固定版本的 lookup 路径由 `VLLM_RPC_BASE_PATH`、`lookup_rpc_port` 和 DP rank 组成。旧脚本对同主机的两个 DP1 实例都传 `0`，未为子进程单设 IPC 根目录。通用启动器现按各实例 API 端口生成不同的本地 lookup 标识。历史归档没有 socket 对端记录，保留端点重合风险，尚不能量化对历史结果的影响。 |
| API 与代理 | 通用入口曾默认选 r14 固定路由并关闭代理至引擎的连接复用。r27c 的站点代理确实使用固定路由，启动事件显示上游连接复用保持开启。通用入口现默认使用上游调度及连接复用。历史压测路由和关闭复用都需显式选择。计时还应记录 API 形态、输入预分词、客户端并发、代理进程数及重试策略。本回放使用 token ID 输入和确定性采样，服务端分词和真实工具调度的开销另有口径。 |
| 端口限速和共享资源 | 100/200 Gbps 是实验室 D 节点八个 NPU 口的聚合出站上限，分别读回每口 12.5/25 Gbps。r11/r12 的后台 READ 还会竞争端点资源。现场应核对方向、单口或聚合、实际瓶颈链路、两种 KV 流量是否共链路，再用收发字节与成功率解释限速效应。 |
| profiling 对运行的影响 | r26/r27c 正式轮未开 CANN profiler，仍包装了方法、写阶段日志并记录 NPU 时间事件。通用 `serve` 将详细观察改为显式 `--observe`。正式计时和同配置归因轮分别记录实际观察模式。 |
| 整轮输出吞吐 | 用所有正式请求的成功输出 token 数，除以首条计划投放至最终完成的时长。通用分析器提供 `finite_cohort.output_tokens_per_s`，缺记录、失败或 token 计数错误时该值为空。固定窗口的输出速率和已完成请求速率用于定位启动、平台与排空。 |

启动参数以 `state.json`、引擎实际配置及 trace 为准。r26/r27c 固定 vLLM `0fc695f`、vLLM-Ascend `5cb98ca` 与 Mooncake NPU wheel `0.3.11.post1`。官方文档用于核对参数语义。`enforce_eager` 的通用默认是 `False`，Ascend Store 的 `lookup_rpc_port` 区分共用 IPC 目录的独立实例。[部署入口](deployment.md#运行域) · [vLLM 引擎参数](https://docs.vllm.ai/en/latest/configuration/engine_args/) · [Ascend Store 参数](https://docs.vllm.ai/projects/ascend/en/main/user_guide/feature_guide/kv_cache_pool_ascend_store.html)

## 当前结论的适用范围

- r13/r14 的 100→200 Gbps 近倍增是热前缀、短输出诊断的带宽因果证据。r19 的 5.71%/3.65% 是选中的高恢复波次上的原生与打包配对。[r14](results.md#r14-远端恢复限速) · [r19](results.md#r19-apc-开启的高远端恢复-ab)
- r26 的整轮变化约 +2.06%/+2.22%，r27c 约 +0.17%。这两组的计时请求均进入 D→P 恢复路径，可归因到长输出和 D 排空的影响。[r26/r27c](results.md#r27c-原生持续高压的输出平台)
- r28 原自然长会话的两次 100 Gbps 整轮输出吞吐均低约两成。端口只短暂接近上限，实际输出量和末请求生成时间解释了差值。D→P 带宽限制向整轮吞吐的传导在本次采样中缺少证据。[r28 分析](results.md#r28-原生长会话的-100200-gbps-正反序对照)
- r40/r41 的相同 30 个长会话都在 4.56 秒内集中启动，后续是前驱释放的闭环回放。两档分别启动，对应原生位置观察到 **390.83→382.37** 和 **406.98→355.69 token/s**。A1 的 200 档更早结束但实际输出更少，A2 的差主要在末会话的生成。四个原生臂都缺少 100 档持续 RDMA 压力证据。该对照用于冷首轮调度和生成尾部分析。持续高压验收单独核对实际到达时段、各口及关键 GET、D 可运行供给和整轮吞吐。 [输入、八口读回和原生完工链](r40-prefill-order.md#原生跨档与负载复查)
- r42 保留 r28 的实际部署命令和 170 条原输入，扩至 48 个独立会话，根持续投放 92.5 秒。同一部署的正反序原生吞吐均是 200 档较高。逐口没有持续受限，增加的工作主要是 P 冷算。回放只控制外部起点，实际后继释放密度、命中构成和生成量须从本轮事件读出。[部署和负载复验](r42-natural-sustained.md)
- r43 沿用 r42 到达，D 增加 APC 与上游重算调度器。独立冷暖探针对两个 D 都观察到 35,840 个实际命中 token，完整输出的贪心序列在分数接近时会分叉。实际出入站字节和 D 本地缓存统计各有计量口径，报告带宽效应时同时复核实际生成量、路由、配对终点和同档波动。[r43 的协议和正反序](r43-native-decode-apc.md)
- r44 将同一批 48 条会话链在两个独立租户命名域相差 1.25 秒回放。两臂核对同一份合成投放表、原始输入和前驱指纹、实际输出和 EOS、空 Store、原生路由及八口读回。组间比较的是该双租户回放上的出口限速。r43 到 r44 的对照同时包含到达和缓存工作集规模变化。放量后两档均实录 Store 空间不足、P 实算上升和回读下降。[r44 复查和原因](r44-native-intensity.md)
- 目标现场的路由、P/D APC、池和链路拓扑、D 并发与显存预算、采样/停止规则、会话到达和工具间隔尚未有完整记录。当前模板保留已知的实验室值，完整的现场收益仍由自然命中高压回放的整轮输出吞吐确定。[验收状态](research-seven-steps.md#主负载的吞吐验收状态)
