# 2P2D 中的远端 KV 恢复与批队列模型

2026-11-18。建模对象是 r14 的两台 8 卡 910B2、Qwen3.5-35B-A3B BF16，以及官方 vLLM-Ascend 与 Mooncake 组合。每个角色有两个独立实例，每实例 attention TP4 / expert EP4。P 经 HIXL 从 D 侧 Mooncake Store 同步读到 P NPU，P→D 随后有独立的推理解码交接。本章用于按因果链归因，并比较传输实现与调度联合改动。可复算基线见 [r14 结果与运行域](results.md) · [工作负载](workloads.md)。

## Tailguard 模型迁移

《2026-11-12-Tailguard》第 2 页式（1）以因果策略 $\pi$ 最小化固定集合的 TTFT p99，并约束节点 CPU 池占用与两个方向的活跃流速率。式（2）让放置 $g$ 和远端取回选择 $z$ 决定可用前缀 $H$ 和跨机字节 $S$。式（3）用 $T^{\rm start}+S/b$ 估计 fetch，用等待的 step 时长之和估计排队，再计本地 Load 和计算。第 3 页的 4 卡 TP1、Qwen2.5-14B 和 D 本地 DMA 归因来自较早环境。第 4 页的模拟验证使用 4 卡 TP1、Qwen2.5-7B 和 95 个请求。

| PPT 要素 | 当前模型的处理 |
|---|---|
| 因果策略、可用前缀、物理容量 | 保留决策与状态反馈。前缀完整性扩至 TP rank、attention KV 和对齐的 SSM/conv checkpoint |
| CPU 池、统一的远端 fetch 加 Load | r14 的 D0/D1 各有四条 16 GiB Store 段的原生注册记录，均为 host。P 的恢复目的在 NPU。staging 和本机复制经独立观测后作为单独节点 |
| $S/b$ 和两个方向的总带宽 | 保留作为固定速率特例。用实际描述符字节、端口及端点资源约束、动态剩余字节表示并发传输 |
| 按请求累加等待 step | 用真实 engine 取件、batch 顺序、rank 本地读取、collective 依赖与结果返回表达。单个慢读会影响同批以及后续入队 |

## 请求时钟与可归因边界

记 $a_i$ 为请求就绪，$p_i$ 为代理开始 P 请求，$e_i$ 为 P scheduler 接收，$s_i$ 为首次批次派发，$f_i$ 为 P 最终批次结果，$o_i$ 为代理收到 P 响应，$d_i$ 为 D 请求发出，$y_i$ 为客户端收到首内容 token。多轮会话的 $a_i$ 受前序完整结束约束。用于同一协议的计时恒等式为

$$
T_i^{\mathrm{TTFT}}=y_i-a_i=
(p_i-a_i)+(e_i-p_i)+(s_i-e_i)+(f_i-s_i)+(o_i-f_i)+(d_i-o_i)+(y_i-d_i).
$$

$e_i-p_i$ 是代理起始到调度器收到的区间，含 HTTP、入站处理与 EngineCore 取输入的等待。$s_i-e_i$ 才是调度器接收后到首次派发。$f_i-s_i$ 包含 worker 等待、GET、设备执行和返回。GET、HIXL 与 CANN 区间是其内部观测，分析时取受控对照或同一时间轴的交集。设备 memcpy、HIXL API 和硬件收发统计存在包含或重叠，逐项求和会重复计时。跨主机边界需要记录时钟误差。见 [阶段与抓栈](../results/2026-11-18-r14/summary.json)。

100→200 Gbps 的平均 TTFT 缩短 26.87 秒。其中接收前缩短约 5.78 秒，调度排队缩短 12.68 秒，派发至 P 结果缩短 8.05 秒。前序 GET 与接收前区间的重合量差约 5.61 秒。它支持已有请求拖住后续摄入，具体 HTTP 与 IPC 等待之间仍需进一步埋点。低到达率时 GET 延迟随限速变化，P 排队 p50 约 31 ms。采用同一个状态转移模型可以解释高载放大和低载近似按到达完成两种结果。

## KV 对象、物理字节与可见性

对象索引包含缓存内容键、状态组、块或 checkpoint、模型及布局版本、必要的 head 或 rank 身份和内容代次。令 $\mathcal K_i(H,r)$ 为请求 $i$ 在 rank $r$ 运行到前缀长度 $H$ 所需的对象集合。$H_i$ 是选定恢复或重算计划下，所有相关 rank 可见的最长一致前缀。越过对齐边界时，attention hit 与 SSM/conv checkpoint 需同时满足。新计算 token 数 $W_i=L_i-H_i$，结合历史长度、批形状、图执行及并行运行域估计设备服务。P→D 在其自己的 state bundle 和资源路径上建立交接，D 持续 decode 占用资源至释放。

令 $\mathcal F_{i,\to}$ 是为 $i$ 的恢复实际发出的跨机传输集合，$S_f$ 是一次传输的描述符载荷，单位为字节。对于 r14 成功读取，按各 rank 完成的描述符合计。去重后对共享的跨机读记一次传输，本机复制另计。

$$
W_{i,\to}^{\rm payload}=\sum_{f\in\mathcal F_{i,\to}} S_f,\qquad
\sum_{o,r} m_{or}\,x_{or,a}(t)+\operatorname{reserved}_a(t)+\operatorname{staging}_a(t)\le M_a(t).
$$

MAC 端口字节单独观测。占用以唯一物理分配计，预留和 staging 只扣尚未记入实体分配的部分。D 段、P 目的 HBM 以及临时缓冲分别有容量约束。提交读取前源需 pin，目的需已合法分配。完整可见时再发布。取消、失败和 fallback 要等在途访问安全终止后再释放 pin 与内存，并记录重试载荷和重算成本。

当前 TP4、两个 KV head 提供同 head 的候选等价类。仅当共享版本、head 内容、布局、KV 块位置、分发目的和完成顺序校验通过，才可按等价类选读者并在本机补齐各 rank 副本。SSM/conv 继续按 rank 处理。跨请求在途合并是另一个开关，需要独立验证并计每个等待者的可见时间。见 [固定版本 Ascend Store worker](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py)。

## 传输服务与 batch 的因果约束

物理流 $f$ 有数据量 $S_f$、有向资源路径 $\mathcal P_f$ 和实际启动 $\tau_f$。读取首先经过提交及端点准入。对每个在途流，剩余量 $R_f(t)$ 与有效速率 $v_f(t)$ 满足

$$
R_f(\tau_f)=S_f,\qquad
R_f(t)=\max\left(0,S_f-\int_{\tau_f}^t v_f(u)\,du\right),\qquad
\sum_{f:\,a\in\mathcal P_f}v_f(t)\le C_a(t).
$$

$a$ 可以是 D 发端、P 收端、两端提交资源、集线通路或本机复制路径。当前硬限速使 D 发端的 $C_a$ 具有可读回上界。测得的端口 TX、载荷 goodput 和单调用有效速率用于检验服务分配。方向独立时并行，已证实共享的端点资源再作耦合。可先用分段流体共享近似，在留出集对比 per-port 字节与完成事件。$R_f=0$ 后仍可有 completion 通知或设备可见性延迟。实际在同一个 HIXL/设备计时里的端点时间无需另加一个估算值。

基线 P worker 的同步 load 对同一 batch、同一 rank 的 GET 按观察次序完成。若 $G_{b,r,1},\ldots,G_{b,r,n}$ 为该序列，$v_{b,r,k}$ 是第 $k$ 项 GET 及其依赖状态在 rank 本地的可见时间，$u_{b,r}$ 是本次 host forward 进入，则 $u_{b,r}\ge\max_k v_{b,r,k}$。rank 可以在其他 rank GET 完成前开始自己的 forward，后续真实 collective 和返回依赖再形成 join。设 $\rho_b$ 为批结果实际依赖的设备与通信事件集合，future 的可取时间 $h_b\ge\max_{e\in\rho_b}t_e$。加入本机复制后将相应完成事件连到消费该副本的 rank，最后一个相关事件的到达时间决定对应 join。

EngineCore 为每实例维护待取输入、可调度请求、已发出的 batch future 和输出。队列有空间且能发批时继续排程，否则在具体条件下等待下一 future。进入阻塞等待的时间内，engine 暂停该主循环的取输入。此依赖由并发和当前队列状态决定。异步候选把远端恢复改成独立在途状态，允许 engine 接收输入或推进其他 ready 批。被阻塞请求仍需等完整状态就绪。模型需要有上限的传输 credit、实际目的分配和完成通知，因此可表达异步时的排队迁移。见 [固定版本 EngineCore 批队列逻辑](https://github.com/vllm-project/vllm/blob/0fc695fc6d1d82e9a5ac6835ac8e4e1c83703665/vllm/v1/engine/core.py#L443-L523)。

物理减量先比较固定请求集的容量约束。若端口 $p$ 承担总载荷 $W_p$，速率上限 $C_p$ 以字节每秒计，纯载荷时间下界为 $\max_p(W_p/C_p)$。同头合并后要重算每口分布，再加入本机复制与可见性依赖，比较批次关键路径。异步在固定字节时保持同一个容量下界，但会改变传输活跃窗口及 GET 到摄入、就绪批的依赖。调度可通过改变本地命中、物理路径、重算选择或实际利用率改善带宽受限的吞吐。在低载和固定字节条件下，主要看等待和 TTFT。

固定外部到达后，对每个窗口 $[t,t+\Delta)$，把已进入恢复阶段的描述符按实际提交时间计入 $W_\Delta(t)$，以 $8W_\Delta(t)/(B\Delta)$ 衡量聚合出站服务压力，$B$ 以 bit/s 计。端口归属可观测时同样检查最热口。GET 的同步提交本身会受上游堵塞限制，因此结合 D TX、在途 GET 和 P 批队列，分别解释已提交和未获准提交的字节。原 r11 的 1 秒和 5 秒峰值需求约 68、20 Gbps，整轮平均 2.66 Gbps。r19 集中释放 10 条前驱已完成的高恢复后继，实测原生 41.832 GB 对应 100/200 Gbps 的聚合纯载荷下界 3.347/1.673 秒。100 Gbps 下，按每轮 MAC 字节算出的最热口串行下界达 3.76–3.91 秒，同窗口原生 2 秒提交峰值约 101.28 Gbps。该波次的 P0 GET 活跃时间对带宽近似成反比，粗粒度端口监测仍仅针对可观测的窗口。[r19 到达和负载](workloads.md#r19-高远端恢复的自然后继) · [实测](results.md#r19-apc-开启的高远端恢复-ab)

### 减量如何传到服务指标

对给定的批次与释放事件，按事件依赖计算两条路径的到达时间 $F_v(m)=d_v(m)+\max_{u\to v}F_u(m)$。模式 $m$ 的 GET 时长包含实际端口分流、队列与服务，本机补齐有独立的等待与服务。根据每条模式的实际状态核对跨机量 $W$。打包自身节省的是 $W_{\rm packed}^{\rm native}-W_{\rm packed}$，即用同一已掩码恢复计划算出的原生请求量减实发量。两臂 $W^{\rm native}$ 的变化单独归于缓存状态和恢复计划差异。

在固定临界 rank 和近似串行的情形，可先用 $8\Delta W_\star/B_\star^{\rm eff}>\Delta A_\star$ 筛选有机会获益的批。$\Delta W_\star$ 取这次 join 相关的被消除重复字节，$B_\star^{\rm eff}$ 是其可得的服务速率，$\Delta A_\star$ 是临界路径新增的配对、计划与本机填充。对实际并发，比较 $F_{\rm join}$ 的差，允许两臂的关键 rank、配对等待与计算重叠变化。打开 APC 后由原始前缀长度直接推断 $\Delta W_\star$ 会高估可消除的字节。

整轮吞吐取决于最后完成的请求。令 $T_i^{\rm post}$ 为首 token 后到请求结束的时间，则从共同回放起点计 $D(m)=\max_i(a_i+T_i^{\rm TTFT}(m)+T_i^{\rm post}(m))$，$X(m)=\sum_i n_{i,\mathrm{out}}/D(m)$。因此同一笔 P 恢复提前量只有传到尾部请求完成时，才改变有限轮吞吐。批次缩短与 TTFT、TTFT 与整轮吞吐各有一次关键路径选择。校准时把同一请求的 P 入队、同步恢复、P 结果、D 首 chunk 和 decode 尾段对齐，独立汇报尾部请求的身份和耗时。峰值提交负载和 PFC 帧增量只能帮助定位潜在受限窗口。可用服务时间还需结合热点端口字节、粗采样粒度和 GET 活跃区间估计。

r19 的配对给出这两次关键路径选择的实测量级。每轮同头少读 20.594 GB，100/200 Gbps 下 P0 的同步 GET 活跃量分别下降约 2.01/1.06 秒，打包活跃量为 0.58/0.57 秒，P0 同步 load 净省 1.48/0.53 秒。整轮平均排空时间只净省约 1.23/0.74 秒，最长完成请求均有约 17 秒 D 输出。两档都应分别用传输窗口、批窗口和排空窗口校准。当前两档的数据可以检查成本差随带宽变化的方向，交叉点受实际目的页分散、P/D 两侧负载及读算重叠影响。[r19 阶段和各请求](results.md#r19-apc-开启的高远端恢复-ab)

对 r20 的同批流水，令 $s_i$ 为 rank 提交第 $i$ 次本机分发返回的时刻，$c_i$ 为设备分发完成时刻，$g_{i+1}$ 为后继 GET 完成。目标地址互斥时，下一 GET 从 $s_i$ 之后可启动，下一次同头汇合仍等待对应的 $\max(c_i,g_{i+1})$，随后复用 wire buffer。最后一次分发的 $c_i$ 仍是本 rank forward 的硬依赖。以设备事件的交集计算重叠，再用批次和排空按 $F_v$ 对应各自的收益。模型需要重新估计重叠条件下 GET 与本机 copy 的服务时间，r19 静态时长回放只用于筛选。[r20 原始机会](results.md#r19-trace-提供的机会)

r20 四对实测中，P0 并集重叠下界为 278–316 ms，同步 load 净省 99–180 ms。以 200 Gbps 反序为例，异步臂的 P0 GET 活跃并集增加约 101 ms，P0 同步 load 仍净省 99 ms。模型要保留配对等待、流内提交和实际 GET 服务的变化。按跨 rank 区间并集衡量重叠，再按每个 batch 的最晚相关 rank 估算结果时间。两档的 TTFT p99 两对一升一降，同一请求的 P 阶段收益还会被 D 首步等待改变。排空由另一条长输出请求决定，四对吞吐小幅提高。[r20 实机对照](results.md#r20-同批分发与下一笔-get-的异步重叠)

逐轮校准使用两个嵌套分解。把客户端 TTFT 按客户端、代理 P HTTP 与 D 首步的相邻事件在 D 单调钟上相加。P HTTP 内部用 P 单调钟单独算接纳到首派发、首派发到末批结果，余项是引擎观察窗两侧的合量。用 Unix 事件锚点估算两侧各自耗时；若要归到具体接口，保留该接口的直接事件。D 首步分为查池前、查池与发起传输、传输 handler 包络、末笔传输到首块。r20 两个尾部回退分别落在 P 结果后和 P/D 接纳侧。估计同批流水的服务效果时也要跟踪实际组批，尤其是首次重叠以前已经出现的批形差异。[r20 逐轮复盘](results.md#逐轮阶段复盘)

对跨批方案，调度器生成输出、目标页和租约有效、依赖 chunk 在设备可见、executor 可以启动是不同的事件。提前发 GET 的最早时刻由合法源、目的页与传输 credit 决定。提前发 forward 还需该请求自己的前缀与最近 chunk 就绪。核对未来等待时，只从依赖完全就绪起算，按当时被阻塞的具体 future 或资源归因。r19/r20 中与旧 GET 共时的无自身 GET 后继均带前序依赖。若检测到首 chunk 已被派发但其 GET 未发，进一步比较对应的页分配和 connector 就绪时间，才能判断可否提前。[跨批等待实测](results.md#跨批等待证据)

## 决策、目标与公平比较

当前设计固定合法前缀与 P/D 路由，从 APC 后的实际缺页导出可共享的 Attention 恢复组，再用物理字节、端口与本机补齐代价解释收益。保留批次依赖用于归因。r18 对同一观测图的比较中，批次就绪策略只比通信完工多提前 28.55 微秒，分发积压较少。该原会话更新了模型适用范围，当前设计见 [七步法](research-seven-steps.md#5-what-is-the-design) 与 [r18 证据](results.md#r18-原长会话打包分发-trace)。

实现参数 $\theta$ 包含跨机同头合并、本机分发路径、GET 启动与完成机制、描述符粒度。在线策略 $\pi$ 在当时状态 $\mathcal S_t$ 上选择路由、完整前缀获取或重算、预取与保留、批准入和 credit。$\mathcal S_t$ 包括已观察到的缓存、租约、资源余量和队列。远端读省掉的跨机字节属于 $\theta$ 或改变了物理路径的策略动作。调度次序在相同字节和有效容量下主要改变完成顺序和资源利用率。优先按固定输入和正确性约束比较

$$
X(\theta,\pi)={\sum_i n_{i,\rm out}\mathbf 1(i\text{成功})\over t_{\rm drain}-t_0},
\qquad \big(-X,\ Q_{.99}(\{T_i^{\rm TTFT}\})\big).
$$

同时报告请求完成率、比较组成功数、相同输出预算、TTFT 分布、D TPOT 和端口/显存预算。给定线上 SLO 后可最大化达标完成率。统一接收集合，同时记录拒绝、取消和失败，避免因丢失长请求而误判改进。用固定字节的异步对照辨认阻塞放大，用固定调度的去重对照辨认物理减量，之后再比较联合决策。

## 远端读取与重算

令 $H_i^{\rm local}$ 是 P 已有的完整 Hybrid 前缀长度。重算从这个位置继续，P 本地无合法状态时从头 prefill。远端读计划在 $H_i^{\rm local}$ 之外取回连续且可校验的状态，得到更长的 $H_i^{\rm read}$，再计算剩余 token。可选恢复边界由 attention KV 与 SSM/conv checkpoint 的共同可用性决定。若运行时只有整段恢复接口，先比较这两条完整路径。

在同一到达状态 $\mathcal S_t$ 下，对每条路径 $m\in\{{\rm read},{\rm compute}\}$ 预测首 token 时间 $\widehat y_i(m\mid\mathcal S_t)$。读路径包含现有 GET 积压、有效服务率、本机复制与状态发布、以及尾段 prefill。重算路径包含可排到的 P 时间、按 4096 token 预算推进的分块 prefill 及批间等待。两条路径都计 P→D 交接和 D 首步。分块成本按已有前缀长度、块形状、并批和图模式估计。

近似串行且有效读速率可视作常数时，把读计划的首 token 延迟写成 $8W_i^{\rm read}/B_i^{\rm eff}+A_i^{\rm read}$。$W_i^{\rm read}$ 为实际 D→P 字节，$B_i^{\rm eff}$ 为该请求可获的有效 bit/s，$A_i^{\rm read}$ 是同一状态下读计划的其余关键路径成本。重算延迟为 $A_i^{\rm compute}$。若 $\Delta_i=A_i^{\rm compute}-A_i^{\rm read}>0$，读的近似分界为

$$
B_i^*=\frac{8W_i^{\rm read}}{\Delta_i}.
$$

若 $B_i^{\rm eff}>B_i^*$，读的预计单请求首 token 更早。若 $\Delta_i$ 非正，即使传输服务时长趋近于零，这次读也无预计首 token 优势。并发变化或存在读算重叠时，用事件依赖直接估计两条完成时间。重算会占用 P 的分块预算，远端读会消耗端口并可能阻塞后续批。系统策略需同时看两类资源的积压和对其他请求的影响，并以整组吞吐和 TTFT p99 验证。减少读取字节或优化图执行都会移动这个分界。[成本模型参考](https://arxiv.org/html/2610.21500v1#S4)

r14 比较的是不同带宽下的热读取，缺少同 token IDs 的主动重算对照。r10 的自然会话提供不同历史长度下的分块成本样本，可用于初始校准。同前缀的两条路径需实测分界。见 [读和重算的受控比较](bottleneck-and-validation.md#远端读与重算对照)。

## 校准与留出

| 层级 | 校准输入 | 检验输出 |
|---|---|---|
| 路径与状态 | 原始前缀尺寸、每 rank 描述符和键等价、端口 readback、目的容量 | 方向字节守恒、rank 完整性、失败清理、无提前可见 |
| 执行与进度 | 调度器事件、原生 GET、rank forward、CPU 与 CANN 时钟 | 同批传播、GET 和设备前进重合、接收前停滞、实际批大小 |
| 端到端 | 到达及输出契约、配置、独立轮次 | 吞吐、排空、TTFT、D TPOT、成功数和置信区间 |

先用一部分重复轮估计成本，再留出完整轮和负载。低载点约束单次读取，强限速点约束有效服务，原始端口设置点检验剩余端点/串行路径，带 APC 的自然会话检验可推广范围。当前 r14 的固定 96 请求用于有限集合比较。它与持续流量的稳态容量和生产 P99 分开标注。按编排和源数据的版本绑定参数。优化前的排队、已完成时刻和最终 cache hit 只用作校验标签，在线策略不从这些结果取未来信息。相关机制的判据见 [定位与补测](bottleneck-and-validation.md)。
