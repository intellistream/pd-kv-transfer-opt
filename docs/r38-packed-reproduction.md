# r38 原生带宽复测与同头打包对照

## 对照与计量

保留 r28 的 Terminal-Bench 2.1 三十个长会话、170 条请求和同一会话起点。源轨迹的历史和工具结果进入后继输入，后继发布时间依赖前驱本次实际完成。生成使用温度 0、EOS 和 r28 的逐条预算。两臂使用同一个原生 P/D 路由策略，路由、组批及实际生成内容由本次运行产生。两台 8 卡 910B2 跑 Qwen3.5-35B-A3B 的 2P2D，P 开启 APC 并保持默认图策略，D 的 APC 关闭并使用 `FULL_DECODE_ONLY`。每臂开始时排空引擎、清空 Store、隔离 P APC 命名域并重启代理。四个引擎在各臂间保留已捕获的图。[r28 的完整配置](r28-natural-bandwidth-plan.md) · [源轨迹清单](../configs/workload-natural-r10.json)

原生臂执行 vLLM、vLLM-Ascend 和 Mooncake 原生逐 rank 同步读。打包臂复用 r19 已归档的实现，在 APC 完成本地缺页判断后，同头组用一次跨机读取，再同步在 P 上填充目标页。其 preflight 同头校验不满足时回到逐 rank 读。打包首次初始化和每个活跃 worker 的首次 4 KiB 样本对照在正式时窗内，额外校验 GET 载荷单列。两臂握有同样的 GET 时钟探针和客户端输出摘要，关闭 CANN。按 `原生100 → 打包100 → 打包200 → 原生200 → 原生200 → 打包200 → 打包100 → 原生100` 执行，D 八口分别读回 12.5 Gbps 或 25 Gbps/口。100 Gbps 为主要判断条件。[r19 运行适配](../results/2026-11-18-r19-natural-ab/runtime/provenance.json)

最终吞吐使用首条计划投放到最后完成的正式输出 token/s。每臂记录实际输出量、完工会话、原生等效描述符和物理 GET、各端口的 MAC 计数、D 运行及排队指标。减少量以**同一批实际缺页描述符**的原生等效字节为分母，D MAC TX 提供独立核对。GET 与本机分发的活跃时间各自取 P 同机事件并集，同期可能跨实例重叠。D 有在途 P 任务时的空闲由周期指标和代理路由估计，粒度与精确的 D KV 就绪事件不同。

生成端摘要按实际 token ID 序列保存完整 SHA-256 和最长至 16,384 token 的若干前缀摘要。相同前缀摘要只核对该段输出；第一个不同的存档长度是分叉位置的上界。固定外部计划的正反序有助于识别重复性。实际输出分歧时，分别比较 $N$、$T$ 和 $X=N/T$。对占据排空路径的生成阶段，把首 token 后的驻留 $g_i$ 精确写作 $N_i(g_i/N_i)$，用两臂实测的首 token 之前阶段、输出量和每 token 驻留分别替换，再传播会话依赖。该分解跟随混合条件下的完工会话切换，用于描述时长差。路由和调度在真实干预中也会变化。[计算入口](../pd_kv_transfer_opt/profiling/analyze_packed_natural_replay.py)

## 之前的调整为何难以传到吞吐

先用同一分解重算 r28。100→200 的正序两轮，首 token 前阶段贡献约 11.97 秒净节省，实际输出量贡献约 0.33 秒，每 token 生成驻留抵消 12.42 秒，整轮近乎持平。反序两轮的 83.77 秒时差中，首 token 前贡献 2.03 秒，实际生成量贡献 131.77 秒，单 token 驻留抵消 50.03 秒。100 Gbps 的同档重复也出现 73.14 秒时差，其中实际生成量项约为 79.03 秒。时间差落在 D 的生成部分之后，仍需区分生成多少与生成多快，再检查是否有 P→D 供给传导。[r28 归档与阶段对照](critical-path-attribution.md#r28-原生长会话的完工路径)

r28 首轮和 r38 首轮原生 100 Gbps 的实际输出量仅从 148,164 增至 148,739，完工仍快 79.26 秒。两轮同样的 `natural-crack-7z-hash` 会话最后结束，最后一条由 D1 转到 D0。该会话首 token 后驻留合计少 74.68 秒，P HTTP 少 3.99 秒。170 条中 37 条 P/D 实际去向均匹配，24 条输出长度相同。把每请求生成量与每 token 驻留分别置换，折算完工差中的贡献为 +106.77 秒和 −31.73 秒。只比整轮总 token 会漏掉请求之间的工作量重分布。[重算数据](../results/2026-11-20-r38-packed-reproduction/direction-screen.json)

- **减少等待需要推进有独立前驱的工作。** r19/r20 中，有些无自身 GET 的批与旧 GET 同时在途，仍在等自身前一 chunk。r21 的扩展重放中，固定原依赖时关键路径选读与最长可行读没有稳定差异。r24 提前处理 ADD 后，等待主要移到调度器和 worker 入口前。下一次尝试流水需要明确一个已经满足页、状态和计算前驱的消费者，并量到它的实际开始移动。[依赖与接纳归因](critical-path-attribution.md#多恢复批选读的扩展重放)
- **前段提早交付收益取决于 D 容量和完工会话。** r27c 固定路由和输出，200 档把 GET 活跃从 78.39 降到 40.28 秒。决定全轮的请求 P 提早 39.35 秒，D 到首 token 多等 32.69 秒，之后生成又多 5.29 秒。D1 持续有工作可跑，整轮只快 1.36 秒。r31 自然长会话 P 未观测到物理分配失败。D 信用、P 暂存和 GET 优先级各需要相应的实际约束才能生效。[r27c / r31](critical-path-attribution.md#r27c-原生路径的带宽与排空归因)
- **r19 行为改变了实际工作量。** 100 Gbps 高回读波次相同恢复计划从 41.832 GB 减至 21.238 GB。P 同步 load 净省 1.48 秒，整轮吞吐增 5.71%。这组安排使 10 条高恢复后继集中释放，端口服务直接影响 P forward。r33 原生自然长会话即使在已观测的 P 窗口中将 GET 占用归零，固定其他驻留的尾链重放仅省 0.283 秒。当前工程组件保留独立对照，覆盖范围由实际回读与 D 排空验证。[r19](results.md#r19-apc-开启的高远端恢复-ab) · [r33](critical-path-attribution.md#整轮敏感性)

## 跨领域可借用的机制与证据门槛

**Spacker 的本地状态复用。** Spacker 在状态迁移中对各状态单元比较目的端本地重载和网络搬运。把这个选择迁移到 2P2D，单位是一个可合法恢复的 Hybrid 前缀，需要逐 rank 对齐 Attention 页和同一代的 SSM/conv 检查点。r33 的 58 条实际恢复请求中，56 条换了 P。逐 token 核对输入，这 56 条的上一轮输入都覆盖本轮读取所需的逻辑前缀，涉及 97.05/100.29 GB。该候选集仍需确认旧 P 的已计算前缀、可用页和匹配检查点确实存在。按上下文长度和固定 4,096 分块的实测 forward 中位数估算，单纯重算缺失段比最慢 rank 实测 Store GET 慢的比值中位为 7.18，58 条中最有利一条也为 1.46。重算估计已略去队列和派发。[Spacker §III–V](https://me.sage.org.ai/contents/research_papers/2025/2025_spacker_icdcs_2025.pdf) · [r33 的实测数据](../results/2026-11-20-r33-native-prefill-path/summary.json)

对该候选先计算可兑现的收益。若 P 路由候选 $p$ 有完整状态，令 $Q_{i,p}$ 为请求到真正进入计算的预计等待，$W_{i,p}$ 为实测缺页成本，$C_{i,p}$ 为新增 prefill 开销，$H_{i,p,d}$ 为真正交付到目的 D 的耗时。D 可开始的时点至少为

$$
 A_{i,p,d}=\max\!\left\{r_i+Q_{i,p}+W_{i,p}+C_{i,p}+H_{i,p,d},\ A^{\mathrm{decode}}_{i,d}\right\}.
$$

顺序相加描述一条串行请求路径，存在真实并行时按依赖图重算。$A^{\mathrm{decode}}$ 包含 D 的实际槽和页可用时点。用 r33 的 P 单调时钟检查这 56 次到达，有 21 次旧 P 没有其他尚未完成 prefill 的 HTTP，涉及 35.03 GB。r33 实际尾链唯一命中的换 P 请求在这 21 条之外。旧 P 可以少做恢复工作，但增加的等待、占页和对其他批次的影响都要进入重放。最强的比较对象是同 session 粘滞、缓存与队列感知的 P 路由，以及 AMPD 式 D 本地增量。通过比较后才能判断有没有可独立主张的机制。[Mooncake](https://arxiv.org/abs/2407.00079) · [AMPD §3–4](https://arxiv.org/html/2602.14516v2#S4) · [状态与排空模型](problem-model.md)

**TENT 的动态端口选择。** 根据剩余流量和逐路径完工选择 rail。迁移到本平台，首先需要确认同一源页可从多个物理出口服务，并取得各出口未完成量与最晚 rank 的下一步依赖。r29/r30 在 100 Gbps 总额固定时，旧权重使吞吐低 3.02%，按当轮热点重标定后高 1.98%。这给出静态分配的代价及可测空间。自然长会话如缺少可替换的路径或临界端口等待，优先用可观测的减量与落点做比较。[TENT §4.2](https://arxiv.org/html/2604.00368v1#S4.SS2) · [两组实测](results.md#r29r30-固定总额的八口限速实测)

FaSST 的零等待合批也有本机机理对照。r32 的 HIXL READ 将 64 个 12 KiB 描述符由 64 次提交并成 1 次，6.536→1.221 ms。相同大载荷改变每次提交的向量大小后，在 100 Gbps 的单口仍约 12.25 Gbps，已接近 12.5 Gbps 上限。自然负载需先观察热路径有多少可再合并、同端点且此刻已就绪的小片，然后看最后完成 rank 能否提前。线速区间的优先动作是消除重复字节，或在确实有出口选择时重分配物理流量。[FaSST §3.2](https://www.usenix.org/system/files/conference/osdi16/osdi16-kalia.pdf) · [r32 探针](results.md#r32-同字节的-hixl-批提交)

**FineStream 的实测服务曲线。** 借鉴其按工作形态测量执行成本的做法，校准 D 实际有效批宽、图宽度和前缀长度，再估计提前送到 D 的任务改变了多少生成服务。r34 的 D1 上，同一长会话首轮 `natural-crack-7z-hash:31` 在批内，四 rank FULL replay、已全部 KV 就绪且排除 CANN 窗口。八条活跃请求映到八槽图，39 个步样本的中位间隔 21.58 ms。九条映到十六槽图，50 个步样本的中位间隔 25.15 ms。最长上下文中位约 206K 和 204K。按实际批宽折算，约 371 和 358 token/s。以观测的八条组为参照，九条组达到相同阶段速率需要把步间隔压到 24.28 ms，差约 0.87 ms。这是运行形态的相关性，新增请求的输入和其他批成员也发生了变化。用同一个九请求 batch 固定输入和页映射，改变捕获档位才能测到 padding 的独立成本。这个对照可以校准供给模型和已有图配置的影响。[FineStream](https://www.usenix.org/conference/atc20/presentation/zhang-feng) · [r34 步进原始观测](../results/2026-11-20-r34-native-decode-path/summary.json)
