# r40/r41 冷首轮换序的 100/200 Gbps 对照

r40 在两台各八卡 910B2 上对照同一套 vLLM、vLLM-Ascend、Mooncake 和 Qwen3.5-35B-A3B。正式基线沿用 r28 的自然长会话与原生执行。对照顺序为原生 A1、历史评分 C1、全队列短 prefill 优先 B1、全队列短 prefill 优先 B2、原生 A2。SJF 分别与前后两个原生轮配对。两个原生轮也给出同档自然波动。[r28 的配置与工作量](r28-natural-bandwidth-plan.md)

## 实机对照口径复查

| 项目 | r40 实际使用 |
|---|---|
| 执行版本 | 两机 vLLM `0fc695f`、vLLM-Ascend `5cb98ca` 的跟踪文件干净，Mooncake NPU `0.3.11.post1`。 |
| 引擎启动 | 读取在运行的四实例 argv 和 Store 配置，与 r28 逐项一致。每实例 attention TP4、expert EP4、DP1，16 个运行槽，4,096 token 批预算。 |
| 图与缓存 | P 使用原生图策略与原捕获列表，实测选择 `FULL_AND_PIECEWISE`，D 为 `FULL_DECODE_ONLY`。两侧日志均为 `enforce_eager=False`。P 本地 APC 开启，D 本地 APC 按 r28 关闭。两侧走原生 Hybrid KV、原生同步读取和 P→D 交接。D 写入并提供 Store。 |
| 到达与生成 | 同一 Terminal-Bench 2.1 源版本、30 会话、170 请求、原始 token 指纹和前驱释放。两臂终止条件为自然 EOS 或原有生成预算。温度、种子、路由策略和连接复用来自 r28。 |
| 初态 | 各臂从无计时在途请求及空 Store 开始，采用独立 APC 命名域。前驱与后继都计时。对比的是集中启动的真实长会话重放，持续独立到达与长工具等待另需相应覆盖。 |
| 带宽 | 100 Gbps 为唯一实测档，D 八口各 12,500 Mbps。每臂核对限速的配置值、运行值和恢复回执。 |
| 共用观察 | P 侧两组都携带冷首轮信息并记录一次首块事件，便于验证是否真的换序。A 的等待队列原样交给 scheduler。正式计时关闭详细方法及设备 profiler。 |

C1 在两个 P 首次接纳后约 5 秒，对已到达、仍在 waiting 的冷首轮按输入长度和历史后缀估计，允许提前最多两条。历史后缀使用 r28 其他会话，留出当前会话身份。B 臂在同一时点按输入长度稳定排序全部符合条件的冷首轮。两种模式保留非候选的位置和原生 running 执行，D 的选择仍由原代理在 P 返回后决定。计时中不使用固定输出、固定路由或同头打包。原生库的发布、SSM 对齐和页分配由 scheduler 继续执行。[P 实现](../pd_kv_transfer_opt/experiments/prefill_order.py) · [离线筛选](cold-prefill-order.md)

预估来自离线同模型对照。全队列 SJF 的吞吐变化为 **+6.92% 至 +10.23%**，历史评分为近似持平。r28 的 100 Gbps 两轮原生实测为 **312.38／281.78 token/s**，用于校验协议和波动幅度。r40 采用当轮的 A1 和 A2 计算实测策略效应。由于自然生成量可以变化，每一对同时核对实际输出总量和排空时长。计时中按真实端口与 D 进度解释收益传导。

实机审计包含各臂实际队列置换、30 条冷首轮首块、客户端全部终点、实际 P/D 去向以及八口和 Store 回执。历史评分选择空集合时，使用该轮实际的队列行为解释测得差值。[复算入口](../pd_kv_transfer_opt/profiling/analyze_prefill_order_trial.py)

## 含排空实测

| 执行顺序 | 有效请求 | 实际输出 token | 含排空时长（秒） | 总吞吐（token/s） | 冷首轮首块等待 p50（秒） |
|---|---:|---:|---:|---:|---:|
| A1 原生 | 170 | 149,304 | 382.02 | **390.83** | 39.25 |
| C1 历史评分 | 170 | 168,008 | 467.46 | **359.41** | 33.60 |
| B1 SJF | 170 | 155,780 | 359.47 | **433.36** | 14.40 |
| B2 SJF | 170 | 147,002 | 348.03 | **422.38** | 15.82 |
| A2 原生回切 | 170 | 155,930 | 383.14 | **406.98** | 33.03 |

SJF 正序比 A1 高 **10.88%**，实际输出多 4.34%，完工早 **22.55 秒**。反序比 A2 高 **3.78%**，实际输出少 5.73%，完工早 **35.11 秒**。两次 SJF 的两个 P 均记录了实际换序，A1/A2 均为零换序。只看保持同一 P 的冷首轮，等待减少的中位数分别是 **23.77 秒**（16 条）和 **12.79 秒**（22 条）。A2 与 A1 的原生吞吐自身相差 **4.13%**，含排空时长仅相差 1.12 秒。两对各有 40 条实际 P/D 去向都相同，16 和 19 条逐请求输出长度相同。自然生成变化和调度对实际时序的作用都进入了实测对照。[配对与根请求审计](../results/2026-11-20-r40-prefill-order/summary.json)

逐阶段用实测驻留代入会话依赖。A1 到 B1 的 22.55 秒提前中，P HTTP 对应 **7.20 秒**，首 token 后阶段对应 **15.54 秒**。A2 到 B2 的 35.11 秒提前中，P HTTP 对应 **−0.16 秒**，首 token 后对应 **35.24 秒**。B1、B2 的最后完工分别为 `crack-7z-hash` 和 `gpt2-codegolf`。两个原生臂的末会话均为 `fix-ocaml-gc`。这给出了原始时差出现的位置。观察到的组批、输出和路由也随实际执行变化。

C1 在 P1 把 `gcode-to-text:97` 从队列第三位提到首位。其首块等待相对 A1 少 **19.55 秒**，实际 P 去向也改变。C1 的吞吐比两个原生臂分别低 **8.04% 和 11.69%**，最后完工落到 `crack-7z-hash`。与 A1 的 85.44 秒完工差中，约 **86.00 秒**对应首 token 后期间。当前历史评分只覆盖一次实测，局部提前和整轮结果均按本次自然生成解释。

A1 实际 P 输入约 **60.77%** 来自本地 APC，**18.01%** 来自外部恢复。五臂 D 侧八口合计的一秒发送峰值为 **49.25–61.69 Gbps**，对齐到各短采样段时，达到 85 Gbps 的累计时间均为零。r40 的证据支持固定 100 Gbps 配置下的 P 首波排队与 D 生成推进。SJF 留作有效的简单对照，当前历史评分结果给出其覆盖冷长尾的局限。引擎方向依靠实际生成步数和每步服务成本分析。[引擎层敏感性](decode-execution-options.md)

五臂共 **850/850** 条完成，均确认驱动读回及当臂结束恢复。两台控制器已停止，16 张卡均空闲，D 八口均恢复每口 200 Gbps。归档保留清洗后的请求阶段、实际队列和端口指标。[运行版本、协议和收尾](../results/2026-11-20-r40-prefill-order/manifest.json)

## r41 的 200 Gbps 补测

r41 单独重启同一部署，沿用 r40 的五臂顺序、同一份历史评分和同一批 30 个 Terminal-Bench 2.1 长会话、170 条请求。两机运行参数与 r28 逐项核对，保持 P APC、自然 EOS、原生路由、16 个运行槽及 4,096-token 批预算。D 八口的 200 Gbps 聚合上限均读回 25,000 Mbps/口。每臂从独立 APC 命名域和空 Store 开始。正式计时记录首块、代理、客户端及端口事件，详细设备与传输 profiling 使用已有独立观测轮。100 和 200 Gbps 分别使用各自同场的原生臂做分母。 [环境和读回](../results/2026-11-20-r41-prefill-order-200/manifest.json)

各列依次报实际输出、含排空时长和总吞吐。

|---|---:|---:|
| A1 原生 | 149,304 / 382.02 / **390.83** | 138,768 / 362.92 / **382.37** |
| C1 历史评分 | 168,008 / 467.46 / **359.41** | 139,289 / 361.90 / **384.88** |
| B1 全队列 SJF | 155,780 / 359.47 / **433.36** | 132,784 / 288.43 / **460.37** |

### 吞吐变化的阶段归因

正值表示 SJF 提前。P HTTP、D 首 token 后和其余阶段由原始时间轴的阶段替换重放分解。实际生成和去向随轮次变化，分解结果说明时差出现的位置。

| 对照 | 首块等待 p50，原生→SJF | 整轮提前 | P HTTP 对应 | D 首 token 后对应 | 输出量变化 | 吞吐变化 |
|---|---:|---:|---:|---:|---:|---:|
| 100 A1→B1 | 39.25→14.40 s | 22.55 s | +7.20 s | +15.54 s | +4.34% | **+10.88%** |
| 100 A2→B2 | 33.03→15.82 s | 35.11 s | −0.16 s | +35.24 s | −5.73% | **+3.78%** |
| 200 A1→B1 | 36.74→15.96 s | 74.49 s | +0.50 s | +74.18 s | −4.31% | **+20.40%** |
| 200 A2→B2 | 32.76→14.29 s | 122.69 s | −8.26 s | +131.05 s | −12.60% | **+18.80%** |

- **200 首对的冷队列确有推进。** 两侧都有 SJF 队列置换，20 条保持同一 P 的冷首轮等待中位减少 22.43 s。原生末会话的冷根 crack-7z-hash:31 首 token 后从 165.37 s 变为 27.66 s，实际输出 8,192→1,741。其后继 :32 的 P HTTP 从 2.42 s 增到 31.83 s，说明首轮推进可以把等待移给后继。同一末会话提前 74.58 s 后，build-cython-ext 接替决定整轮完工。
- **200 反序主要移动的是生成尾部。** 两个 P 均有合法置换，但 16 条保持实际同 P 的冷根等待改善中位约为零。原生末会话的 :35 和 :36 都输出 8,192 token，SJF 轮中分别为 900 和 1,641。原末会话从 464.19 提前到 177.90 s，winning-avg-corewars 接替，在 341.51 s 最后结束。实际 P/D 去向完全相同的只有 43/170 条，输出长度相同的只有 17/170 条。
- **历史评分的作用随实际激活而变化。** 100 Gbps 的 C1 实际前移 gcode-to-text:97，整轮相对 A1 低 8.04%，其多 85.44 s 的时长中，首 token 后阶段多约 86.00 s。200 的 C1 没有改变两侧等待队列。相对 A1 的 0.66% 原始吞吐差属于本轮自然执行差异。
- **同档原生变化提供背景。** 200 的 A2 比 A1 多输出 18.98%，却多用 101.28 s，吞吐低 6.98%。两个原生都由 crack-7z-hash:36 排空，其自身首 token 后约 112 s。主要前驱 :35 的输出 1,738→8,192，首 token 后由 25.74 增至 114.73 s，P HTTP 只差约 0.01 s。

**端口与 D 供给。** 100 五臂 D 聚合 TX 一秒峰值 49.25–61.69 Gbps，任一单口在有效采样中也未达到限额的 85%。200 五臂聚合峰值 63.05–100.12 Gbps，只有 B2 记录单口接近限额约 0.83 s。D 无运行无等待且有最终路由到该 D 的 P 请求在途的观测窗口，与各档接近限额的窗口均无重叠。r41 原生最后 P 回复后的排空分别为 91.01 / 112.51 s，SJF 两轮为 8.62 / 19.70 s。SJF 在两档都缩短了首波中一些冷请求的等待，观察到的整轮收益还受自然输出量、接替的尾会话和实际路由影响。r39 的同工作量对照进一步限制了将这些差值归因给跨机 RDMA。 [r41 请求、阶段和计数](../results/2026-11-20-r41-prefill-order-200/summary.json) · [r39 归因](bottleneck-verification.md#归因对照-r39)

r41 完成 **850/850**，清洗归档含五臂回执和实际置换，两个原生臂均零置换。两台服务已停止，16 卡释放，D 八口都恢复为每口 200 Gbps。 [r41 清洗轨迹与收尾](../results/2026-11-20-r41-prefill-order-200/manifest.json)

## 原生跨档与负载复查

重新读取 r40/r41 的 trace 与清单。170 条请求的输入 token 指纹、生成预算、前驱、会话起点、软件与模型指纹全部一致。两个原生臂均没有 P 重排，Store 在每臂开始前确认为空，P APC 使用独立命名域。每臂八个端口分别读回 12,500 或 25,000 Mbps。两个带宽档来自分开启动的两组调度对照，A1/A2 只是各自档内的执行位置。如下跨档换算用于解释观测数值。

| 同名原生臂，100→200 Gbps | 整轮吞吐 | Δ 实际输出 token | Δ 整轮时长 | 实际 P/D 同时匹配 | 输出长度相同 |
|---|---:|---:|---:|---:|---:|
| A1 | 390.83→382.37 token/s（−2.16%） | −10,536（−7.06%） | −19.10 s | 44/170 | 22/170 |
| A2 | 406.98→355.69 token/s（−12.60%） | +9,179（+5.89%） | +81.05 s | 43/170 | 19/170 |

A1 的 200 档先完成了 170 条，输出少得更多，所以 token/s 较低。A2 的 200 档最后一条 P 回复反而提前 **29.71 s**，该时点至整轮结束从 **1.74 s** 增到 **112.51 s**。同一个 crack-7z-hash:35 在 100/200 分别输出 **1,840 / 8,192** token，P HTTP **0.480 / 0.494 s**，首 token 后 **27.12 / 114.73 s**。它结束才释放后继 :36。逐阶段替换也把 A2 多出来的 **81.05 s** 中约 **73.79 s** 归到首 token 后。归因以实际生成量、请求驻留和会话依赖为依据，逐 token 生成分叉原因仍待观测。

两组的 **30 个独立会话都在 4.56 s 内启动**。之后只有前驱完成释放后继。四原生轮的 5–30 s 均只发出 5–6 条后继，D 聚合 MAC TX 全轮均值 **1.78–2.18 Gbps**，100 档一秒峰值 **52.02 / 61.69 Gbps**，四轮均无采样口达到本档限速的 85%。输出预算使用 r28 的“原轨迹输出计数与 8,192 取较大值”规则，156/170 条上限为 8,192，源轨迹输出中位数为 2,132。这些条件可以研究冷首波队列、EOS 与生成尾部，持续自然 RDMA 高压的验收仍需独立负载。后续按实际独立会话到达、逐口服务、关键 GET 等待和 D 供给判定哪段负载满足条件。 [负载设定](r28-natural-bandwidth-plan.md#负载与缓存) · [固定生成量与实例的归因对照](bottleneck-verification.md#归因对照-r39)
