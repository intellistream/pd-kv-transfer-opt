# 原生 2P2D 整轮吞吐瓶颈复核

主负载为 r28 的 30 个 Terminal-Bench 2.1 长会话、170 条请求，采用原生 vLLM、vLLM-Ascend 和 Mooncake。每个实例 Attention TP4、Expert EP4，两台 8 卡 910B2。以 100 Gbps 为主，200 Gbps 为带宽参考。本页以整轮输出吞吐做比较，用已完成的请求和原始时间戳追踪原因。[环境与数据集](r28-natural-bandwidth-plan.md)

**归因结论。** 100 Gbps 会增加同步 GET 服务时间。r39 锁定实际输出量和去向后，整轮升档效应在两对中为 +0.91% 和 −1.21%。当前完工路径的最大成本是依赖会话沿 D 累计的串行生成，另有冷首轮排在既有 P 计算之后。部署基线 r28 保留自然 EOS 和原生路由，较大的跨轮吞吐差由实际输出量和输出在完工会话上的分布解释。已证实的持续带宽瓶颈对应 r14 的高回读短输出诊断。[实机匹配对照](#归因对照-r39) · [跨轮批次与完工链](cross-run-throughput.md)

## 吞吐差异与请求完工的时间来源

对每个实际观测，$X=N/T$。将相对变化按 $\log(X_B/X_A)=\log(N_B/N_A)+\log(T_A/T_B)$ 分解。按请求的计划到达和前驱递推，复现从就绪到 P、P HTTP、P 至 D、D 至首 token、首 token 后五段以及最后完工。r28 的 680 条请求往返误差小于 1 微秒。将首 token 后驻留写成 $N_i\tau_i$，再逐项替换 token 量与每 token 驻留，用于解释不同观测中的完工变化。改变实际带宽可能影响组批、路由和 EOS，阶段替换只描述观测，实机干预效应另用匹配对照辨认。[模型定义](problem-model.md#会话闭环生成工作量与完工) · [r28 逐请求重放](../results/2026-11-19-r28-natural-bandwidth/closed-session-profile.json)

| 实际比较 | 含排空吞吐 token/s | 整轮完工差中的主要来源 |
|---|---:|---|
| r28 正序，100→200 | 312.38→403.72 | 多输出 43,369 token，整轮只慢 0.12 秒。P HTTP 提早 11.19 秒，被之后的生成驻留抵消。 |
| r28 反序，100→200 | 281.78→354.80 | 整轮快 83.77 秒，约 81.74 秒落在首 token 后。100 档最终 `gpt2-codegolf:31` 生成 24,098 token，200 档该请求生成 3,431 token。它在 100 档完成前已独跑超过 100 秒。 |
| r31，100→200 | 424.63→362.94 | 整轮慢 112.19 秒。对称替换中有 105.02 秒落在首 token 后。200 档最后的 `winning-avg-corewars:131` 本身只多 3 token，因前驱 `:126` 和 `:129` 均在 8,192 token 达预算，`:131` 的实际释放晚 230.18 秒。 |
| r28 首轮→r38 首轮，原生 100→100 | 312.38→376.51 | 总输出仅多 575 token，整轮快 79.26 秒，最后会话的生成累积少 74.68 秒。170 条中只有 37 条实际 P/D 去向均相同，24 条输出长度相同。 |

r28 的两次 100 档达到 85 Gbps 的计数窗口合计各约 0.45、0.40 秒，与采样到的 D 无运行无排队且同实例有 P 工作在途的窗口没有交集。r31 两个档位均无此种聚合压力，P 物理分配均零失败。r27c 是压力更强的受控例子，100→200 把 GET 活跃窗口从 78.39 降到 40.28 秒，并使 0–10 秒输出速率从 368.2 升到 647.8 token/s。在 18–32 秒输出平台，两 D 基本满槽，累计供给的增加主要留在 D 队列，整轮仍是 **886.81→888.31 token/s**。这三组观测提供了实际压力、解码供给和整轮收益之间的边界。[原生高压和自然对照](critical-path-attribution.md#r27c-原生路径的带宽与排空归因)

## r33、r34 和 r37 的方法证据

r33 原生自然 100 档实测 **392.33 token/s**，全轮 GET 100.29 GB。按 232 次 GET 的每进程时间戳，Store 墙钟中位 160.13 ms，内含 ADXL READ 区间 158.50 ms。同步读的等待已实测，单次调用的主要成本位于后端 READ 与完成段。首轮压尾的 P HTTP 是 53.54 秒，其中 50.97 秒在接纳后等待首块，等待窗口内有 185 个前序冷首轮批次、41.55 秒设备 forward、零 Store GET。最后完工的会话首 token 后驻留累计 356.89 秒，最后 P 回复之后仍需 120.37 秒，期间 D MAC TX 约 0.254 MB。[P 及 D 事件](critical-path-attribution.md#r33-原生-100-gbps-从-p-http-到-d-排空)

用 D 机同一单调时钟连接每请求实际完整 KV 就绪、完成、P HTTP 在途和逐口计数。排除 D 首次开始接收 KV 之前，D0/D1 在有目标 P 工作在途时完全无已就绪未完成请求的时长为 **0.49/2.15 秒**。两侧这两段与聚合达 85 Gbps 或任一口达其限速 85% 的窗口都没有交集。将就绪条件放宽到最多 3 条，仍无交集。按最多 7 条，D1 与聚合热窗重合约 0.40 秒，与任一口热窗约 0.81 秒。这是通过实际就绪事件核对的完全和部分供给，热窗阈值及端口统计采样粒度保留在归因中。[口径与重算入口](../pd_kv_transfer_opt/profiling/audit_bandwidth_bottleneck.py)

固定以上实测请求、路由、输出和其他阶段，用最大值重算 30 条会话的最后完工。GET 行乐观地从每个 P HTTP 窗口扣除同 P 的全部实测 GET 重叠，包括可能同时进行的计算时间，很多早于关键批的 GET 也会被扣除。此模型的变化范围是冻结的会话链成本。

| r33 条件回放 | 实测基准→模型总吞吐（token/s） | 排空提前 | 相对增幅 |
|---|---:|---:|---:|
| P HTTP 内观测到的同步 GET 占用归零 | 392.33→392.60 | 0.283 s | +0.07% |
| D 分页至完整 KV 就绪全部归零 | 392.33→392.64 | 0.326 s | +0.08% |
| P 前序与自身 forward 均缩短 10% | 392.33→396.70 | 4.618 s | +1.11% |
| 首 token 后驻留缩短 10% | 392.33→428.80 | 35.689 s | +9.29% |

r34 在同一自然负载的单臂实测为 **345.14 token/s**。D0 最后请求输出 8,192 token，共覆盖 8,160 个独跑步。完整偏移对应 14.40 ms/token，CANN 关闭窗口的局部步间隔中位为 13.59 ms。r34 与 r37 两次四 rank 采集校准到该原生周期，最大的时间成分是 NPU 算子执行与访存 **8.72–9.01 ms**，之后为四 rank 到齐后的机内 collective **1.89–1.95 ms**。按上下步设备依赖和会话前驱回放，仅 D0 已观测独跑步的算子耗时降 10%，总吞吐模型为 **345.14→350.32 token/s**。机内 collective 完成段缩短 20% 为 **345.14→347.37 token/s**。采集与普通运行有扰动，未覆盖的 host 时间保留为残差。[完整步进分解与回放](critical-path-attribution.md#r37-原生尾请求的单步分解)

## 归因对照 r39

同一 170 条输入、同一会话起点和依赖、原模型、P APC、空 Store。用 r33 实测的原生 P/D 去向和逐请求输出长度固定路由与工作量，每臂要求 164,662 个输出 token。保留原生逐 rank 同步 GET 与 P→D 交接，带宽以八口驱动真实读回为准。输出长度在该归因对照内固定，生成内容仍由模型产生，逐请求记录输出序列摘要。按 100→200→200→100 正反序进行，逐臂读回、清空缓存命名域并恢复端口。P 加入 Store 和 ADXL 调用及 prefill 批次计时，D 加入分配和交接就绪事件，两档使用相同探针。该对照用于验证固定输出和路由下的带宽作用，r28 正式自然 EOS 数据继续用于解释实际吞吐差异。

重启后 D 驱动库指纹有变化，正式臂统一用当前驱动的 `hccn_tool -stat -g` 读八口 MAC 计数，按单口观测窗口对齐。两机重新核对 vLLM、vLLM-Ascend、Mooncake 及模型元数据指纹与 r33 一致。

每对带宽的吞吐比在固定工作量下等于完工时间之比 $X_{200}/X_{100}=T_{100}/T_{200}$。分别报告正序、反序和同档复测。用相同实际描述符字节数的请求核对 GET 服务变化，再看同一时间段的 P 交付、D 已就绪工作和最终完工链。若改变带宽主要改变生成批次，继续用实际 token 工作和每 token 驻留区分中间环节。此过程与自然 EOS 的分子、分母分解互相核对。

四臂共对齐 916 次 Store GET 与相同载荷字节的 ADXL 调用，无失败。同步读变快在两个顺序中均可见。100 档的单口热窗，与目标 P 尚有工作在途且 D 无已就绪工作或只有至多三条的区间，均无交集。最后 P 回包后的 112–118 秒内，四臂 D MAC TX 各约 0.10–0.27 MB。这个阶段仍有大量生成工作，最终由 D1 上同一会话完工。[方法事件和逐请求分析](../results/2026-11-20-r39-bottleneck-verification/summary.json)

逐请求对称替换严格闭合正序的 3.66 秒与反序的 4.88 秒完工差。正序 P HTTP 提早 3.61 秒，D 至首 token 提早 1.11 秒，首 token 后驻留抵消 1.05 秒。P 的差主要来自冷首轮 `extract-elf:11` 的 HTTP 提早 3.55 秒。四臂这一请求在 scheduler 接纳后等待首块 47.30–51.41 秒，期间前序 P rank 0 forward 为 41.27–44.22 秒，Store GET 重叠为零。反序中升档增加的首 token 后驻留为 4.91 秒，其他段净抵消约 0.02 秒。最终会话的首 token 后成本累计 340–345 秒，占各臂整轮约 84%–85%。[逐阶段归因](../results/2026-11-20-r39-bottleneck-verification/summary.json)

用两次 100 档的实测时间图，冻结每请求输出、路由和其他阶段，将 P HTTP 内与同 P 的同步 GET 重叠的所有时间扣掉。含排空吞吐的模型结果为 **406.84→406.93**、**412.12→412.21 token/s**，两臂分别提早 0.094、0.080 秒。这两个模型量和实机正反序一起支持同一个归因。读取影响实际的 P 恢复服务，主要完工等待位于 D 的生成工作，冷首轮另受 P 计算队列影响。[重算入口](../pd_kv_transfer_opt/profiling/audit_bandwidth_bottleneck.py)
