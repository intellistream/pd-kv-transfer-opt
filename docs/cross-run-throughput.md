# 自然基线与固定工作量回放的跨轮比较

历史 r28 和当前的 r45 都采用自然 EOS 和原生 P/D 路由。r39 用同一批 Terminal-Bench 2.1 长会话，按 r33 的观测固定逐请求输出长度和实际 P/D 去向，供归因使用。各轮输入、计划会话起点、前驱关系一致。重算以首条计划投放至最后完成计吞吐。 [实验定义](bottleneck-verification.md)

## r28 的差距在同负载复测中怎样变化

**复核结论。** r28 的原始计量有效，作为带宽因果对照失效。重读四臂 680 条结束事件，每臂 170 条唯一请求全部成功。逐请求流式 token 计数、整轮输出桶、完成时刻和公布吞吐相互一致，D 八口限速读回及恢复也一致。正反序只有 20/170、21/170 条生成长度相同，即使 P/D 实际去向都相同，也分别有 42/47、38/40 条生成长度不同。在固定观测会话图上，仅把低档 P HTTP 换成高档观测，整轮分别提前 11.19 和 0.97 秒。r28 的约两成保留为生成工作量和排空路径漂移的历史观测。 [原始复算和受控正对照](../results/2026-11-22-cpu-rdma-effect-audit/summary.json)

逐项比对两份清单，r28 和 r45 的 30 个会话、170 条输入指纹、前驱、投放、生成预算、EOS 和原生路由策略完全一致，模型与软件指纹亦一致。r28 只限制 D 出站，D 本地 APC 关闭。r45 双向限速，D 开启本地 APC 并采用原生重算调度。两轮的实际去向和输出由各自的原生执行决定。 [r28 原配置](r28-natural-bandwidth-plan.md) · [并排复算](../results/2026-11-21-r45-r28-symmetric/r28-comparison.json)

- **反序更换了决定完工的生成工作。** r28 的 `gpt2-codegolf:31` 在 100 档撞到 24,098 token 的预算，单请求首 token 后占 329.26 秒。在 200 档按 EOS 停在 3,431 token，首 token 后 57.68 秒。此请求 D 发出到首 token 只差 15.51 ms。r28 两档整轮相差 83.77 秒，固定会话图的阶段替换把其中 81.74 秒归到 D 首 token 后。r45 同一条在两档按 EOS 停在 2,904 和 2,888 token，退出了最末路径。r45 反序都由 `crack-7z-hash:36` 决定终点，100/200 的这条请求实际输出 8,192/3,364 token，首 token 时间为 367.43/367.10 秒，首 token 后为 113.88/46.98 秒。r45 200 档全轮还少生成 6,847 token，抵消部分随完工提前得到的吞吐增量。 [替换分解和尾请求](../results/2026-11-21-r45-r28-symmetric/r28-comparison.json)
- **两轮实际跨机工作发生了变化。** r28 四臂 D 本地 APC 均零命中，外部 KV 交接 1,324.22 万输入 token。r45 的 D 本地复用是 849.82–875.32 万，D 外部交接减到 448.91–474.40 万 token。D MAC 接收从 668.06–676.20 GB 降至 308.60–315.54 GB，含原生交接和 Store 后台写。r28 的实际带宽干预在 D 出站，两次 100 档 30 秒出站峰值只有 15.07/20.11 Gbps，聚合达到 85 Gbps 分别持续约 0.45/0.40 秒。r45 同档最热 D 口十秒峰值 3.30/3.74 Gbps。r28 的吞吐差量级主要来自生成工作与压尾变化。两轮的 KV 交接和实际路由均有变化，现有同负载比较提供分阶段归因，D 侧各设置对 EOS 的单独作用仍待隔离。 [逐口及供给分析](restore-workload-screen.md) · [对比入口](../pd_kv_transfer_opt/profiling/compare_native_bandwidth.py)

再用 r28 自己的端口计数与完工链交叉校验。在 100 档的固定阶段回放中，从每条 P HTTP 中扣掉与任一 D 口达到自身限额 85% 的全部采样交集，正序完工时间不变，反序只提前 1.60 秒，总吞吐由 281.78 增至 282.60 token/s。把两条 200 档的 D 出站样本按原采样时刻作为待发输入，经每口 12.5 Gbps 的独立队列回放，最长连续排队分别为 1.07 和 0.50 秒，与各自最后会话的 P HTTP 均无时间交集。两项复算说明已观测的热点及直接等待难以解释 83.77 秒的反序完工差。采样内的微突发及组批反馈仍需独立观测。 [逐口回放和删减敏感性](../results/2026-11-21-r45-r28-symmetric/r28-comparison.json)

同源扩容的 r48 采用不同的会话数量与到达表。其正序 **456.74→427.91**、反序 **437.71→389.22 token/s**。反序也出现了几乎相同的完工时长（515.33→513.25 秒）和很大的输出量差（225,568→199,770 token），方向与 r28 正序相反。两次 200 Gbps 复测的总吞吐亦相差 9.04%。r48 两次 100 档原生交接减至零的模型总吞吐增量均约 0.16%，端口及 D 供给采样也仅观察到短时重叠。因此扩容后的总吞吐排序仍不能作为带宽因果证据。 [r48 实机与模型](restore-workload-screen.md#r48-同源扩容实测)

## 两次 100 Gbps 大差异怎样产生

沿 r28 **原来最后完工的会话**逐轮重算终点，再扣掉 r39 另一条会话成为末链带来的时间。令某轮首 token 后时间为 $g=N\tau$。两次观测的差可精确写成 $(N_A-N_B)(\tau_A+\tau_B)/2+(\tau_A-\tau_B)(N_A+N_B)/2$，分别对应输出工作量和有效每 token 驻留。$\tau$ 包括连续组批、调度和流式处理的影响。对同一会话逐请求相加时，保留实际前驱释放和首 token 前时间。这个分解避免把换到另一条末链所带来的差误算成解码提速。[逐会话及逐请求数据](../results/2026-11-20-r39-bottleneck-verification/cross-run-comparison.json)

| 同档对照 | r28 末会话的完工，r28→r39 | 其中输出长度变化对应时间 | 该会话提早 | 新末会话比它晚 | 整轮提早 |
|---|---:|---:|---:|---:|---:|
| 100 首轮，`crack-7z-hash` | 474.30→403.14 s | 71.85 s | 71.17 s | 1.60 s | **69.57 s** |
| 100 反序，`gpt2-codegolf` | 547.45→237.82 s | 365.89 s | 309.63 s | 161.73 s | **147.90 s** |
| 200 首轮，`crack-7z-hash` | 474.42→396.56 s | 70.09 s | 77.87 s | 4.52 s | 73.35 s |
| 200 反序，`crack-7z-hash` | 463.67→395.91 s | 69.26 s | 67.77 s | 8.52 s | 59.25 s |

首轮的 `crack-7z-hash:35` 从 **8,192→3,335 token**，首 token 后从约 123.3→48.1 秒。反序的 `gpt2-codegolf:31` 从 **24,098→1,393 token**，首 token 后从 329.3→24.4 秒。与此同时，r39 里 `extract-elf:11` 从 337 或 416 增至 8,192 token，`:16` 从 806 或 913 增至 10,479 token，把该会话推到尾部。整轮输出总量增加与 r28 原末会话的实际工作减少可以同时发生。正式优化按 r28 的自然生成条件验收。[链路分解](../results/2026-11-20-r39-bottleneck-verification/cross-run-comparison.json)

同样两次 100 Gbps 对照中，D 端口累计发送分别为 **100.43→100.07 GB** 和 **102.61→106.00 GB**。沿各自会话的前驱统计，P 换实例从 60、61 次变为 69 次，D 换实例从 65、49 次变为 50 次。MAC 计数反映端口实际发送，逐请求的恢复量仍受 APC 和路由影响。这组数据约束了用跨机减量或 P 命中提升解释数十个百分点的整轮差异。[同口径端口与去向](../results/2026-11-20-r39-bottleneck-verification/cross-run-comparison.json)

在固定 r28 两次 100 Gbps 的逐条输出量、路由和非生成阶段的模型里，要达到所比较的 r39 吞吐，完工需到 **364.19、374.30 秒**。若只改 D 首 token 后的服务，所有请求的这段时间需统一缩短 **27.00%、36.37%**。这给保持原生成工作时所需改动的量级，实际执行时还会受到组批和资源反馈影响。[计算入口](../pd_kv_transfer_opt/profiling/compare_session_runs.py)

## 同工作量下的实际批次与生成步

以 r33 和两次 r39 的 100 Gbps 对照为主。两个 D 的输出量在三轮均为 **73,231 / 91,431 token**。r33 的两条竞争末链分别在 419.70 和 411.33 秒结束。r39 首轮变为 403.14 和 404.74 秒，反序变为 397.17 和 399.54 秒。D0 与 D1 都提前，最后完工由 D0 换到 D1。对称替换同一组已观测阶段，正序和反序的总时差 **14.96 / 20.15 秒**中，P HTTP 对应 **3.19 / 7.09 秒**，首 token 后生成对应 **11.65 / 12.27 秒**。这两组数据找到了时差在执行中的位置。[阶段与实例终点](../results/2026-11-20-r39-bottleneck-verification/cross-run-comparison.json)

## 如何转成保持原工作量的设计

**P 首批准备。** 已将 r39 第四臂实测的前 16 批间隔放进 r33 和 r39 首轮的原 P1 时间线。回放维持每个批次的请求和 token，按原 scheduler 接纳时点限制可派发批，核算第一条后继进入前能完整结束的 13 条 P1 冷请求，再传播各会话依赖。原始节拍代回时，复现三轮实际排空。采用后续轮节拍时，保留输出量、路由和其余阶段驻留，得到 **392.33→397.10** 和 **406.84→410.35 token/s**，分别增加 **1.21% 和 0.86%**。这给预执行冷路径或减少上一批完成到下一批启动的等待一个量级。验证时应保持请求和 KV 初态，单列 readiness 之前的准备成本，以及已经持续运行时的服务吞吐。若进入系统方案，将分别定位首次启动、设备服务及 host 回执。[已执行的条件回放](../results/2026-11-20-r39-bottleneck-verification/cross-run-comparison.json)

**D 两条接近完工的会话。** 模型保留各实例的可运行时刻、请求级串行进度和后继。如下比较仅缩短已观测的单请求 D 窗口，逐条重算实际输出工作量下的排空。r39 两次 100 档两条末链之间只隔 **1.60／2.37 秒**，加速当前最后一个实例，很快会换另一条链决定完工。用 D 总 token 做静态均衡也解释不了现象。r28 反序两实例的输出是 76,015 和 78,244，终点仍相差 102.41 秒。r39 同档反序两实例的总量相差 18,200 token，终点只差 2.37 秒。候选调度按实际 D 推进和会话前驱评估两条链，单实例的局部吞吐改善要通过新的最大完工时刻验证。[会话依赖模型](problem-model.md#会话闭环生成工作量与完工)

| r28 自然首轮 | 312.38 | 320.03（+2.45%） | 320.03（+2.45%） |

| r39 首轮 | 406.84 | 408.45（+0.40%） | 419.49（+3.11%） |
| r39 反序 | 412.12 | 414.59（+0.60%） | 425.21（+3.17%） |
