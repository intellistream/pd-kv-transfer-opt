# 双机 2P2D 研究七步法

2026-11-19。按《2026-11-12-Tailguard》第 1、3–11 页的七个问题维护。PPT 的四卡 TP1 实验用于理解原来的提问结构。下文的问题、证据和基线来自双机 16 卡 910B2、Qwen3.5-35B-A3B BF16、2P2D，每实例 attention TP4 / expert EP4。每次改变主张时，记录改变它的证据和受影响的后续步骤。[运行域](deployment.md#运行域) · [实验证据](results.md) · [相关工作](related-work.md)

## 1. What is the problem?

在多轮 P/D 分离推理中，下一轮 P 的本地 APC 缺页时，需要从 D 侧远端池恢复历史状态。原生同步恢复会为同一个 GQA head 的两份目标页分别跨机读同一个对象。当前原型让同头 rank 分担跨机读取，在 P 侧补齐另一份。SSM/卷积状态继续逐 rank 恢复。当前研究问题是 **消除重复读取后，哪些剩余的远端恢复等待仍会拖慢首 token 或排空，且能被稳定缩短**。[状态与可见性](problem-model.md#kv-对象物理字节与可见性) · [r20 逐轮复盘](results.md#逐轮阶段复盘)

当前研究范围固定合法前缀、TP、P/D 路由、P→D 交接和数值语义。读与重算是单独的竞争对照。APC 开启时，决策只作用于本地 APC 之后确实需要远端恢复的部分。

## 2. Why does it matter?

**已验证。** r14 使用 223,256 和 238,600 token 热前缀，每轮 96 请求，16 请求/s 到达、每条产出 16 token，关闭 P 本地 APC。每轮 D→P 有效载荷固定为 914.164 GB。D 侧八口聚合上限从 100 提升至 200 Gbps，排空吞吐 **16.85→33.11 token/s（+96.5%）**，TTFT p99 **85.97→41.06 s**，最慢 rank GET p50 **1.707→0.828 s**。三组回切方向一致。[r14](results.md#r14-远端恢复限速)

同步 Store GET 是可干预的阻塞点。100 Gbps 下，P0 rank 0 诊断窗口内设备 `hccl_batchGet` 覆盖同步 GET 墙钟的 99.73%，与设备计算重合 0.022 ms。抓栈看到 EngineCore 等 worker、worker 等 GET。100→200 Gbps 时，平均 TTFT 的缩短主要来自 P 调度排队 12.68 s、派发至批次结果 8.05 s、调度器接收前 5.78 s。因果链是 **D→P 服务受限 → 同步恢复变慢 → 取件与批队列放大**。端口异常或拥塞停顿时长还需要专门的计数器证据。[阶段归因与边界](bottleneck-and-validation.md#同步读取怎样放大等待)

批次依赖的粒度已经有实测证据。r14 的 265 个可匹配 batch 中，有 141 个在最慢 rank 结束 load 前，rank 0 已进入本地 host forward。一个 TTFT 为 84.31 s 的请求，自身最慢 rank GET 约 0.95 s，所在批次各 rank 的其他 GET 合计约 10.68–11.24 s。预测对象应是等待发生的具体 join 和批结果。本地 rank 准备就绪即可进入一部分计算，而同步 GET 仍可把等待传给同批和后续批次。[批内和跨批事件](bottleneck-and-validation.md#同步读取怎样放大等待)

r15 证实合并读取可以把跨机载荷减少 49.66%。r16 在固定跨机字节后，把并发下约 3,700–3,780 次本机广播收为 18–19 次，分发 p50 降约 67%。两档吞吐分别增 15.96% 和 33.87%。因此本机分发也确实可以独立影响服务结果。APC 开启的自然会话 r11/r12 中，P 同步 GET 仅占观测窗口 0.23%–0.29%，当时施加双向竞争主要改变 P→D，完整吞吐只变动约 0.87%。两类实测限定了问题何时显著。[r15/r16 与自然对照](results.md)

r18 用同一原长会话和固定 D 原档补齐了实际打包 trace。APC 开启时，49/170 条请求确实远端恢复，实际 GET 载荷为 33.920 GB。按同一批请求的原生目标描述符，未经减量需 64.686 GB。本机分发确实延后有恢复的 rank 启动，48 个含打包的批次仅 1 个出现前一笔 copy 后才开始第二笔 GET。回放数据支持部分命中的跨机减量，限制了把机内分发积压作为自然会话主因的假设。[r18](results.md#r18-原长会话打包分发-trace)

r19 在同数据集中选择实际远端读量高、首次换 P 的 10 条真实后继。APC 开启时，原生直读每轮恢复 **41.832 GB**。同一恢复计划用同头单读加打包后降至 **21.238 GB**，端口计数同步下降约 49%。100 Gbps 下，TTFT p99 两次回切降低 **20.3%–23.5%**，排空吞吐增加 **5.1%–6.3%**。200 Gbps 下分别改善 **8.7%–13.8%** 和 **1.5%–5.8%**。P 同步恢复得到净缩短，固定长输出仍使最后一条请求在 D 上生成约 17 秒。这个负载验证了 APC 开启时，远端服务仍能成为首 token 关键路径上的可干预瓶颈。[r19 配对与阶段](results.md#r19-apc-开启的高远端恢复-ab)

另核对了 PPT 中的邻近工作。SYMPHONY 用未来请求提示把加载移出关键路径，KVServe 在线选兼顾服务质量的压缩配置，EdgeFlow 将远端迁移与激活重算结合。MCF 在 chunked prefill 中改变暂存 KV 的复制策略。上述机制提供需查重的边界。本课题的候选动作发生在固定合法前缀的恢复中，选择何处最终产生各个同头目的页。[SYMPHONY](https://www.usenix.org/conference/nsdi26/presentation/agarwal) · [KVServe](https://arxiv.org/abs/2605.13734) · [EdgeFlow](https://ieeexplore.ieee.org/abstract/document/11619197) · [MCF §4](https://arxiv.org/html/2610.34731v1#S4)

## 4. What is the key idea?

**论文主 key idea 待确定。** 同头去重与同步打包归为当前方法的工程组件，也是后续方案的强基线。它们在 APC 后按 GQA 同头子组减少跨机读取、保留原 NPU 目的页和逐 rank 私有状态。r19 证实这一实现能减少 49.23% 的跨机载荷，并在两档限速下缩短同步路径。公开 AscendStore PR 已覆盖同步分片读取、打包与机内汇聚，SGLang 已覆盖全复制对象的一读多分发和混合状态预取。[r19 实证](results.md#r19-apc-开启的高远端恢复-ab) · [同一入口的先例](related-work.md#同一-ascendstore-入口的公开方案)

同批异步是本机补齐的可选组件。r20 中，地址互斥的下一笔 GET 覆盖了部分分发，四对的排空吞吐小幅提高，两档 TTFT p99 均有反向配对。新主 idea 需要在同步打包基线上先定位一段可干预的剩余等待，再说明已有机制在这个条件下的局限，并通过匹配对照验证收益。现阶段跨批证据只把已派发请求的 GET 迟发列为候选，是否可提前仍取决于目的页、租约和传输就绪时点。[r20 逐轮复盘](results.md#逐轮阶段复盘) · [跨批等待证据](results.md#跨批等待证据)

## 5. What is the design?

下表记录已实现的远端恢复工程组件。固定打包是当前原型和后续设计的强对照。

| 难点与对应局限 | 设计细节 | 可检查输出 |
|---|---|---|
| **确定真正缺失的数据。** 本地 APC 命中后，完整前缀长度和必须跨机搬运的长度不同。 | 从原生 worker 的已掩码描述符得出实际缺页，按前缀版本、状态组、head、逻辑页和布局判断等价。支持逐 rank 私有 SSM/conv checkpoint。 | 同时核对 APC 后的有效字节、私有状态描述符及快速数据抽样。 |
| **避免把同一份状态重复送过网络。** 现有共享键不能阻止所有消费 rank 各自发 GET。 | 两个同头 rank 提交前核对请求顺序和 Attention 描述符签名。匹配后按组内条带分摊远端读，另一份由本机打包补齐。签名不匹配或无可共享 Attention 时沿原生路径。 | 按实际描述符和 D MAC 核对跨机减量，量化签名与配对的开销。 |
| **使本机补齐代价可控。** 高并发碎片可带来大量小提交。 | 使用已有有界打包缓冲与批量拷贝，分发完填回原目的页。用 batch 和 rank trace 观察同步路径，区分等另一个 GET、等待本机分发和等待真正下一步 forward。 | 单次分发墙钟、提交数、本机实际串行同批 GET 数、全 rank 窗口和服务指标。 |

当前原生 GET 可以把 Attention 与私有状态放进同一批 API。现有 trace 能确认分类字节和整次完成，私有状态独立完成时刻仍未观测。保留原同步发布约束，按原生负责的 pad/mask 与状态完整性判断继续运行。[批依赖与运行域](problem-model.md#传输服务与-batch-的因果约束)

现有启动脚本启用了 `HCCL_INTRA_ROCE_ENABLE=1`，CANN 在部分 Atlas A2 配置下允许机内通信走 RoCE。r15 第一配对组两档都观察到，新增约 454 GB 本机分发时，P 侧八口 MAC TX 仍约 932 GB，P MAC RX 随跨机减量由约 928 降至 467 GB。已监测的八口 TX 没出现对应的新增载荷，设备通路和共享端点还须用路径事件验证。模型可在证据支持时给两条路径添加共同的端点约束。[P 端口原始摘要](../results/2026-11-18-r15-same-head/summary.json) · [启动配置](../pd_kv_transfer_opt/experiments/serve.py) · [HCCL 环境变量](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/hcclug/hcclenvref_07_0007.html)

## 6. What is the experiment plan?

负载来自固定版本的 Terminal-Bench 2.1 DeepSeek-V4-Flash 轨迹，诊断用 `regex-chess:120` 与 `winning-avg-corewars:145` 两条完整历史。自然会话用同来源的 170 条请求并保留轮间依赖。来源版本、分词指纹和回放方式见 [数据集与负载](workloads.md)。

| 试验 | 当前状态 | 判定 |
|---|---|---|
| 固定字节与固定分发路径回切 | r14–r17 已做。用原生直读、直接分发和固定打包分离跨机字节与本机提交次数。 | 100/200 Gbps 的高远端恢复中已有明确收益，原档短轮的吞吐和尾延迟差异方向混合。 |

### r18 原长会话的 trace 判据

使用原 r11 的 170 条闭环请求、固定 P/D 路由和逐请求输出，开启 P 本地 APC，保持 D 八口各 200 Gbps 的原始设置。历史 r11 有 48 条实际远端恢复，46 个恢复批次里只有两批各恢复两条。它保留真实原生 GET 耗时，缺少打包分发和全 rank forward。r18 仅补一轮固定打包。只对同头组内描述符序列及签名可匹配的非空 Attention 状态采用打包，其余走原生读。记录 APC 部分命中下的短校验、打包前对齐开销、每次 GET、每 rank 本机分发与 forward，采用批键和实际 worker 窗口对齐。

同步分发结束后同 worker 才发下一次 GET。按这条实际串行关系区分先前 copy 延迟后续 GET、不同 pair 的分发重叠、单独一次本机分发等待。`pair_wait` 包含较慢 GET 和配对同步，独立计量。把所有 copy 服务设为零、维持 GET 服务和配对关系，可得到固定观测下最晚 rank 启动门槛的乐观提前量。

三种方案共用同一实际批次、rank 初始释放时刻和可选读法。固定打包复制观测。另两种方案在每批最多替换一个同头组的一次恢复，用 r11 中同一稳定请求、同一 P 实例及 rank、同一原生描述符字节的 GET 估计双读。通信完工选择四 rank 最晚 load 返回更早的动作。批次就绪选择加上各 rank 已观测的本地准备后，最晚 host forward 入口更早的动作。同一目标取额外 D 字节较少者。报告匹配覆盖、实际选取动作的额外字节、原生 GET 耗时 ±25% 的敏感性，以及两种选择的估计差值。结论只解释观测图下的恢复和 forward 启动。调度器 `ready` 事件用于配对和检查先后，真正的 collective 到达或端到端 TTFT 仍需另行测量。[重算程序](../pd_kv_transfer_opt/profiling/analyze_packed_readiness.py)

**结果。** 875 个 P 批次全四 rank 对齐。98 个双 rank 打包操作的 host 窗口出现同一 P 实例的不同组重叠 37 对、不同 P 实例重叠 2 对。重叠只说明时间相交。48 个含 copy 的批次中仅 1 个有两次恢复。该批第一笔 copy 占用各 worker 约 2.0 ms，按程序顺序延迟第二笔 GET。排除两个快速校验批后，188 个 copy 的墙钟 p50 为 3.66 ms，最大 119.43 ms。46 个批次中的去 copy 理想变化表明，各批最晚 rank 的 host forward 可提前的中位数为 4.01 ms。

46 个可重放批次有 94 个单组替换候选，78 个匹配到真实旧原生 GET，其中 38 批的候选全部匹配。两种选择都改变 38 个批次，多用 9.532 GB D→P，累计最晚 rank 启动提前量分别为 158.396 和 158.425 ms。两者仅有一个批次选了不同的读者组，差 **28.55 微秒**，调整原生 GET 时间 ±25% 和只统计有完整客户端收尾的 45 批时结论一致。170 条都保留了 P 批次和代理 `decode_end`，168 条有客户端终点。此轮用于 P 侧证伪，整轮吞吐与客户端 TTFT 缺完整排空数据。[r18 事件与汇总](results.md#r18-原长会话打包分发-trace)

### r19 同数据高远端恢复 A/B

r11 的原生 GET 字节约 96.7% 出现在后继换 P 的轮次。r18 按原生等效描述符计算，该比例约 96.0%。从两份 trace 对应的高贡献会话各选一个首次访问目的 P 的后继，固定原路由、输出和输入。每臂完整执行计时外的 18 条前驱，目标 10 条在 0–0.45 s 固定到达。APC 开启，100/200 Gbps 分别在同一进程内做 A/B 和 B/A。每臂独立缓存命名域，在原档完成前驱准备后限速。逐轮核对实际到达、原生等效字节、端口读回和前驱缓存状态。[负载与清单](workloads.md#r19-高远端恢复的自然后继)

**已完成。** 两档各两次相反顺序，共 80 条目标和 144 条准备请求。两臂原生等效计划相同，约 20.594 GB 减量来自组内消重。数据分开记录 D TX 与 P RX、P GET、配对分发、同批同步 load 和 D 排空。TTFT p99 和输出吞吐四对同向，200 Gbps 时本机代价占省下的 GET 时间比例更大。尾部样本来自相同的 10 条后继，结论限定在受控恢复波次。[逐轮摘要与重算](results.md#r19-apc-开启的高远端恢复-ab)

### r20 同批异步分发

r19 存在多笔分发之间的真实串行。两个 100 Gbps 臂中，P0 的一个四恢复批包含 TTFT 和排空尾请求。固定批次重放给出的可隐藏时间约 0.25–0.28 s，同头 GET 与分发在原路径上为串行。分发可能和同批另一 head 的 GET、其他 rank 的 host forward 重叠。现有记录缺少能对齐实际 prefill kernel 的设备时间原点。[r19 overlap 重算](results.md#r19-trace-提供的机会)

只改同批本机分发的同步位置。一笔 copy 在既有 NPU 流提交后，同一 worker 发同批下一笔地址互斥的 GET。下一次同头汇合和最终 forward 之前等待在途 copy，继续用同一 wire buffer。固定 r19 的 18 条前驱、10 条计时目标、P/D 路由、APC、到达和输出，两臂 GET 载荷均为 21.238 GB。分别在 100/200 Gbps 比较。用 copy 的 NPU 事件状态和 GET 本地边界算重叠下界，随后核对同步 load、TTFT 与排空。

**已完成。** 两档各做 A/B 与 B/A，80 条计时请求全部成功。四对的跨机 GET 保持逐请求相同，100 Gbps 吞吐提升约 0.83%–0.84%，200 Gbps 提升约 0.53%–2.98%。TTFT p99 的变化在 100 Gbps 为 −6.85% 和 +0.61%，在 200 Gbps 为 −2.87% 和 +1.92%。P0 的设备事件重叠下界约 278–316 ms，同步 load 净省 99–180 ms。两档的 p99 均按小样本方向混合报告。[阶段与配对数据](results.md#r20-同批分发与下一笔-get-的异步重叠)

**复盘判断。** 局部预期成立。三个能够按相同恢复顺序匹配的 P0 批，最晚 worker 到最晚 host forward 缩短 123、227、215 ms，固定服务回放分别预测 245、245、186 ms。100 Gbps 首对的关键 rank GET 多耗约 96 ms，解释预测偏高的主要部分。100 Gbps 反序的尾请求在引擎内变快，损失集中在末批结果至 P HTTP 返回及实际客户端派发。200 Gbps 反序的主要抵消在 P 接纳前与 D 查池前，且领先的排空请求在首笔可重叠 copy 提交前就已进入不同的批形。异步保留为局部组件，端到端尾延迟按实际批形和全链路核验。[逐对定位](results.md#逐轮阶段复盘)

**跨批异步判据。** r19/r20 各 88 个批的复核留下 31/29 个与旧 GET 相交的无自身 GET 批，全部包含前序结果未交付的同一请求。现有 trace 支持继续观测调度、发布和取件之间的依赖。r20 有 24/80 个首次恢复请求在等待 worker 时与其他请求的 GET 相交，可用于检查 connector 是否迟发。缺少目标页和租约何时可用、哪个 future 挡住 executor 以及何时有传输容量，因果判断需要这些事件。[跨批等待证据](results.md#跨批等待证据)

## 7. What is the takeaway?

**已成立。** 在受控的高远端命中、长前缀回放中，D→P 服务是吞吐约束。同步恢复会把 GET 的等待传给批队列。合并原生重复读降低了网络下界，同字节下压缩本机提交次数又能改善吞吐。

**当前结论。** 数据支持按 Hybrid 实际缺页消除同步路径上的重复读取。r19 把那部分读取压到约一半，P 阶段和 TTFT 明显缩短。D 长输出占据排空尾部，整轮吞吐增幅较小。r18 原会话中串行分发积压稀少，继续用来约束低恢复压力端。模型应分别预测端口服务、P 批结果和 D 排空，依据真实缺页和批依赖给出何时有收益的可复核判断。[r18](results.md#r18-原长会话打包分发-trace) · [r19](results.md#r19-apc-开启的高远端恢复-ab) · [数学模型](problem-model.md#减量如何传到服务指标)

同批流水的实证支持给模型加入单份在途 copy、下一笔独立 GET 和批尾发布门槛。局部重叠传到 TTFT 的幅度会随批次组成、GET 等待和 D 首步变化。r20 的有限波次保留了吞吐的小幅收益，TTFT p99 的效果随配对轮变化。[r20](results.md#r20-同批分发与下一笔-get-的异步重叠)

同头去重和打包作为工程组件进入后续强基线。论文主贡献以此基线之上可解释、可复现的改进为判据。[当前定位](#4-what-is-the-key-idea)
