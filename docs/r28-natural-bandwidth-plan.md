# r28 自然长会话带宽对照计划

2026-11-19。定时检查确认两台 8 卡 910B2 同时空闲后，以 `cd422eb` 对应代码完成四臂实验。两机服务已停止，D 八口读回恢复至实验前的 200 Gbps/口。[r28 实测结果](results.md#r28-原生长会话的-100200-gbps-正反序对照) · [部署复查](experiment-audit.md)

## 问题与比较口径

用同一个原生 vLLM + vLLM-Ascend + Mooncake baseline 比较 D 的聚合出站上限 100 和 200 Gbps。检验自然缓存命中和原始长会话并发下，100 Gbps 能否复现明显且可重复的整轮吞吐劣势。此轮只改变 D 端硬件带宽上限。

整轮输出吞吐等于全部正式请求实际输出 token 总数除以首条计划投放到最后一条成功完成的时长，包含排空。整轮结果同时列出成功请求数、实际输出总量、时长、token/s，以及 100 Gbps 相对 200 Gbps 的吞吐损失 `1 − X100 / X200`。阶段速率和 profiling 用于查因。[吞吐计算](data.md#结果与事件契约)

## 负载与缓存

| 项目 | r28 设置 |

| 输入 | 固定 Terminal-Bench 2.1 的 30 个独立会话窗口，共 170 条请求。范围约 32.9K–207.7K token。沿用原 prompt token 指纹及会话内前驱。所有正式前驱与后继都计时。 |
| 到达 | 复用 r10 的会话起点序列，使用高压计划中的 8 会话起点/s 参数，最后一个起点约在 4.56 秒。后继在前驱完整输出之后释放。8 描述外部会话起点参数，实际入服请求率由回放记录计算。 |
| 回放假设 | 助手历史和工具结果沿用源轨迹。工具间隔缺少实测，使用清单中的零间隔。源轨迹的助手输出文本继续作为下一轮的输入历史。 |
| 生成 | 保留 EOS 和确定性采样。逐条生成上限取 8,192 与源轨迹记录的输出 token 数中较大者，受 262,144 上下文约束。8,192 是本次回放的预算选择。源输出量只用于设置预算，实际长度和 `stop`、`length` 结束都从客户端采集。 |
| 路由 | 代理使用上游原生路由和上游 HTTP 连接复用。两档使用相同路由策略与初态，记录每条实际 P/D 去向以及每个 D 的输出量。 |
| 缓存 | P APC 开启，D APC 沿用已测试的关闭配置。D Store 每 rank 16 GiB，共 128 GiB，P 不提供 Store 容量。每臂开始时 Store 确认为零键。两 P 的 APC 重置 API 在该版本返回 404，因而每臂使用独立 `cache_salt` 隔离逻辑命中。旧本地页可随内存压力被驱逐。同臂内缓存随实际请求产生和复用，保留自然的冷算、本地命中、Store 命中和驱逐。 |

## 执行顺序

1. 两机按已发布代码启动四个原生实例。核对 2P2D、每实例 Attention TP4 和专家并行、DP1。P 保持默认图模式与 4096 捕获列表，D 保持 `FULL_DECODE_ONLY`。两侧分块预算 4096、每实例 16 槽、显存利用率 0.8，Store lookup 每实例使用独立 IPC 标识。此次以四个 API 就绪和原负载预检进入正式计时，快速验收以首批请求完成和正式臂全量计数为准。
2. 在独立 Store 和排空的两侧引擎上准备每个实验臂。记录 Store 初始键数、P 缓存重置回执或实用的命名域隔离方式。每臂重建代理初态。分别应用 D 八口 12.5 Gbps/口（聚合 100）和 25 Gbps/口（聚合 200），读回全部端口。完整重放同一批会话并排空。每臂结束恢复当轮原端口档位并读回。
3. 第一对按 100→200 进行，第二对按 200→100 复测。比较吞吐方向与同档复测的波动，同时核对实际输出量、最后完成的请求及其尾部时长。端口和 D 侧供给用于检验带宽的因果归因。
4. 正式计时关闭详细方法插桩和 CANN profiler。用低开销端口计数、引擎指标和客户端完成事件解释结果。需要拆解具体等待时，在归因轮独立采样。每轮保存版本、配置、校验值、成功数、初态和限速恢复回执，并及时清理确认无效的日志与重复数据。

首对所需机时随实际 EOS 和排空变化。按原轨迹总输出约 54.5 万 token 及历史双 D 输出速率量级估算，可先预留约 25–40 分钟完成启动和两档。反序复测另留一对的时间。这是机时规划估算，r28 实际时长以完整排空为准。

## 如何判定原因

| 观测 | 归因 |
|---|---|
| 100 档有持续的端口压力、P 有待恢复工作、D 可运行任务供给下降，200 档缓解且整轮改善 | 证据支持带宽限制传导到了整轮吞吐。关联方向、热点端口、P 恢复和决定排空的请求。 |
| 100 档传输或早期交付变慢，D 仍有足够工作，最后排空接近 | 报告 RDMA 局部受限与本次整轮差值。核对 D 入队、实际交接、解码和每路负载。 |
| 两档端口都未出现持续压力，实测总吞吐接近 | 报告该自然负载下的带宽压力和结果。若后续需要更大压力，用同源更多独立会话扩充持续到达，保留 APC 与 EOS。 |
| 200 档整轮吞吐更高，端口和关键 GET 缺少持续受限的证据 | 保留实际原生吞吐差，拆分输出量和完工时长，并核对实际路由及排空链。r28 正序生成量不同，反序差异集中在 D 侧生成尾部。 |
| EOS 结果或路由负载分布明显偏移，吞吐差值随顺序波动 | 分别报告实际输出量、排空时间、每实例流量和输出。用反序复测检查效应的稳定性。 |

每档保存实际 D MAC TX/RX 累计字节、逐口速率及接近上限的时长、P 本地计算/本地 APC/外部恢复 token、Store 占用及驱逐、D 运行和等待、每请求完成及输出长度。P 的外部 token 与 D 的 MAC 字节保持各自的计量口径。需要逐请求实际 GET 与 P→D 描述符字节时，在归因轮采集。[历史分阶段归因](critical-path-attribution.md#r27c-原生路径的带宽与排空归因)

## 后续自然高压的原生对照

r28 的原生配置是部署 baseline，两对自然 EOS 实测提供 200 档高于 100 档的历史观察。原始会话集中在 4.56 秒内启动。后续主负载用同源的更多独立长会话拉长投放，保留会话依赖、P APC、EOS 和原生路由。两档在同一部署按 `100→200→200→100` 回放相同的会话名单和起点，核对逐口硬件限速和缓存初态。[r28 实测](results.md#r28-原生长会话的-100200-gbps-正反序对照)

用正式跑前确定的持续投放区间对齐逐口限速压力、关键恢复 GET 等待、P→D 实际交付和 D 的可运行工作。主场景需要在 100 档看到持续受限及向下游的传导，在 200 档看到约束缓解，并在正反序复测中看到含排空总吞吐改善。保存所有完整对照，同时列出实际输出量、整轮时间和终点会话。遇到 EOS 或路由偏移时，用固定输出及去向的附加对照隔离带宽效应。r40/r41 用于解释冷首波调度和生成尾部。[r40/r41 归因](r40-prefill-order.md#原生跨档与负载复查)
