# Terminal-Bench 原生 2P2D 的 NPU 实验计划

2026-11-24

## 主场景

研究主线为两向 KV 搬运以及与计算的重叠。历史 r69/r78 使用 **D 出站聚合 100 Gbps** 的集中自然回读做机制验证，同负载 **200 Gbps** 作对照及回归。r43 原始自然负载用于评估常规吞吐，Basin 长上下文窗口 v1 用于检查突发拥塞及恢复。D 八口各读回 12.5 或 25 Gbps，P 维持原档。余量按实际方向、逐口压力、待发工作与关键路径判定。P→D 另用已有双向限速轮辅助定位，明确 P 出站条件与 D 目的页状态。 [关键 NPU 实测](../results/2026-11-24-native-npu-reference/README.md) · [Basin 窗口 v1](basin-windows-v1-review.md) · [r43 历史原始档](r43-native-decode-apc.md)

两台 8 卡 910B2、Qwen3.5-35B-A3B BF16、每实例 Attention TP4、Expert EP4 和 DP1。使用两侧 APC、D `AsyncRecomputeScheduler`、P 原生分块图、D `FULL_DECODE_ONLY`、4096 分块预算、16 槽和 262,144 上下文。D 通过 `MooncakeConnectorV1` 从 P 拉取交接 KV。同步 `AscendStoreConnector` 从 P/D 各 64 GiB 的共享池恢复缺页，两侧启用就近分配。保留原生路由、自然 EOS 和固定版环境。以下归档数据与 CPU 校准对应历史 D 单侧 128 GiB，新的带宽效果以双侧池下的实测来源和端口观测为准。 [固定版部署说明](decode-apc-baseline.md) · [本地配置模板](../configs/ascend-2p2d-decode-apc.example.json)

上机先核对两侧各八个 8 GiB 的实际 segment 注册，再用少量自然请求核对共享复用和读源。随后沿用已冻结的负载和带宽顺序，给双侧池结果记录独立布局标识。正式计时与详细 profiling 单独运行。

### Basin 突发的实机顺序

等待两台 NPU 机器确认可用。机时有限时，先用 r69 原生负载在当前双侧池重建带宽基线。Basin 窗口 v1 作为独立的拥塞与恢复验证，三组共享每档的同一 `steady`。先做 **10 个自然完成臂**，原生取消诊断证实请求、槽和 KV 释放后再做 **2 个终止臂**。每个条件各跑一遍 100/200 Gbps。 [Basin v1 评审](basin-windows-v1-review.md) · [执行矩阵](../configs/basin-windows-v1/matrix.json)

每臂 32 次预热，正式计划 304–448 次调用。使用 seed 216、自然 EOS、双侧 APC 和原生路由，突发第 60–150 秒，基础流继续到第 360 秒，随后排空。优先用首对实测核对 EOS、D 准入、Store 驻留和带宽压力。五倍组的 CPU 代表样本表现为 D 等待增加且共同基础流吞吐走低。原始总吞吐随负载与输出量变化，后续性能 A/B 保持负载、带宽和原生基线一致。

几十次调用的短测用于工具链功能回归。正式统计从同一清洁初态完成预热后开始，按实际请求、实际输出和最终排空时间验收。

#### 机时预算

窗口 v1 前十轮 CPU 预算约 **4.52–4.94 小时**，含两轮已验证终止时约 **5.38–5.87 小时**。完整矩阵预留 6–7.5 小时负载机时，启动、现场取消诊断、详细 profiling 和后续复测另计。 [预算与计量范围](basin-windows-v1-review.md#上机计量和归档)

### r43 常规长会话

保留 r43 的 **48 个会话窗口和 254 条原请求**。前 12 个根请求沿用 0–1.60 秒的偏移，其余 36 个从第 5 秒起每 2.5 秒投放，最后一个在第 92.5 秒。后继等待实际前驱完成，用原输入和原生成预算，服务照常判定 EOS。两个 200 档各有 246 条以 EOS 停止、8 条达到原预算。提示中位数为 45,490 token，输出中位数 433/458 token。这是同类长上下文 multi-turn Agent 的可复算服务负载。输入来自另一个模型的终端任务轨迹，后继沿用其历史工具结果，回放的工具间隔为零，根到达由实验计划给定。对真实客户的负载分布和端到端 Agent 行为，仍需客户数据。 [冻结清单](../configs/workload-r42-natural-sustained.json) · [来源和投放](r42-natural-sustained.md)

r45 是 170 条、30 会话的短投放复核，r48 是同 254 条输入的突发投放复核。两者历史上为双向限速，r45 的输入也是 r43 的子集。若将其用于确认通用候选，在主协议下重建原生对照。跨输入的外推使用预先冻结的独立原会话。r69/r78 的短生成和集中恢复用于验证 RDMA 问题，首 token 放行、强制输出长度、关 APC 和附加流量留作机制对照。 [突发对照](restore-workload-screen.md) · [放行敏感性](simulator.md#首-token-放行如何放大完工差)

r43 的历史 200 Gbps 正式臂分别为 209,884 / 210,866 输出 token、504.80 / 379.79 秒和 **415.78 / 555.21 token/s**。两个 200 档均未采到 D 口超过各自上限的 85%，但真实输出分布和压尾会话不同。在当前双侧池下用相同输入做 200 Gbps 原生同档复测。单独采四 rank，优先覆盖 **批宽 1–4 与 9–16**，把 KV 就绪、host 提交、计算/访存、最晚 rank 到齐、到齐后机内通信和下一步实际启动关联起来。沿用原生路由及每条请求的自然 EOS。 [四 rank 采集及分析](r43-decode-profiling.md) · [r43 原始记录](r43-native-decode-apc.md)

## 最后一轮 RDMA 收益验证

1. 冻结 r69 的 **53 个会话、106 条原请求**，沿用该轮的计划到达、原前驱、EOS 与双 APC。不增加后台流量、强制路线或同头打包。每臂统一初始缓存，正式计时与详细观测分开。P 保持原档，只设置 D 八口出站总上限，按 **100→200→200→100 Gbps** 回切。读回每口 **12.5 / 25 Gbps**，随后恢复原档。原实测参考 **225.27→245.16、220.91→243.66 token/s**，低档低 **8.11% / 9.34%**。 [冻结到达](../results/2026-11-22-terminal-source-restore-short-guard/workload.json) · [原实测与同字节方法](restore-workload-screen.md#r69-用实际根进度校准后继投放时间)
2. 用相邻 **400 Gbps 聚合参考**核对 200 的剩余约束，八口各 50 Gbps，其他方向仍为原档。若高档继续加快匹配 GET 或降低整轮时间，保留 200 局部受限结论。如需确认平台，再配一次高档反序和 200 参考。高档单点只提供余量诊断。r78 的同量正序用作已有交叉证据。
3. 主结果逐臂报实际输出、含排空秒数、token/s、两种序的相对差和同档变化。归因沿同 P 去向、同 rank 布局、同描述符字节及同实际来源的 GET，记录逐口服务、P 结果、D 已就绪/可运行与无供给、决定完工的 EOS 链。同步记录实际 P/D 路由、APC 命中、分方向载荷和未知来源 GET。匹配输出量和阶段的回放只用于归因。若热点与关键 GET 等待解除后总吞吐持平，确认现负载的带宽收益小。两种顺序都出现关键 GET 缩短、D 供给和整轮提升时，按实测幅度报告。历史 r19 同头打包作为网络工程项的旁证，实际键未知的跨请求减量仍为条件估计。 [历史强压边界](simulator.md#传输主导和解码主导的实测对照) · [逐口实测与同载荷方法采样](../results/2026-11-24-native-npu-reference/README.md)

### 100/200/400 Gbps 的 CPU 回放结果

正序和反序分别用各自的 200 Gbps 正式归档作锚点。三档共用同一参考的实际 EOS、原生去向、到达和逐口字节，保留前驱完成后释放。D 出站档位是唯一干预。两份锚点在 P HTTP 覆盖期间分别传输 192.97/192.50 GB，200 档任一口达到自身上限 85% 的采样时长为 2.22/1.72 秒。不同次序的回放使用不同参考归档，每档沿确定性的 CPU 模型求解。

| 次序参考 | 共同输出 token | 100 总吞吐 | 200 总吞吐 | 400 总吞吐，采用两种突发假设 |
|---|---:|---:|---:|---:|
| 正序 | 19,583 | 224.24 | 244.72 | 244.97 / 252.68 |
| 反序 | 19,352 | 225.04 | 245.26 | 245.26 / 252.96 |

吞吐单位为 token/s。两种突发假设下，100 档分别比 200 档低 **8.37% / 8.24%**，接近归档实测的 **8.11% / 9.34%**。200 档较 100 档使最后一条 P 回复分别提前 5.81/6.60 秒，D 两实例有 P 请求在途却无生成的时间合计少 2.10/3.34 秒，均为回放归因。按整采样间隔匀速发包则只重现 **4.86% / 4.52%** 的低档差距。

每个采样窗口的最多一口平均速率记为 $q$，突发活跃比例记为 $f$。总档位 $B$ 下，容纳已观测字节至少需要原窗口的 $\max(f,8q/B)$ 倍。用与 200 档的差值调整窗口内重合的 P HTTP，再重算 D 进度和会话释放。若突发需求最高已被 200 档满足，400 档的额外收益约 **0–0.10%**。若同量突发可填至 400 档，额外收益为 **3.25% / 3.14%**。两种亚秒需求分布在 100 和 200 档产生相同结果。

补查独立方法轮的 13 个同字节 GET 批，共 123.88 GB。仅 5 批同时满足非负固定成本加反比带宽的服务式与唯一调度批对齐。只对这 5 批外推到 400，固定其他观测阶段，吞吐 **235.37→236.64 token/s（+0.54%）**。该结果覆盖部分匹配 GET，200 档的真实剩余等待仍需 400 档的逐口与方法事件确认。 [逐档总吞吐、服务假设和方法交叉核对](../results/2026-11-23-cpu-terminal-validation/summary.json)
