# Terminal-Bench 64K 连续长会话复测计划

## 实验目的

在原生 2P2D 部署上，从会话第一轮开始投放，让 P、D 的本地缓存和双侧共享池随请求自然形成。到会话连续进入 64K 长上下文后，观察 P→D 交接和跨机 Store 回读的真实流量，判断它们有没有让 D 等不到 KV，或让最后完成的会话拖得更长。

两轮都用每机 RDMA 入站、出站各 100 Gbps。以 TTFT 为主指标，看首 token 延迟及其阶段构成能否复现。整轮输出吞吐为次指标。两次同档复测用来定位网络等待和同档波动，量化带宽对 TTFT 或吞吐的影响需要同负载的不同带宽对照。

## 负载与投放

沿用 [固定版本的 Terminal-Bench 源轨迹](workloads.md)。从原有 30 个源任务中筛选。对每个候选从第一个模型请求开始，保留到首次出现连续 5 条源输入都达到 65,536 token 的第 5 条，包含这条请求。保留上一版满足条件的 7 个会话，从其余合格会话按截断前累计源输出从少到多补 3 个，减少个别长会话占用的机时。

每轮有 50 条请求进入上述 64K 区间。累计源输入为 19,935,241 token，包含各轮重复出现的上下文。P 实际新算多少，由当次的缓存命中和调度决定。64K 筛选与耗时估算使用源轨迹 token 统计。上机前用固定 Qwen tokenizer 物化同一批输入，核对实际 token 数、相邻轮公共前缀和长度上限，单列实际达到 64K 的请求数量。

- **首轮到达。** 以会话名排序，第一条在第 0 秒投放。其余九个起点使用平均 **0.5 个新会话/秒**的泊松到达，相邻首轮之间的间隔按指数分布抽样。用 Python `random.Random(64).expovariate(0.5)` 生成，最后一个会话约在第 27.131 秒进场。两轮复用同一份投放表。
- **后继到达。** 上一条请求完整结束后，等待一段随机时间再发下一条。每段间隔有 90% 概率在 1–3 秒内均匀抽样，有 10% 概率在 3–5 秒内均匀抽样，期望为 2.2 秒。用独立随机种子 65，按会话名与源步骤顺序逐条抽取。每条先抽取区间，再抽区间内的秒数，将 506 个实际间隔写入 `tool_gap_s`，两轮复用。一份固定计划有 453 个短间隔和 53 个长间隔。后继实际何时发出仍取决于前驱何时结束。每条请求保留源轨迹中完整的对话与工具输出。
- **生成。** Qwen 采用 `temperature=0` 和自然 EOS。沿用仓库自然会话的输出预算取法，每条 `max_tokens` 为 8,192 与该条源输出 token 数中的较大者。记录实际输出、停止原因和触及上限的请求。两轮使用同一份物化输入、预算和依赖，记录清单与分词器的指纹。 [自然会话输出预算实现](../pd_kv_transfer_opt/workloads/basin_small.py#L118)

## 部署、限速和轮次

| 项目 | 取值 |
| --- | --- |
| 机器和模型 | 两台 Ascend 910B2，P 机运行 P0/P1，D 机运行 D0/D1，Qwen3.5-35B-A3B BF16。每机 8 卡时用现有每实例 Attention TP4 / Expert EP4 / DP1。只拿到每机 4 卡时，优先准备每实例 Attention TP2 / Expert EP2 / DP1 的 2P2D 部署，按下文核对可用性。两轮使用同一并行配置。 |
| 调度和执行 | 固定版本 vLLM、vLLM-Ascend 和 Mooncake NPU。原生代理选 P/D，启用上游连接复用和 D 原生重算调度器。每实例 16 个请求槽。P 的批 token 预算设为 8,192，D 沿用 4,096。两轮 P0/P1 均开启 MatmulAllReduce，D0/D1 关闭。 |
| 缓存和交接 | 双侧本地 APC 和 Store 就近分配。四卡方案每模型 rank 注册 16 GiB，八卡方案每 rank 注册 8 GiB。两种配置都是 P、D 各 64 GiB。实际复用由运行状态决定，P→D 走原生 Mooncake Pull。 |
| 限速和轮次 | 先跑 100-1，排空并重建相同初态后跑 100-2。每轮两台机器的实验 RDMA 端口均按每机发送合计 100 Gbps、接收合计 100 Gbps 配置，并分别读回。 |

固定版本、实例分组和现场核对步骤见 [原生 2P2D 上机执行](native-npu-run.md)。P 的 8K 预算沿用短测取值。

本次站点部署配置中，设置 `P.max_num_batched_tokens=8192`、`P.enable_matmul_allreduce=true`、`D.enable_matmul_allreduce=false`。启动器把各角色的开关传入 vLLM 的 `--additional-config`，在 `state.json` 的实例启动参数中留档。MatmulAllReduce 将支持的行并行线性层的矩阵乘和 TP 组内归约融合。完成就绪和配置核对后直接跑两轮主实验，从主实验采集 P 的实际等待和计算耗时。 [固定版配置](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/ascend_config.py#L167-L172) · [固定版融合算子](https://github.com/vllm-project/vllm-ascend/blob/5cb98caaadeff42b5b62b996e34bb2aaa29d20fd/vllm_ascend/ops/linear_op.py#L420-L438)

### 四卡部署

从 [四卡配置模板](../configs/ascend-2p2d-tp2.example.json) 生成现场配置，填写两端地址、模型路径和各自获分配的两组实体卡号。每个实例使用两张卡，Attention TP2 与 Expert EP2 共用这两张卡。启动器按卡组大小生成 vLLM 的 TP 参数及两端的 Mooncake TP 元数据。上机核对 BF16 加载、实际输入与输出的 KV 容量，以及 P→D 交接。 [Qwen 模型配置](https://huggingface.co/Qwen/Qwen3.5-35B-A3B/blob/main/config.json)

每台两个实例，共四个模型 rank。每 rank 注册 16 GiB，每台 64 GiB，两台共 128 GiB。上机用两端的 `state.json` 核对 `two-sided-16gib-local-first/v1`，再用 Master 的 `segment_total_capacity_bytes` 确认 P、D 各有四个 16 GiB 的段。 [启动器](../pd_kv_transfer_opt/experiments/serve.py)

### 出站和入站分别限速

服务器出站在本机 RDMA 口用现有 `hccn_tool -shaping` 设置。两台实机的驱动帮助里只查到一个端口整形项，未见独立 RX 限速项。对两端各两个口的 LLDP 查询显示，RoCE 链路接到华为 CE8875 交换机，因此主机入站可以规划在**交换机发往该主机的端口**做发送整形。实施前由网管核对所用端口的整形能力、速率粒度及可用权限，并提供设置前、运行时和恢复后的配置读回。交换机的出站在这里就是服务器的入站。 [CE8875 规格](https://e.huawei.com/en/material/enterprise/68a0c996124e405fa9c32e42213d18a2)

| 每台主机实际参与实验的 RDMA 口 | 主机每口 TX 上限 | 交换机发向主机的每口上限 | 每方向合计 |
| ---: | ---: | ---: | ---: |
| 8 | 12.5 Gbps | 12.5 Gbps | 100 Gbps |
| 4 | 25 Gbps | 25 Gbps | 100 Gbps |

逐口数以卡与 RoCE 端口实际映射为准。P→D 经过 P 的 TX 整形和 D 的入站整形，D→P 经过 D 的 TX 整形和 P 的入站整形。两层串在同一方向各设 100 Gbps，其上限仍是 100 Gbps。发送与接收分别记账，可同时发生。主机 TX 和对端 RX 的计数用于复核，RX 计数本身不等于入站限速的配置读回。四卡就只配置确认属于本实验的活动端口。 [主机限速实现](../pd_kv_transfer_opt/experiments/hardware.py#L41) · [昇腾 A2 端口计数说明](https://www.hiascend.com/doc_center/source/zh/HDK/2610/A2/A2HCCN/hccntoola2_044.html)

## 执行与数据记录

1. **CPU 准备。** 物化 516 条输入，核对首轮、末轮、前驱、实际 Qwen token 数和输出空间。冻结输入和到达表，对客户端和控制端进行 dry-run。单请求和整轮超时、限速保持时间覆盖正常排空。
2. **实机就绪。** 核对两侧获分配的卡和端口，检查四实例启动参数、P 的 8K 与融合开关、Store 初态、代理及 KV 交接就绪。分别保存主机 TX 限额和接收侧交换机配置的初值与写入后读回。两侧就绪并确认每个实验口的发送、接收限额后，直接进入正式回放。
3. **正式采集。** 每轮从首条计划投放计时，等全部请求自然结束，使用相同的轻量采集。每轮收尾保存两种限速的恢复读回。第二轮重建缓存初态并重复。
4. **归档和复核。** 每轮先汇总 TTFT 分位数，再列成功数、实际输出 token、首投至末完时长、含排空吞吐和请求停止原因。核对客户端、双端日志和主机/交换机回执后归档。出现请求失败、首 token 或输出计数缺失、限速失效或外来任务干扰时保留失败证据，标记该轮有效性。最后核对原始限额、关闭本轮服务并释放卡。

| 层次 | 保留的观测 |
| --- | --- |
| 客户端和会话 | 源步骤 ID、前驱、计划起点、每轮抽到的等待秒数、实际发出、首 token、结束、实际输出 token 数、停止原因。保留流式片段的收到时刻和可验证的 token 数，按会话还原前驱与最后完成链。 |
| P 与缓存 | P/D 实际路由；P 排队、首个调度步、各 chunk 的批次与 token 数、P 完成；本地 APC 命中、Store 匹配和实际读取。区分同机、跨机和来源未知，记录对象来源、字节、提交和完成。 |
| P→D 与 D | 交接提交/完成、D 分配、KV 就绪、首个 Decode 步、首 token；D APC 命中、重算、活动批次、运行槽与步进间隔。 |
| RDMA | 两台主机的实验端口约每秒一组 TX/RX，保留采样单调时间、PFC/CNP、重传、主机出站与交换机接收侧限速读回。用逐口差分看热点，并与实际 KV 事件对齐。 |

**主指标是 TTFT**，按客户端实际发出请求到收到第一个生成 token 的时间计算。每轮以全体 P95 为主，附 P50、P90 和样本数，分开报告会话首轮、后继和实际输入达到 64K 的子组。工具间隔另计入会话时间线。

**次指标是含排空输出吞吐**，按实际总输出 token 除以首条计划投放到最后一条完成的时长。TPOT、输出速率曲线和阶段耗时用于归因。用请求 ID、批次 ID 和时钟锚点对齐 P 排队、P 实算、Store GET、P→D 交接、D 等 KV、D 就绪后排队和 Decode 步进。对尾部 TTFT 样本逐条核对阶段，保留重叠区间和覆盖率供模拟器使用。应用层字节和 MAC 字节分别统计。 [现有事件口径](data.md#事件口径)

## 预期结果与对应结论

先看两轮的尾部 TTFT 来自哪些请求。根据历史双侧就近池的结果，重点查长轮重叠时的 P→D 交接，也检查实际跨机的 Store 回读。再结合最终完成链解释吞吐是否受影响。

| 两轮看到的现象 | 可以下的结论 |
| --- | --- |
| 两轮同一方向反复出现端口热点，尾部 TTFT 的请求有明确的 GET 或交接等待，且这些等待挡住了首 token。 | 找到了可复现的网络等待和受影响的请求。后续用同负载不同档位量化 TTFT 对带宽的敏感性。 |
| KV 等待推高了部分请求的 TTFT，但 D 有其他就绪请求可生成，最后完成的会话也未被这批传输拖住。 | 网络可能影响首 token 体验，整轮吞吐仍可能接近。 |
| 两轮端口有余量，尾部 TTFT 主要耗在 P 排队、P 计算或 D 的就绪后排队。 | 在这套配置下，先聚焦实际占用首 token 关键路径的阶段。 |
| 两轮 TTFT 或吞吐差距较大，同时路由、命中、实际输出长度、请求重叠或尾链也变了。 | 按这些变量解释同档波动。 |

## 资源与排期

- **NPU 与网络。** 每机 8 卡的现有部署同时占用 16 张卡，数据回放按每轮 40–50 分钟估算，两轮加启动、重置和收尾预留约 1.5–2 小时，约 24–32 NPU 卡时。每机 4 卡方案同时占用 8 张卡，机时在第一轮确认后更新。两种方案均按实际启用的 RDMA 端口申请交换机配置窗口。
- **估算依据。** 历史 TP4 的 100 Gbps r43 约 400–458 输出 token/s，按 92.9 万源输出折算约 34–39 分钟。最慢候选的固定工具间隔合计约 116 秒，按历史 14.4 ms/token 折算，这条会话约 36 分钟。实际时长取决于 Qwen 的 EOS、排队和排空阶段的批宽。 [历史 100 Gbps 结果](../results/2026-11-25-native-2p2d/throughput.csv#L2) · [历史步进测量](bottleneck-verification.md#L52)
- **CPU 容器。** 输入物化产物、原始日志、配置、投放表、客户端逐请求数据、两端采样、交换机与主机限速回执、派生结果按 `run_id` 存到指定 CPU 容器的持久卷。NPU 容器只留临时运行数据，逐轮确认 CPU 归档完整和哈希后再清理。两轮共 1,032 条计划请求。Git 留可发布摘要与指纹。 [历史归档记录](online-routing-bandwidth-experiment.md#2026-11-20-实测归档)
